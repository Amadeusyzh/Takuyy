## 为什么重要

本专栏的[研究愿景]({{ '/blog/2026/3d-gui-agent-01-research-vision/' | relative_url }})是把 GUI 智能体（GUI agent），即代替用户操作图形用户界面（graphical user interface，GUI）的 AI 智能体，带到 VR、AR 和 MR 设备的三维界面中。在追问三维 GUI 智能体应当是什么样子之前，我们需要准确了解二维 GUI 智能体已经发展到了什么程度。在手机、桌面和网页上，这个领域进展得极快：2024 年 4 月，最好的模型只能完成 OSWorld 中 12.2% 的计算机任务，而人类为 72.4%；到 2025 年 12 月，一个智能体系统超过了人类基线；2026 年，前沿模型已把“计算机使用”（computer use）作为内置能力发布。三维智能体将要面对的几乎每一个设计决策（观察什么、如何指向目标、允许哪些动作、如何训练、如何评测、何时询问用户），都已在二维屏幕上被争论过、测量过，并部分得到了解决。

本文综述截至 **2026 年 11 月** 的相关工作。它按思想而不是按论文来组织：智能体循环、观察、定位、规划与记忆、训练、评测、人与安全。对于关键方法，本文解释它们如何工作（输入、输出、训练信号、循环），并给出关键的数字。每一节都以它对三维界面意味着什么作结，最后一节把这些线索汇集成一份审慎的清单，列出哪些能迁移、哪些会失效。配套文章讨论三维一侧：[为什么三维界面难以操作]({{ '/blog/2026/3d-gui-agent-03-why-3d-interfaces-are-hard/' | relative_url }})，以及 [XR 中的智能体：平台与差距]({{ '/blog/2026/3d-gui-agent-04-agents-in-xr-and-the-gap/' | relative_url }})。

## 前置知识

- 对大语言模型（large language model，LLM）和视觉语言模型（vision-language model，VLM）有基本了解：VLM 读取图像和文本，输出文本。
- 马尔可夫决策过程（Markov decision process）和策略梯度（policy gradient）强化学习（reinforcement learning）的概念（[世界模型系列]({{ '/blog/2026/world-models-01-what-is-a-world-model/' | relative_url }})和[具身智能系列]({{ '/blog/2026/embodied-ai-01-robotics-foundations/' | relative_url }})都有介绍）。
- 不要求具备 GUI 智能体方面的背景。

关于数字的说明。下文的基准分数来自论文、厂商页面和排行榜，它们使用的评测框架（harness）、步数上限和基准版本各不相同，因此不同来源之间只能粗略比较。每个数字都注明了来源和日期；“二手”（secondary）表示仅从新闻报道或聚合网站得知的数字；2025-2026 年的大多数工业系统都是 arXiv 上未经同行评审的技术报告，文中会如实标明。

## 1. 什么是 GUI 智能体

### 1.1 循环

**GUI 智能体**接收一个用自然语言描述的任务（“打开 Wi-Fi”“预订周五飞往大阪的最便宜航班”），并通过操作人所使用的同一个图形用户界面（GUI）来完成它：它看屏幕，决定做什么，然后发送轻触、点击、按键和滚动。因此，任务是*通过界面*解决的，而不是通过每个应用专门提供的 API。这正是要义所在：任何人能用的应用，智能体都能用，而应用的开发者什么都不用做。

形式上，一个回合（episode）是一个部分可观测的决策过程（partially observable decision process）。在第 $t$ 步，智能体拥有指令 $g$、当前观察 $o_t$（一张截图、一段对屏幕的文本描述，或两者兼有），以及它自己的历史 $h_t$，即此前的观察、思考和动作。策略 $\pi$ 输出动作 $a_t$；设备执行该动作并产生下一个屏幕 $o_{t+1}$。当智能体输出 `finish`、宣布任务不可行、询问用户或用完步数时，回合结束。成功与否根据设备的最终状态 $s_T$ 判定：

$$
a_t \sim \pi(\,\cdot \mid g,\; o_{\le t},\; a_{<t}), \qquad \text{success} = \mathbb{1}\big[\,\mathrm{check}_g(s_T) = \text{true}\,\big].
$$

在 $\pi$ 内部，大多数系统运行的都是下图所示循环的某个版本：**观察**（observe，可能还要把屏幕解析成元素），**规划**（plan）下一步，**定位**（ground，把“Share 按钮”变成屏幕上的具体位置），**执行**（act），然后对结果进行**验证或反思**（verify / reflect），并**更新记忆**（memory）。有两条旁路比初看起来更重要：智能体可以**询问**用户（以消除歧义，或确认有重要后果的操作），也可以决定**停止**。

{% include blog_figure.liquid path="assets/img/blog/3d-gui-agent/02-agent-loop.svg" localized="true" caption="二维 GUI 智能体的结构。主循环（紫色）依次执行观察、规划、定位、执行；设备返回下一个屏幕（绿色）。框架式智能体把每个方框实现为单独的模块或提示；原生智能体模型（虚线包络）在一个视觉语言模型中完成全部四步。记忆与反思（蓝色）以及通向用户的询问/确认通道（红色）是各系统差异最大的地方。" %}

两类架构共享这个循环：

- **框架式智能体**（framework agent；2023-2024 年，至今仍很常见）：通过提示让一个通用 LLM 或 VLM 扮演各个角色，配以手工构建的感知模块（无障碍树（accessibility tree）、光学字符识别（OCR）、图标检测器）、记忆文件，有时还有多个相互协作的智能体。AppAgent、Mobile-Agent、AutoDroid、UFO、Agent S 和 SeeAct 都是例子。
- **原生智能体模型**（native agent model；始于 2024 年底）：端到端训练一个 VLM，把截图加历史映射为一段思考和一个动作。UI-TARS、Aguvis、OpenCUA、GUI-Owl、MAI-UI 以及前沿模型（Claude、OpenAI 的 CUA 和 GPT-5.x、Gemini）的计算机使用模式都属于这一类。

这种区分并不严格：原生模型常被包裹在一个轻量框架（规划器、反思器、记忆）中，而框架式智能体也越来越多地调用经过训练的定位模型。

### 1.2 简史，2016-2026

{% include blog_figure.liquid path="assets/img/blog/3d-gui-agent/02-timeline.svg" localized="true" caption="GUI 智能体的里程碑，2016-2026，按时间顺序排列（各行等距排列，时间轴不按比例）。颜色表示所属脉络：UI 数据与理解（蓝色）、合成 UI 上的强化学习（绿色）、LLM/VLM 智能体系统（紫色）、定位与原生模型（橙色）、基准（灰色）、商用计算机使用（红色）。注意下半部分，即 2024-2026 年，比前八年加起来还要密集。" %}

如时间线所示，这段历史可分为四个阶段。

**UI 数据与 UI 理解（2016-2022）。** 人机交互（HCI）与移动系统领域的研究组大规模地挖掘应用。ERICA（UIST 2016）和 Rico（UIST 2017；72k+ 个互不相同的 Android 屏幕，附带视图层级（view hierarchy）和交互轨迹）把屏幕变成了数据。模型学会了为控件生成说明、概括屏幕（Screen2Words）以及对屏幕做嵌入（Screen2Vec、UIBert）。Seq2Act（ACL 2020）把“打开飞行模式”之类的指令映射为动作序列，在其 PixelHelp 测试集上达到 70.59% 的完全匹配率。随后，Google 的 Spotlight（ICLR 2023）和 Pix2Struct（ICML 2023）表明，**只读截图**的模型可以胜过获得视图层级的模型，而视图层级常常缺失或有误。无障碍（accessibility）研究（SUGILITE；以及从像素重建无障碍元数据的 Screen Recognition）贡献了这样一种思路：通过无障碍信息来驱动应用，或者把无障碍信息重建出来。

**合成 UI 上的强化学习（2017-2022）。** 与此同时，强化学习研究者构建了 World of Bits / MiniWoB（ICML 2017），即带有脚本化奖励的小型网页任务（点击这个按钮、填写这个表单），以及 MiniWoB++（ICLR 2018），其中少量演示被用来约束探索。AndroidEnv（2021）把 Android 模拟器封装成强化学习环境。DeepMind 的 CC-Net（ICML 2022）从像素加 DOM 出发，在 MiniWoB++ 上达到了人类平均水平，但需要约 240 万条人类演示：像素级控制行得通，可这样的数据代价，在真实应用上没有人付得起。

**LLM 与 VLM 智能体系统（2023-2024）。** 随着 GPT-4 和 GPT-4V 的出现，基于提示的智能体在所有平台上同时涌现：Android 上有 AppAgent、Mobile-Agent、AutoDroid 和 MobileGPT；桌面上有 UFO、Cradle 和 Agent S；网页上有 MindAct、SeeAct 和 WebVoyager。大型数据集（Android in the Wild，AITW：715,142 个回合）和首批贴近现实的基准（Mind2Web、WebArena、OSWorld、AndroidWorld）也随之出现。这一阶段的主要教训是：瓶颈不在规划，而在**定位**（grounding）。

**原生模型、大规模强化学习与商用计算机使用（2024-2026）。** 在数百万个合成元素上训练的定位模型（SeeClick、UGround、OS-Atlas）和端到端的智能体模型（UI-TARS，2025 年 1 月）取代了手工构建的感知模块。Anthropic 为 Claude 发布了计算机使用功能（2024 年 10 月），OpenAI 发布了 Computer-Using Agent 和 Operator（2025 年 1 月），Google 发布了 Gemini 2.5 Computer Use（2025 年 10 月）；随着 GPT-5.4（2026 年 3 月）的发布，计算机使用成了一个通用模型的原生能力。R1 式强化学习（2025）以及在数千台并行虚拟机中进行的多轮在线强化学习，把多个基准上的分数推过了人类基线，这些基准随后被更难的基准（ScreenSpot-Pro、OSWorld 2.0）所取代。

### 1.3 三个平台

循环在各处都一样，但三个平台在智能体能看到什么、能做什么上各不相同：

| 平台 | 典型观察 | 动作通道 | 实验环境 |
| --- | --- | --- | --- |
| 手机（Android、iOS） | 截图、Android 视图层级 / 无障碍树 | 轻触、长按、滑动、输入、返回、主屏幕（通过 `adb` 或无障碍服务） | Android 模拟器快照（AndroidEnv、AndroidWorld）、真机农场 |
| 桌面（Windows、macOS、Linux） | 截图、操作系统无障碍 API（Windows UI Automation、macOS AX） | 鼠标移动 / 点击 / 拖动、键盘、快捷键、滚动；shell 与应用 API | 带快照的虚拟机（OSWorld、Windows Agent Arena） |
| 网页 | 截图、DOM、浏览器无障碍树 | 点击、输入、滚动、导航、标签页（通过 Playwright / Chrome DevTools Protocol） | 自托管网站（WebArena）、真实在线网站（Online-Mind2Web） |

手机屏幕小，使用触摸手势，而且许多应用缺少良好的无障碍标签。桌面屏幕大、分辨率高，目标细小，窗口相互重叠，还有各种专业软件。网页的结构最丰富（DOM），但内容也最具对抗性。

**对三维而言。** 循环的形状原样迁移，成功的定义（对最终状态的检查）也一样。改变的是方框里面的一切：观察是一个视点（viewpoint），而不是一块屏幕；“定位”必须给出空间中的目标；“执行”包括连续的六自由度（6-DoF）运动；而设备是一台头显，其状态包括用户的身体和所在的房间。第 8 节逐一讨论每个方框。

## 2. 观察：智能体看到什么

### 2.1 结构化观察：视图层级、无障碍树与 DOM

每个 GUI 工具包都维护着一棵控件树。Android 把它暴露为视图层级，并为辅助技术（assistive technology）暴露为**无障碍树**（每个节点有角色、文本或内容描述、边界框，以及 clickable、checked 等标志）。Windows 有 UI Automation，macOS 有 AX API，网页则有 DOM 加浏览器无障碍树。把这棵树序列化为文本，恰好给了语言模型它最擅长处理的东西：一个带名称、带类型、带坐标的元素列表。最早的 LLM 智能体（DroidBot-GPT、AutoDroid、UFO、MindAct）就使用它，它的优点也很明显：标签是精确的，不可见的状态（是否勾选、是否禁用、列表中位于屏幕外的项）可以获取，要操作的元素可以直接点名，而不必去定位。

它的弱点同样明显，并最终决定了这场争论。在许多应用中，树**缺失或有误**：自绘控件、画布、游戏，以及用 `div` 和无标签图标按钮搭起来的网页应用。树**很长**：现代网页的原始 HTML 远远超出模型每一步能读的量，这就是为什么 MindAct（Mind2Web 的基线）要先用一个小模型对候选元素排序，再交给 LLM。树还**依赖平台**：基于 Android 无障碍服务构建的智能体无法在 Windows 上运行。

### 2.2 截图

截图是通用的：每个平台上的每个应用都会渲染出像素。VLM 把截图变成视觉 token。按照 Qwen2.5-VL 系列（2025 年大多数 GUI 模型的基座）的分块方式，一个视觉 token 覆盖 28 x 28 像素的区域，因此一张 1080 x 2400 的手机截图约需 $(1080/28)(2400/28) \approx 3{,}300$ 个 token，一张 1920 x 1080 的桌面截图约需 2,600 个。这是可以承受的，但只占几个分块的小文字和小图标很难看清；高分辨率编码器（CogAgent 的 1120 x 1120 分支）、切片（Ferret-UI 的“任意分辨率”子图）和 token 剪枝（ShowUI）都在解决这个问题。

像素的难点不在于读，而在于**指**：2023 年的通用 VLM 能把屏幕描述得很好，却说不出 Save 按钮*在哪里*。于是出现了两种答案：给模型提供可以引用的标签（下一小节），或者教它输出坐标（第 3 节）。

### 2.3 Set-of-Mark 标签与屏幕解析器

**Set-of-Mark（SoM）提示**（Yang 等，2023）在图像的分割区域上叠加编号标记，使模型可以回答“17”而不是一个坐标。GUI 智能体立即采用了它：WebVoyager、MM-Navigator、AppAgent 和 Mobile-Agent 在每个可交互元素上画一个框和一个编号，这些元素在有无障碍树时取自树，没有时取自检测器。**OmniParser**（Microsoft，2024）仅凭像素构建标记：一个微调过的 YOLOv8 检测器找出图标，一个 BLIP-2 描述模型（captioner）为图标生成描述，OCR 读取文字。配合 GPT-4V，只用截图的 OmniParser 智能体在 Mind2Web 上胜过了获得网页 HTML 的 GPT-4（步骤成功率：跨网站 36.5 对 30.1，跨领域 42.0 对 26.4）。

{% include blog_figure.liquid path="assets/img/blog/3d-gui-agent/02-observations.svg" localized="true" caption="同一个玩具设置屏幕的三种观察。(a) 仅截图：通用，但模型必须在像素中找到目标。(b) Set-of-Mark：可点击元素上的编号框，使模型可以用标记编号作答。(c) 序列化的无障碍树：精确的标签、角色、状态（checked）和边界框，但前提是应用暴露了这些信息。第 4 节的交互组件使用同样的三种视图。" %}

标记也有代价：检测器的错误会向下游传播，标记会让密集的屏幕显得杂乱，还可能遮住它们所标注的内容；SeeAct（ICML 2024）发现，图像标注的效果明显不如给 GPT-4V 一个候选元素的文本列表（离线 Mind2Web 跨任务步骤成功率 20.3 对 39.1）。

### 2.4 哪种观察胜出，为什么

证据随着模型而变化。下图汇集了只改变输入的几组最清晰的对比。

{% include blog_figure.liquid path="assets/img/blog/3d-gui-agent/02-input-evidence.svg" localized="true" caption="同一智能体在不同输入下的任务成功率，来自四项研究。OSWorld（Xie 等，NeurIPS 2024，表 5）：对 GPT-4V，仅截图为 5.26%，截图 + 无障碍树为 12.17%；对 GPT-4o，仅无障碍树为 11.36%，仅截图为 5.03%。AndroidWorld（Rawles 等，2024）：GPT-4 Turbo 使用文本无障碍树为 30.6%，使用截图 + Set-of-Mark 为 25.4%。EntWorld（Mo 等，2026），一个在企业网页应用上训练的智能体：截图 15.6%，无障碍树 35.2%，两者兼用 53.7%。2024 年，通用模型使用文本时表现更好；在可用时，混合输入的帮助最大。" %}

2024 年，用作智能体的通用模型使用文本时比使用像素时表现更好，两者兼用时最好。2025 年的变化在于，**专为 GUI 训练的模型**让只用截图的智能体先是具备了竞争力，继而占据主导：UI-TARS、Aguvis、GUI-Owl、MAI-UI 以及各前沿模型的计算机使用模式都只凭截图行动；GPT-5.4 报告在 Online-Mind2Web 上“仅截图”达到 92.8%（OpenAI，2026 年 3 月）。这一转变有三个原因：

1. **覆盖面。** 每个应用都有像素，却未必有树。依赖树的智能体会在画布、游戏、远程桌面和标注糟糕的应用上悄无声息地失败。
2. **训练数据。** 定位数据可以*从*结构中大规模生成（把 DOM 中的框渲染成截图，见第 3 节），因此视觉模型可以学到树所知道的东西，然后脱离树工作。
3. **一个模型通吃所有平台。** 截图加通用输入事件（轻触、点击、输入）在 Android、Windows 和网页上是同一个接口，而这正是跨平台原生模型所需要的。

树并没有消失。在有树的地方，它仍是很强的额外信号（EntWorld 的混合结果）；UFO2 等 Windows 智能体把 UI Automation 与视觉解析融合在一起；Apple 和 Google 则通过应用意图（app intents）和无障碍 API，而不是像素，来执行助手的动作。

**对三维而言。** “截图优先”的经验可以迁移：XR 场景的渲染视图是合理的主要观察，而 XR 版的 OmniParser（在渲染帧上运行的检测器和描述模型）是可以构建的。结构化的旁路在三维中甚至更丰富，因为引擎知道每个物体的名称、类型、位姿和可交互性（场景图，scene graph），而 visionOS 和 Android XR 也把它们的二维无障碍体系扩展到了空间应用。会失效的是：头显的视图是自我中心的（egocentric），随每一次头部运动而变化，因此一个 UI 状态会产生许多幅图像；画面中包含深度、立体、遮挡以及真实世界的透视画面（passthrough）；许多沉浸式应用渲染自定义的三维 UI，完全没有无障碍元数据，这正是 Screen Recognition 在 2021 年为 iOS 解决的那种情况。智能体的“屏幕”也变成了一个需要选择的问题：用户的视图、放在别处的虚拟相机，还是房间的地图。

## 3. 定位：从“Share 按钮”到屏幕位置

### 3.1 问题及其度量

**GUI 定位**（GUI grounding）把一个指代表达（referring expression，例如“打开分享菜单”这样的指令，或“左下角的 Share 图标”这样的描述）和一张截图映射为要操作的元素的位置。一个定位基准给出 $N$ 个三元组（截图、指令、目标框 $B_i$），模型输出一个点 $\hat p_i$，准确率就是落在各自框内的点所占的比例：

$$
\mathrm{Acc} = \frac{1}{N}\sum_{i=1}^{N} \mathbb{1}\big[\hat p_i \in B_i\big].
$$

输出一个点是很自然的，因为一次轻触或点击就是一个点。这个度量掩盖了一个重要的几何事实：一个略有偏差的点是否仍然算对，取决于目标的大小。如果预测误差在每个坐标轴上都近似服从标准差为 $\sigma$ 像素的高斯分布，而目标是一个以真实点为中心、半宽为 $a$、半高为 $b$ 的框，则命中概率为

$$
P(\text{hit}) = \operatorname{erf}\!\Big(\frac{a}{\sigma\sqrt2}\Big)\,\operatorname{erf}\!\Big(\frac{b}{\sigma\sqrt2}\Big).
$$

对于 44 x 44 px 的手机图标（$a = b = 22$），当 $\sigma = 8$ px 时该值为 0.99；对于 4K 专业应用中 12 px 的工具栏图标（$a = b = 6$），同样的误差只得到 0.30。同一个模型、同样的误差，得分却截然不同：这就是第 3.4 节中 ScreenSpot 与 ScreenSpot-Pro 之间的差距，第 4 节交互组件的定位模式可以让你亲手试一试。

### 3.2 输出位置的三种方式

1. **从列表中选择一个元素**（标记序号、元素 id、DOM 节点）。简单而精确，但上限取决于列表本身：它需要一棵树或一个解析器。
2. **以文本 token 写出坐标。** VLM 直接输出 `click(x=412, y=873)`。SeeClick（ACL 2024）在约 100 万个定位样本上对 Qwen-VL 进行持续预训练（continual pretraining），使其能做到这一点；UI-TARS 和大多数后来的模型沿用了这种做法，坐标是归一化值还是绝对像素取决于基座模型。它不需要解析器，但用数字写出的坐标只得到很弱的空间监督（对交叉熵损失而言，偏差一个像素的答案和偏差整整一个屏幕的答案同样“错误”），而且只给出一个脆弱的点，没有置信度。
3. **预测热力图。** GUI-Actor（NeurIPS 2025）增加一个 `<ACTOR>` token，以它在各视觉分块上的注意力作为输出：与目标框重叠的每个分块都受到监督，峰值就是点击位置，再由一个小型验证器（verifier）对候选区域排序。热力图的分散程度天然就是一个置信度信号。

### 3.5 先看，再放大：搜索与级联

ScreenSpot-Pro 的论文本身就提出了 **ScreenSeekeR**，一种免训练的流程：由一个规划模型提出目标应当所在的区域，定位器在该裁剪区域中搜索，搜索再递归进行。它无需任何训练即达到 48.1%，而最好的单次推理为 18.9%。其中的教训是**缩小搜索区域比换用更大的模型更有效**，这一点后来被吸收进模型，成为显式的放大步骤（GUI-ARP 的自适应区域感知；MAI-UI 的放大模式，73.5% 对单次推理的 67.9%；Qwen-UI-Agent 使用放大达到 81.5%），也被吸收进迭代细化方法（Chain-of-Ground，68.4%）。GroundCascade（2026 年 11 月）仅在第一个定位器的预测看起来不可靠时才询问第二个定位器，达到 85.33%。

“先看再放大”是头显中**注视点渲染**（foveated rendering）与注视（gaze）在二维中的对应物：把分辨率花在目标可能所在的地方。它也提醒我们，测试时计算（第 4.6 节）对感知和对规划同样有效。

### 3.6 把规划器与定位器分开

如果瓶颈在于定位，一种选择是让强大的通用模型负责规划，让专门的模型负责定位。SeeAct（ICML 2024）在真实网站上直接测量了这一瓶颈：当由人来完成定位（“神谕”，oracle）时，GPT-4V 完成了 51.1% 的任务，而使用最好的自动定位时只有 37.8%。Jedi 从另一个方向给出了证据：以 OpenAI 的 o3 作为规划器，当它的点击由 7B 的 Jedi 模型来定位时，OSWorld 成绩从 23% 升至 51%。Agent S2（2025）把这一思路推进为**定位器混合**（mixture of grounders，按目标选用视觉、文本和结构方面的专门定位器），Phi-Ground（2025）则系统地研究了此类专门定位器的训练。

**对三维而言。** 定位比其他任何部分都更容易迁移，在某些方面甚至变得更容易：最好的二维定位器已经输出热力图（GUI-Actor）或分两轮放大，这直接对应于穿过热力图峰值的**射线投射**（ray casting）以及注视引导的注视点渲染；而在二维中从 DOM 生成的合成定位数据，在三维中可以从引擎生成，引擎能从任意视点渲染任意物体，并给出精确的标签。会失效的是：输出不再是一个像素，而是一个物体或一个体积。一个像素可能对应不同深度上的多个物体；小的、远处的或侧对着的目标只投影成几个像素（即 ScreenSpot-Pro 问题，又因头显光学而加剧）；目标可能被遮挡或位于视场之外；指令常常相对于用户的身体（“我左边的面板”）。第 8.2 节会把这些说得更具体。

## 4. 规划、反思与记忆

### 4.1 先推理，后行动

几乎所有智能体都会在每个动作之前写一段简短的**思考**（thought），采用 ReAct 风格：“Wi-Fi 开关是关闭的；点它”，随后是 `tap(...)`。AitZ（2024）为 Android 回合标注了动作思维链（chain-of-action-thought：屏幕显示了什么、动作应当达成什么、实际发生了什么），UI-TARS 则在包含任务分解、反思和里程碑识别的“System-2”推理轨迹上训练其原生模型。推理有助于规划；但对纯定位而言它可能有害：GUI-G1（2025）发现长思维链会降低定位准确率，许多定位器直接用坐标作答。

### 4.2 动作空间

动作空间（action space）是一个影响巨大的设计决策。典型的移动端动作空间包括 `tap(x, y)`、`long_press(x, y)`、`swipe(start, end)`、`type(text)`、`back`、`home`、`wait`，外加三个不作用于设备的动作：`finish`、`infeasible`（任务在这里无法完成；MoTIF（ECCV 2022）把这一点变成了一个研究问题）和 `ask_user(question)`。桌面智能体还加入了鼠标移动、拖动、滚动、键盘快捷键和窗口管理。

设计杠杆图的 (a) 部分显示了这一选择有多重要：在没有任何其他改进的情况下，AppAgent 的成功率就从使用原始动作时的 2.2% 升到了使用基于编号元素的小型动作空间时的 48.9%。Agent S（ICLR 2025）把这一点推广为**智能体-计算机接口**（Agent-Computer Interface，ACI）：*为智能体*设计接口（一个受约束的、已定位的动作集合，并提供即时反馈），而不是强迫它去用为人设计的接口。

近来最强的系统**把 GUI 动作与程序化动作混合起来**。UFO2（2025）在存在原生应用 API 时调用 API，没有时退回到 GUI 点击；CoAct-1（2025）让一个编排器（orchestrator）在 GUI 操作员和编写脚本的程序员智能体之间做选择，在 OSWorld 上达到 60.76%；UI-TARS-2 和 Qwen-UI-Agent（2026）统一了 GUI、终端（CLI）和文件系统动作；MAI-UI 把模型上下文协议（Model Context Protocol，MCP）工具调用和显式的用户交互加入了动作空间。MobileWorld（2025）把询问用户和 MCP 工具变成了计分的任务类型。一项跨接口授权研究（2026）得出了安全方面的结论：授权应与动作的*效果*绑定，无论该动作是通过点击、命令行还是 API 发出的。

### 4.3 反思与验证

一次错误的轻触就可能把智能体带进错误的应用；好智能体与坏智能体的区别在于能否察觉。**Mobile-Agent-v2**（NeurIPS 2024）加入了一个反思智能体，比较每个动作前后的屏幕，把动作归类为正确、错误（页面不对：返回）或无效（什么都没变：换个做法）；配合一个维护任务进度摘要的规划智能体和一个记录关注内容的记忆单元，它把其基准上的成功率从 43.2%（v1）提高到了 75.0%。UI-TARS 使用**反思微调**（reflection tuning）：把在自身在线轨迹中发现的错误与相应的纠正配对，在纠正后的后续轨迹上训练模型，从而使恢复能力成为策略的一部分。

验证还可以用来在候选之间做选择。GTA1（ICLR 2026）采样多个计划，由一个评判器（judge）挑出其中之一。**Agent S3**（2025；TMLR 2026）用 *Behavior Best-of-N* 把这一做法扩展到整个回合：运行若干完整的 rollout，把每个 rollout 转换成一段简短的“行为叙述”（behaviour narrative），描述屏幕上发生了什么变化，再由评判器比较这些叙述。这在 OSWorld 上取得了 72.6%，是首个公开发表的超过 72.36% 人类基线的结果（2025 年 12 月）。

负面结果同样重要：OSWorld 2.0（2026 年 6 月）的失败分析指出，智能体仍然会“忘记约束、错过任务中途到达的信息、在该询问用户时去猜测，以及跳过验证”。

### 4.4 记忆与探索

智能体需要两种记忆。**在任务之内**，它们必须跟踪进度，并记住在一个屏幕上读到、在另一个屏幕上需要的信息（Mobile-Agent-v2 的记忆单元，Mobile-Agent-v3 的记录员）。**跨任务**时，它们可以积累关于应用的知识：

- **探索文档。** AppAgent 先让智能体探索一个应用（或观看人的操作），然后写一份文档描述每个元素的作用。使用自主探索得到的文档时，其成功率从 48.9% 升至 73.3%，使用基于演示的文档时为 84.4%，使用手工文档时为 95.6%（设计杠杆图，(a) 部分）。
- **UI 转移图。** AutoDroid（MobiCom 2024）在离线状态下不借助 LLM 探索应用，构建一张“哪个动作通向哪个屏幕”的图，并在运行时把它转换为提示中的线索：在其 DroidTask 基准上，使用 GPT-4 达到 71.3% 的任务成功率，查询成本降低 51.7%。
- **可复用技能。** MobileGPT 存储子任务；Agent Workflow Memory（ICML 2025）从过去的回合中归纳出可复用的工作流（在 Mind2Web 和 WebArena 上分别相对提升 +24.6% 和 +51.1%）；Mobile-Agent-E（2025）在每个任务之后写下“Tips”和“Shortcuts”（在 Mobile-Eval-E 上绝对提升 +22%）；AppAgentX 把重复出现的动作链压缩成新的高层动作。Agent S4（2026 年 10 月）走得最远：一个元智能体（meta-agent）不断演化智能体自己的工具、脚本和使用知识，用一个 27B 的开源模型在 OSWorld V2 上达到 21.3%（是同一模型使用固定接口时的 3.8 倍）。

### 4.5 多智能体设计

有些系统把工作分给多个角色智能体。Mobile-Agent-v2 使用规划、决策和反思智能体；Mobile-Agent-E 加入了管理者和感知者；Mobile-Agent-v3 把 GUI-Owl 模型包装成管理者、执行者、反思者和记录员等角色。在桌面上，UFO 的 HostAgent 分解任务并分派给各个应用的 AppAgent；Agent S2 把一个通用规划器与多个专门定位器结合起来；Magentic-One 的编排器维护任务账本和进度账本，指挥一个网页浏览者、一个文件浏览者、一个程序员和一个终端。UFO3（2025）在 Windows、Linux 和 Android 设备之间编排智能体。Minitap 的五角色系统（规划、子目标跟踪、状态捕获、决策、执行）报告在 AndroidWorld 上 pass@3 达到 100%，而去掉任务分解会让它损失 26.1 个百分点。

角色的代价是延迟：每个角色都意味着一次额外的模型调用，OSWorld-Human（2025）发现，规划、反思和评判调用占据了智能体耗时的大部分。

### 4.6 测试时扩展与前瞻

当环境可以重置时，智能体可以尝试多种做法并保留最好的那个：Best-of-N rollout（Agent S3）、带评判器的采样计划（GTA1），或在网页状态上做最佳优先的**树搜索**（tree search；Koh 等，2024；在 VisualWebArena 上达到 26.4%）。当环境无法重置时，**世界模型**（world model）可以想象候选动作的结果：WebDreamer 让 LLM 模拟每个候选点击会显示什么，并对这些预测打分，在真实网站上的效率是树搜索的 4-5 倍（第 5.5 节）。

## 5. 训练 GUI 智能体

到 2026 年，大多数强大的智能体都遵循一个四阶段的配方：收集或合成数据；在定位和轨迹数据上进行监督微调（supervised fine-tuning，SFT）；用基于规则的奖励对定位进行强化学习；在大量并行环境中进行在线多轮强化学习。世界模型出现在其中的多个环节。下图描绘了这些阶段。

### 5.1 数据

**人类演示**最先出现。AITW（NeurIPS 2023）收集了 30,378 条指令下的 715,142 个 Android 回合；AndroidControl（NeurIPS 2024）收集了覆盖 833 个应用的 15,283 条演示，同时带有高层指令和步骤级指令，并给出了一个发人深省的结果：域内性能随数据量增长，但在未见过的应用上，性能增长要慢得多。OpenCUA（2025）发布了 AgentNet，即覆盖三个操作系统和 200 多个应用的桌面演示数据，并附带了其标注工具。

演示的代价很高，因此如今大多数数据都是**合成**的：

- **来自教程。** Synatra 把间接知识（操作指南类文章）转换为约 100K 条演示，每条约 0.031 美元；AgentTrek 用 VLM 智能体重放网页教程，每条轨迹约 0.55 美元；TongUI 从多模态教程构建了 143K 条轨迹；Explorer 以每条约 0.28 美元的成本生成了 94K 条；Fara-7B 的 FaraGen 流水线以每条约 1 美元的成本产出经过验证的轨迹。
- **来自探索。** OS-Genesis（ACL 2025）颠倒了通常的顺序。它不是先写任务再尝试执行，而是先探索（基于规则的点击、输入、滚动），然后让 GPT-4o 把观察到的每次状态转移描述为一条低层指令，并把这些指令组合成高层任务（“反向任务合成”，reverse task synthesis），再重新执行这些任务，并用奖励模型过滤轨迹。用大约一千条这样的轨迹，Qwen2-VL-7B 在 AndroidWorld 上达到 17.41%，而“任务优先”的合成方法只有 6.25%。
- **从结构生成定位标签。** UGround 渲染网页，并利用其 DOM 标注了约 1000 万个元素；OS-Atlas 在五个平台上构建了 1358 万个；Jedi 把界面分解为控件类型，合成了 400 万个样本。对三维而言，这是最重要的一条数据路径，因为在三维中，引擎扮演着 DOM 的角色。

### 5.2 监督微调

常见的 SFT 配方是**先训练定位，再训练行动**。Aguvis（ICML 2025）把这两个阶段明确分开：先在单步的（指令、截图、点）数据上进行定位阶段的训练，再在带有内心独白（inner monologue）的多步轨迹上进行规划与推理阶段的训练。UI-TARS 加入了大规模感知数据集（元素描述、稠密的屏幕描述、状态转移）、统一的跨平台动作空间、推理轨迹以及反思微调。SFT 得到的是一个能力不错但很脆弱的策略：它模仿数据中的路径，却从未经历过自己的错误。

### 5.3 基于规则奖励的强化学习

2025 年初，来自推理模型的“R1”配方（群体相对策略优化，Group Relative Policy Optimization，GRPO，配合可验证奖励）进入了 GUI 领域，最先用于定位和单步动作。对一个训练样本，模型采样 $G$ 个答案 $o_1, \dots, o_G$，每个答案得到奖励 $r_i$。GRPO 不需要价值网络：每个答案的优势（advantage）就是其奖励在组内标准化后的值，

$$
A_i = \frac{r_i - \operatorname{mean}(r_1, \dots, r_G)}{\operatorname{std}(r_1, \dots, r_G)},
$$

策略被推向优势为正的答案（与 PPO 一样，使用截断的概率比和相对参考模型的 KL 惩罚）。对定位而言，奖励是一条规则，而不是一个学习得到的模型：

$$
r = r_{\text{format}} + \mathbb{1}\big[\hat p \in B\big] \quad\text{or}\quad r = r_{\text{format}} + \mathrm{IoU}(\hat B, B).
$$

由于奖励精确且免费，几千个样本就足够了。UI-R1（2025 年 3 月）用 136 个任务把一个 3B 模型在 ScreenSpot 上提升了 22.1 个百分点，在 ScreenSpot-Pro 上提升了 6.0 个百分点；GUI-R1 用约 3K 个样本超过了 OS-Atlas；SE-GUI 用 3K 个样本在 ScreenSpot-Pro 上达到 47.3%（7B）。有两项改进针对 0/1 点奖励的明显问题。GUI-G1 发现，当模型预测框时会出现**奖励投机**（reward hacking：预测巨大的框能廉价地提高 IoU 类奖励），于是加入了框大小的约束。GUI-G² 用**高斯奖励**（Gaussian reward）取代二值命中：这是一种平滑的分数，在元素中心最高，并随元素大小向外扩展，从而让“差一点就对”比“差得很远”得到更多奖励。

### 5.4 在线多轮强化学习

单步奖励教不会恢复能力和长程规划。为此，智能体必须在真实环境中行动，并在回合结束时得到奖励。**DigiRL**（NeurIPS 2024）首次在真实 Android 应用上给出了令人信服的演示：先在已有数据上做离线强化学习，再在并行模拟器中继续在线训练，采用优势加权更新、自动课程（curriculum）以及一个判断是否成功的 VLM。一个 1.3B 模型在 AitW 任务上从 17.7% 提升到 67.2%，超过了 CogAgent（38.5%）和过滤行为克隆（filtered behaviour cloning，57.8%）。**WebRL**（ICLR 2025）从智能体的失败中生成新任务，并训练了一个结果奖励模型（outcome reward model），把 Llama-3.1-8B 在 WebArena-Lite 上的成绩从 4.8% 提升到 42.4%。

在 2025-2026 年，这变成了一场基础设施竞赛：

| UI-TARS-2（2025 年 9 月） | 数千台虚拟机；GUI + 终端 + 文件系统沙盒 | 带稳定性修正的多轮 PPO，数据飞轮 |

### 5.5 GUI 世界模型

**世界模型**在给定当前观察和一个动作时预测下一个观察。对 GUI 而言，它有三种用途：行动前的前瞻、供强化学习使用的想象环境，以及数据合成。各方法使用的表示不同：

- **文本。** WMA（ICLR 2025）预测动作之后*发生了什么变化*的自然语言描述，并用它在 WebArena 和 Mind2Web 上选择动作，而无需训练策略；WebDreamer 让 LLM 自己想象每个候选动作的结果。
- **代码。** Code2World（2026）把下一个屏幕预测为可渲染的 HTML，从而保持文字和布局的精确；接入 Gemini-2.5-Flash 后，在 AndroidWorld 上提升 9.5%。Generative Visual Code Mobile World Models（ICML 2026）在移动端做了同样的事。
- **像素。** ViMo 生成带文本占位符的下一张截图；NeuralOS（ICLR 2026）用一个循环状态跟踪器和一个扩散渲染器模拟整个桌面。
- **用于训练。** DynaWeb 和 WM-R1（2026）在想象的 rollout 中训练策略，WebWorld 把网页模拟器扩展到超过 100 万次交互。

这些是[世界模型系列]({{ '/blog/2026/world-models-01-what-is-a-world-model/' | relative_url }})中讨论的视频与三维世界模型在 GUI 领域的对应物。

**对三维而言。** 这套配方可以迁移，其中一部分还会变得更容易。射线-碰撞体检测（ray-collider test）是精确且免费的定位奖励，因此面向空间目标的 R1 式定位强化学习可以从引擎数据启动，无需人工标注；反向任务合成与引擎非常契合，因为随机探索产生的状态转移可以由 VLM 描述成任务；而预测场景描述的增量（USD 或 glTF 变换的变化）正是 Code2World 的 HTML 在三维中的类比。会失效的是：完全没有 XR 轨迹语料库（没有 AITW，也没有 AndroidControl）；XR 模拟器的每个实例都需要一块 GPU，这让 20,000 个并行环境变得十分昂贵；而泛化研究警告说，强化学习的收益未必能延续到未见过的 XR 应用上，因为 XR 应用之间共享的控件惯例远少于手机应用。

## 6. 评测与最新水平

### 6.1 离线、在线与实时评测

早期的数据集采用**离线**评测：在每一步，智能体的动作是否与记录下来的人类动作一致？AITW 规定，若一次轻触落在屏幕距离的 14% 以内，或落在（放大后的）元素框内，就算正确。离线步骤准确率便宜且可复现，但具有误导性：任何合理的替代路径都会被算作错误，而且高步骤准确率并不意味着整个任务能够成功。**在线、基于执行**（execution-based）的基准在真实环境中运行智能体，并用程序检查最终状态。**实时网页**（live-web）基准在真实网站上运行，并使用评判器，因为网页无法重置。

OSWorld 曲线是对这一领域最清晰的概括：发布时为 12.24%（2024 年 4 月），启用计算机使用功能的 Claude 3.5 Sonnet 为 14.9%（2024 年 10 月；步数更多时为 22.0%），OpenAI 的 CUA 为 38.1%（2025 年 1 月），Claude Sonnet 4.5 在 OSWorld-Verified 上为 61.4%（2025 年 9 月），Agent S3 为 72.6%（2025 年 12 月），GPT-5.4 为 75.0%（2026 年 3 月），GPT-5.5 为 78.7%（2026 年 4 月）；到 2026 年年中，工业模型约为 80%，二手来源报告 Claude Opus 4.8 达到 83.4%。两年间大约提高了 6.5 倍。随后，长程的 OSWorld 2.0 又把尺度重置到约 20%。

为什么更长的任务会如此急剧地崩溃？一个粗略的估算有助于理解。若每一步以概率 $q$ 独立成功，而任务需要 $n$ 步，则任务成功的概率为 $q^n$。当 $q = 0.99$ 时，一个 30 步的任务（OSWorld 1.0 的量级）有 74% 的时候能成功；一个 318 步的任务（OSWorld 2.0 中工具调用的平均次数）只有 4% 的时候能成功。真实的智能体能从一部分错误中恢复，所以这个估算偏悲观，但它解释了为什么决定长任务成败的是验证和恢复，而不是单步准确率。

### 6.4 这些数字有多可信

二维领域吃了不少苦头，才学到几条关于评测的教训：

1. **离线评测会高估。** Online-Mind2Web 的论文“An Illusion of Progress?”（COLM 2025）发现，许多在早期基准上看起来很强的网页智能体，在真实任务上并没有超过 2024 年的 SeeAct 基线。
2. **评估器也有 bug。** OSWorld-Verified（2025 年 7 月）修复了 300 多个问题，大多在评估脚本中；修复前后的分数不能直接比较。评测框架、步数上限和思考预算都会让分数变动好几个百分点。
3. **自报与饱和。** AndroidWorld 排行榜列出了若干自报 100% 的条目，并把该基准标记为已饱和；ScreenSpot、ScreenSpot-v2 和 WebVoyager 也都已饱和。
4. **可靠性不等于能力。** 若单次尝试的成功概率为 $p$，则 $k$ 次尝试中至少一次成功的概率为 $\text{pass@}k = 1-(1-p)^k$，而 $k$ 次全部成功的概率为 $\text{pass}^k = p^k$。当 $p = 0.9$、$k = 3$ 时，二者分别为 0.999 和 0.729。用户需要的是后者。Minitap 在 AndroidWorld 上同时报告了两者：pass@3 为 100%，pass^3 为 94.0%。
5. **效率。** OSWorld-Human（2025）发现，最好的智能体所用的步数是必要步数的 2.7 到 4.3 倍，后期步骤的耗时可达早期步骤的三倍，而任务耗时长达数十分钟。
6. **评判器有噪声。** WebVoyager 的 GPT-4V 评判器和 Online-Mind2Web 的 WebJudge 与人的一致率约为 85%。

**对三维而言。** 基准的设计可以迁移：可重置的环境、带程序化检查的参数化任务（AndroidWorld）、留出的应用（held-out apps）、可靠性（pass^k）与效率指标，以及经过人工验证的评判器。会失效的是：可重置的虚拟机变成了 XR 模拟器或引擎构建版本，它们必须在 GPU 上以无头（headless）方式并行运行；成功检查需要空间容差（放置误差在 5 cm 以内、朝向用户）；只看一帧渲染画面的评判器看不到被遮挡的结果；在真实设备上测试会牵涉人的身体和房间。二维基准文献中唯一与 XR 有关的材料是 GUI-World 中 393 段 VR、AR 和 MR 界面的屏幕录像，以视频问答的形式评测（GPT-4o 在多项选择上为 84.3%）。在二维文献中，没有出现任何让智能体操作 XR 界面的交互式基准；[第 4 篇]({{ '/blog/2026/3d-gui-agent-04-agents-in-xr-and-the-gap/' | relative_url }})考察 XR 一侧已有的工作。

## 7. 人在回路、无障碍、安全与隐私

### 7.1 委托、监督与询问

代表人行动的智能体必须决定何时让人参与进来。**Morae**（UIST 2025）针对盲人和低视力（blind and low-vision，BLV）用户研究了这个问题，对这些用户而言，智能体默默做出的选择是不可见的：在一项形成性研究中，智能体对 576 个可行请求中的 484 个报告“已完成”，但其中只有 189 个是正确的，有 182 个失败涉及歧义（哪个航班、哪个尺码）。Morae 检测决策点、暂停，并生成一个无障碍的选择界面。在需要暂停的任务上，它的成功率为 65.6%，而 OpenAI 的 Operator 为 50.8%；在一项有 10 名 BLV 参与者的研究中，用户借助它完成了更多任务，代价是运行更慢。

多久询问一次是一个调度问题。“When Should Users Check?”（CHI 2026）对多步任务中的确认频率建模；在 48 名参与者中，81% 更喜欢中间确认，而不是只在最后确认，按计划安排的确认使任务时间缩短了 13.54%。2026 年的其他工作比较了实时会话中的监督策略（48 名参与者，192 个会话），预测真实用户何时会介入（CowCorpus），并为智能体运行期间短暂的“微等待”（micro-wait）做设计。一项针对 Operator 和 Manus 的可用性研究（CAIS 2026）发现，行业的愿景与用户实际能完成的事情之间存在很大差距。

并非每个用户都希望智能体代劳。面向读屏软件用户的情境感知*引导*（CHI 2026）帮助人们自己操作软件，而“Beyond Chat and Clicks”（2026）让智能体改造用户周围的实时界面，而不是替用户一路点击。这些“引导我”和“重塑 UI”的模式，是完全自主之外的另一种选择。

### 7.2 无障碍

GUI 智能体常被宣传为一种无障碍技术，但它们自身的无障碍性很差，而且颇能说明问题。A11y-CUA 数据集（CHI 2026）发现，一个在 78.3% 的任务上成功的计算机使用智能体，在限制为仅用键盘交互时降到 41.67%，使用屏幕放大镜时降到 28.3%，而这些正是许多残障用户所依赖的设置。在来自八名盲人用户的 1,258 条真实桌面命令上，GPT-5 的成功率为 52.5%（EMNLP 2026）。ElderBench（2026）收集了 249 个从老年人那里征集来的任务。

### 7.3 安全：屏幕上的一切都是输入

GUI 智能体会读取屏幕上显示的任何内容，因此**每个像素都是一个输入通道**，包括攻击者写入的内容。这些攻击十分有效：

- **弹窗。** 在 OSWorld 和 VisualWebArena 上，对抗性弹窗的攻击成功率达到 86%，并使任务成功率降低 47%；告诉智能体忽略弹窗也无济于事（ACL 2025）。
- **注入的页面内容。** EIA 在多达 70% 的情况下窃取特定的个人数据（ICLR 2025）；扰动网页中不到 5% 的像素就能在多达 67% 的情况下劫持智能体（ICLR 2025）。
- **视觉提示注入**（visual prompt injection）。VPI-Bench 对计算机使用智能体的攻击成功率最高达 51%，对浏览器智能体达 100%（ICLR 2026）；RedTeamCUA 把网页注入瞄准操作系统层面的动作，发现能力更强的智能体可能更容易被利用（ICLR 2026）；StepJack 把一次注入分散到多个步骤中，把攻击成功率从 41.7% 提高到 72.9%（2026）。
- **自适应攻击。** 面对 21 种防御配置，自适应视觉注入的成功率仍约为 92%（2026 年 11 月）。

危害基准衡量的是另一面：OS-Harm（NeurIPS 2025）在 150 个 OSWorld 任务上测试滥用、注入和不当行为；MobileSafetyBench 在 Android 上做同样的事；SEAM（2026）把有害任务拆分到多个屏幕上，发现智能体会完成其中多达 92% 的任务。

已上线的防御是分层的，而不是完美的。OpenAI 的 Operator 系统卡（system card）报告：在 607 个任务上确认召回率为 92%，提示注入监测器的召回率为 99%、精确率为 90%，采取缓解措施后对注入的易感性为 23%，不采取时为 62%。Google 的 Gemini Computer Use 为每个拟执行的动作附上一个安全决策（允许、需要确认、阻止）。Anthropic 建议使用最小权限的虚拟机，并对有重要后果的动作进行确认。Microsoft 的 Windows 智能体工作区和 UFO2 的画中画桌面把智能体与用户的会话隔离开来。

### 7.4 隐私

截图包含屏幕上的一切。PriMobiBench（ACM CCS 2026）发现，VLM 驱动的移动智能体在多达 82.5% 的情况下能提取屏幕上的敏感数据，并在约 70% 的情况下推断出用户画像；遮蔽界面中与任务无关的部分可以把画像推断减少多达 58%，代价是约 8% 的任务性能。

**对三维而言。** 遇到歧义时暂停、按计划确认、对有重要后果的动作进行确认、在涉及凭据时由用户接管，以及“引导而非代劳”的模式，这些都可以迁移；而空间指代（“把它放到那边”）会让歧义比在二维中更频繁。会失效的是：确认和接管必须在没有鼠标和键盘的情况下进行，而且不能破坏临场感（presence）；在用户空间中移动内容的智能体可能吓到用户，或者移走用户正伸手去拿的东西；透视画面会把不受控制的真实世界文字（海报、屏幕、标牌）带进智能体的输入，扩大了二维防御本就未能封堵的注入面；头显的摄像头、眼动追踪和房间扫描远比截图敏感。

## 8. 从二维到三维：哪些能迁移，哪些会失效

本节把各处“对三维而言”的要点汇集成一个完整的论证。问题不在于二维智能体的思想在 XR 中是否有用（显然有用），而在于二维智能体的哪些假设会失效，因为正是这些失效定义了三维 GUI 智能体的研究问题。

| 维度 | 二维最新水平（2026 年 11 月） | 可迁移到三维的 | 在三维中失效的 |
| --- | --- | --- | --- |
| 观察 | 仅用截图的原生模型；树作为额外信号 | 渲染视图作为主要输入；场景图作为更丰富的树；锚定在物体上的标记 | 自我中心、不断变化的视点；深度、立体、遮挡、透视画面；很少有无障碍树 |
| 定位 | 点在框内；ScreenSpot-Pro 单次推理 74%，级联 85% | 热力图变成射线；放大变成注视点渲染；引擎生成的标签；精确的射线命中奖励 | 目标是物体或体积；一个像素对应多个物体；细小的远处目标；相对于身体的指代 |
| 动作空间 | 轻触、输入、滑动、按键；GUI + API + MCP 混合 | 精心设计的小型动作集；优先使用意图和 API | 6-DoF 位姿、射线、捏合、抓取、双手、注视、语音、移动（locomotion）；用容差代替命中 |
| 视场 | 一切都在一块屏幕上（其余部分靠滚动） | 主动感知、探索记忆 | 目标在用户身后、被遮挡或在另一个房间；需要空间记忆 |
| 延迟 | 每步 2.5-4 s；任务耗时数十分钟 | 量化、批处理、小模型、端云分工 | 用户在界面之内等待；每帧 11-14 ms 的渲染预算与之共享同一设备 |
| 训练 | SFT、规则奖励强化学习、在 10k+ 台虚拟机中的在线强化学习 | 整套配方；免费的空间奖励；反向任务合成 | 没有轨迹语料库；重度依赖 GPU 的模拟器；向未见应用的迁移更弱 |
| 评测 | 执行检查、参数化、pass^k | 设计原则 | 大规模无头 XR 运行时；空间容差；被遮挡的结果 |
| 人与安全 | 确认、暂停、接管、隔离 | 这些模式 | 接管用户的双手和视野；物理上的惊吓；透视画面注入；房间与注视隐私 |

### 8.1 观察

二维智能体的观察是一张截图，用户和智能体看到的是同一张。在头显中有多个候选观察，而且尚无共识：用户看到的立体帧、单目渲染、深度、引擎的场景图、平台为空间应用提供的无障碍信息、用户的头部、手部和注视位姿，或者从智能体自选视点渲染的“智能体视图”。二维的经验（用像素保证覆盖面，有结构时就利用结构）提示应采用混合方案，但视点问题是新的：用户每移动一次，同一个 UI 状态就会产生一幅不同的图像。

### 8.2 带深度的定位

下图用一次真实的可见性计算对比两种设定。

{% include blog_figure.liquid path="assets/img/blog/3d-gui-agent/02-2d-vs-3d.svg" localized="true" caption="左：在二维屏幕上，每个目标都可见，一个点对应一个元素。右：用户周围的四块面板，用户的视锥（64 x 50 度）朝向前方，场景中还有一个虚拟盒子。百分比表示每块面板上 400 个点中位于视锥内且未被盒子遮挡的比例，通过从用户头部出发的射线投射计算：前方的面板 A 完全可见，面板 B 在视野内但有 87% 被盒子遮挡，右侧的 C 和用户身后的 D 都在视场之外。红线是选中 A 上一点的手部射线。" %}

二维定位器输出一个像素。三维定位器必须输出一个目标物体（或其上的一点），而从二维模型出发，到达那里的自然方式是**投射一条射线**。如果模型在一个内参为 $K$、相机旋转为 $R$、位置为 $\mathbf c$ 的视图中预测出像素 $(u, v)$，则射线为

$$
\mathbf x(t) = \mathbf c + t\,\frac{R K^{-1} [u, v, 1]^\top}{\lVert R K^{-1} [u, v, 1]^\top \rVert}, \qquad t > 0,
$$

目标就是它命中的第一个碰撞体（collider）。像素误差会变成约 $\delta/f$ 弧度的角度误差（$f$ 为以像素计的焦距），在距离 $z$ 处则变成约 $z\,\delta/f$ 的横向误差：对于宽 1920 像素、水平视场 90° 的视图，$f = 960$ px，因此在 2 m 处，10 px 的误差约为 2 cm，足以错过远处面板上的一个小按钮。在这里，热力图输出（GUI-Actor）比单点更好，因为它的分散程度可以转换成一个射线锥，并与候选物体的大小进行比较。遮挡带来了一种二维定位从未有过的失败：射线可能先命中更近的物体（图中的面板 B），而正确的动作可能是先移动头部或先移开面板。

### 8.3 动作空间

二维动作是作用在二维点上的少数几种离散类型。XR 输入包括射线加捏合的选择、直接触摸、带完整 6-DoF 位姿的抓取与放置（一个旋转加一个平移，即 $SE(3)$ 中的一个元素）、旋转与缩放、双手手势、注视加捏合、注视停留（gaze dwell）、语音、手柄按键，以及移动或瞬移（teleportation）。其中许多操作没有对应的“点击”，其成功与否要用容差来判定（对齐误差在几度以内、放置误差在几厘米以内）。语言模型不擅长直接生成这样的序列：在 ComboBench（2025）上，最好的模型只有 11.7% 的时候能把 VR 游戏中的动作准确映射为手柄和头显的操作序列。二维给出的答案，即一个精心设计的小型动作空间，并在可能时使用 API（AppAgent、Agent S 的 ACI、UFO2），很可能是正确的起点，再在语言模型之下配上确定性的底层控制器，正如 ClawMobile（2026）针对手机所主张的那样。

### 8.4 视野之外的目标

二维智能体通过滚动、切换标签页和打开菜单来处理隐藏的内容，记忆则帮助它记住看到过的东西。在 XR 中，窗口可能在用户身后，可能被真实或虚拟物体遮挡，也可能在另一个房间里，而且用户还会移动。智能体需要决定往哪里看（或请用户转身），还需要一个关于窗口和物体位置的**持久空间记忆**（persistent spatial memory），它是一个带锚点（anchor）的场景图，而不是一串屏幕。空间记忆是当前多模态模型的已知弱点：在 VSI-Bench（2024）上，针对室内视频的空间问题，最好的模型得分为 45.4%，而人类约为 79%。

### 8.5 延迟

{% include blog_figure.liquid path="assets/img/blog/3d-gui-agent/02-latency.svg" localized="true" caption="每次决策的耗时，对数坐标。90 Hz 下的一个 XR 帧持续 11 ms。Lumine 游戏智能体（2025）在 114 ms 内发出第一个动作，带推理时为 234 ms。一个二维 GUI 智能体步骤耗时 2.5-4.0 s（UI-TARS-2，量化与全精度）。已发表的 XR 研究原型每轮约需 4 s（DuoZone 窗口布局）、9.1 s（SIAgent 意图智能体）和 49 s（NavAI VR 导航）。绿色条与橙色条之间的差距，就是三维 GUI 智能体的延迟问题。" %}

在桌面上，一个每步三秒、每个任务二十分钟的智能体可以在后台运行，用户则去做别的事。在头显中，用户就在界面*之内*看着。图中把这些数字并排列出：二维智能体的单步耗时比实时三维游戏智能体高出两个数量级，而首批 XR 原型还要更慢。二维的工具箱（量化：它把 UI-TARS-2 每轮的延迟从 4.0 s 降到 2.5 s，代价是 OSWorld 上 3.1 个百分点；UFO2 中的推测式多动作规划；批量动作；Ferret-UI Lite 和 Fara-7B 等端侧小模型；MAI-UI 的端云路由）全都适用，但头显在同一块芯片上还有每帧 8-14 ms 的硬性渲染预算，而且 VideoGameBench（2025）表明，在游戏会暂停等待时表现良好的智能体，在实时条件下表现要差得多，而 XR 是无法暂停的。分摊工作的设计（头显负责感知和渲染，手机或云端负责规划），以及在智能体思考期间*引导*用户的设计，很可能是必需的。

### 8.6 数据与评测

二维领域是建立在数据之上的：Rico、AITW、AndroidControl、Mind2Web，以及数百万条合成定位标签。对 XR 而言，没有从指令到动作的轨迹语料库，最大的公开 VR UI 元素数据集约有 17.7K 帧（DISCOVR，UIST 2025），也不存在要求智能体操作 XR 应用来完成任务的交互式基准。构建这样的基准，意味着要在三维中解决第 6.4 节的那些问题：无头、可重置的 XR 运行时，带空间容差的成功检查，留出的应用，以及可靠性指标。[第 4 篇]({{ '/blog/2026/3d-gui-agent-04-agents-in-xr-and-the-gap/' | relative_url }})回顾了能够承载这类基准的平台与工具，[第 3 篇]({{ '/blog/2026/3d-gui-agent-03-why-3d-interfaces-are-hard/' | relative_url }})则从人的角度解释，哪些三维交互难到值得交给智能体去做。

### 8.7 这对本专栏意味着什么

有三个结论将延续到[研究愿景]({{ '/blog/2026/3d-gui-agent-01-research-vision/' | relative_url }})和研究计划之中：

1. **智能体技术栈的大部分可以复用。** 截图优先的原生模型、规划器/定位器分离、反思、探索记忆、混合动作空间、先 SFT 后强化学习的配方以及基于执行的评测，都已成熟且开放（UI-TARS、GUI-Owl、OpenCUA、MAI-UI 的权重与代码）。
2. **新问题是空间性的。** 依赖视点的观察、带深度与遮挡的定位、需要空间记忆的视野外目标、连续的 6-DoF 动作空间，以及发生在界面之内的延迟，在二维中都没有能解决它们的对应方案。
3. **缺失的是基础设施。** 一个轨迹数据集、一个面向空间目标的定位基准，以及一个面向 XR 应用、基于执行检查的交互式基准，将扮演 Rico、ScreenSpot 和 OSWorld 在二维中扮演过的角色。

## 小结

- GUI 智能体通过观察、规划、定位、执行、验证和记忆的循环，把一条指令转化为在人所用的同一界面上的动作；原生模型如今在一个 VLM 中完成前四步。
- 截图胜过无障碍树，成为主要的观察方式，因为截图覆盖每个应用，而且定位数据可以从结构中合成；树仍是有用的额外信号。
- 定位是 2024 年的瓶颈。合成数据、热力图输出头、规则奖励强化学习以及放大/级联推理，把 ScreenSpot-Pro 从 18.9%（2025 年 4 月）提升到单次推理 74%、级联 85%（2026 年 11 月）。
- 在模型固定的条件下，动作空间设计、探索文档、反思和 best-of-N 选择都能把成功率各自提升数十个百分点。
- 训练流程是：先在人类轨迹和合成轨迹上做 SFT，再用规则奖励做 GRPO，然后在数千到数万个环境中做在线多轮强化学习；在未见过的应用上，收益会缩小。
- OSWorld 在 2025 年 12 月超过了人类基线，前沿模型已原生提供计算机使用能力；长程的 OSWorld 2.0（最佳 20.6%）显示了尚待解决的问题：跟踪约束、询问、验证。
- 每个像素都是攻击面；自适应注入能击败现有的防御，产品依靠确认、监控和隔离。
- 对三维而言，技术栈可以迁移，但观察、定位、动作、视场、延迟、数据和评测各自以特定的方式失效，这些失效定义了本专栏的研究议程。

## 练习

1. **定位误差与目标大小。** 利用第 3.1 节的公式，计算 44 x 44 px 的按钮和 12 x 12 px 的图标在 $\sigma = 4$、8 和 15 px 时的命中概率。然后估计模型在 12 px 目标上得分为 50% 时的 $\sigma$。这说明放大 2 倍有什么价值？

   <details markdown="1"><summary>提示</summary>

   对 44 px 的按钮（$a = b = 22$）：约为 1.00、0.99 和 0.74。对 12 px 的图标（$a = b = 6$）：0.75、0.30 和 0.09。50% 的命中率需要 $\operatorname{erf}(6/(\sigma\sqrt2)) = 0.707$，即 $6/(\sigma\sqrt2) \approx 0.74$，所以 $\sigma \approx 5.7$ px。放大 2 倍会使目标的像素尺寸翻倍，而模型以像素计的误差大致不变，因此 12 px 的目标表现得就像 24 px 的目标，这就是 ScreenSeekeR 和放大模式收益如此之大的原因。你可以在交互组件的定位模式中验证这些数字。
   </details>

2. **选择观察方式。** 你要为一家医院内部使用的 Windows 应用构建智能体，该应用的自绘控件不暴露任何 UI Automation 名称。列出第 2 节中的各种观察选项，说明你会采用哪一种及其原因，并说明你会首先收集什么数据。

   <details markdown="1"><summary>提示</summary>

   没有名称，树最多只能提供边界框，因此语义必须由截图来承载；以解析器（OmniParser 式）或原生截图模型作为主要输入，再把现有的任何结构作为额外信号。先收集一个小型定位数据集（该应用常用操作的截图，并标注目标框），就能在构建其他任何东西之前，先测量最可能成为瓶颈的定位准确率。
   </details>

3. **可靠性算术。** 一个智能体每次尝试完成某任务的成功概率为 0.85。计算 pass@3 和 pass^3。然后假设任务需要 40 步，每一步的成功概率为 $q$；在没有恢复的情况下，$q$ 为多少时任务成功率为 85%？这说明应该把投入放在哪里：更好的单步，还是恢复能力？

   <details markdown="1"><summary>提示</summary>

   pass@3 $= 1 - 0.15^3 = 0.997$；pass^3 $= 0.85^3 = 0.614$。由 $q^{40} = 0.85$ 得 $q = 0.85^{1/40} \approx 0.9959$，即每 240 步中失败不到一次。把单步准确率推到这么高很难；检测并撤销失败的步骤（反思，第 4.3 节）可以放宽这一要求，因为每一步只需要*最终*正确即可。
   </details>

4. **三维定位的奖励。** 为这样一个模型设计 GRPO 奖励：给定一幅渲染的 XR 视图和一条指令，它输出一个像素，从该像素投射射线。使用引擎的碰撞体。你会如何处理被遮挡的目标和细小的远处目标？这个奖励可能被怎样投机利用？

   <details markdown="1"><summary>提示</summary>

   一个自然的奖励是：若射线命中的第一个碰撞体属于目标则得 1，再加上一个平滑项（类似 GUI-G² 的高斯奖励），它基于射线与目标中心之间的角距离，并按目标的角尺寸缩放，使细小的远处目标不至于毫无希望。对于被遮挡的目标，要先决定正确的输出是遮挡物（以便移开它）、一个“改变视点”的动作，还是穿过遮挡物的目标本身；然后奖励你想要的那种选择。投机方式：把射线瞄准包含目标碰撞体的大物体（例如瞄准整个窗口而不是按钮），因此应使用最小的可交互碰撞体。
   </details>

5. **动手：交互组件。** 在照片回合中，于第 3 步（工具栏）切换到定位模式，找出使放在 Share 图标中心的点命中 Share 的概率低于 90% 的最小 $\sigma$。然后对 Settings 屏幕中的 Wi-Fi 行做同样的事。用第 3.1 节的公式解释两者的差别。

   <details markdown="1"><summary>提示</summary>

   Share 图标的触摸框为 44 x 44 px，因此当 $\sigma \approx 11$ px 左右时，命中率降到 90% 以下；Wi-Fi 行为 328 x 52 px，因此只有垂直方向起作用，$\sigma$ 必须超过约 16 px。交互组件中的采样百分比基于 400 个样本，因此预计会在公式值附近有几个百分点的噪声。
   </details>
