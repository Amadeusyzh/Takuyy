## なぜ重要か

このコラムの[研究ビジョン]({{ '/blog/2026/3d-gui-agent-01-research-vision/' | relative_url }})は、GUI エージェント、つまりユーザーに代わってグラフィカルユーザーインターフェース（graphical user interface、GUI）を操作する AI エージェントを、VR、AR、MR デバイスの 3D インターフェースへ持ち込むことです。3D GUI エージェントがどうあるべきかを問う前に、2D GUI エージェントがすでにどこまで来ているのかを正確に把握しておく必要があります。スマートフォン、デスクトップ、Web の上で、この分野は驚くほど速く進みました。2024 年 4 月の時点では、最良のモデルでも OSWorld のコンピュータタスクの 12.2% しか完了できず、人間は 72.4% でした。2025 年 12 月にはあるエージェントシステムが人間のベースラインを超え、2026 年にはフロンティアモデルが「コンピュータ操作（computer use）」を組み込みの能力として提供しています。3D エージェントが直面するであろう設計上の判断のほとんど（何を観測するか、どうやって対象を指し示すか、どの行動を許すか、どう訓練するか、どう評価するか、いつユーザーに尋ねるか）は、2D 画面の上ですでに議論され、測定され、部分的には決着しています。

この記事は、**2026 年 11 月**までのそうした研究のサーベイです。論文ごとではなくアイデアごとに構成しています。エージェントのループ、観測、グラウンディング、計画と記憶、訓練、評価、そして人間と安全性です。主要な手法については、それがどう動くのか（入力、出力、訓練信号、ループ）を説明し、重要な数値を示します。各節の最後では 3D インターフェースにとっての意味を述べ、最後の節ではそれらの論点を集めて、何が引き継げて何が壊れるのかを丁寧に整理します。関連する記事では 3D の側を扱います。[なぜ 3D インターフェースは操作しにくいのか]({{ '/blog/2026/3d-gui-agent-03-why-3d-interfaces-are-hard/' | relative_url }})と、[XR におけるエージェント、プラットフォーム、そしてギャップ]({{ '/blog/2026/3d-gui-agent-04-agents-in-xr-and-the-gap/' | relative_url }})です。

## 前提知識

- 大規模言語モデル（large language model、LLM）と視覚言語モデル（vision-language model、VLM）についての基本的な知識。VLM は画像とテキストを読み、テキストを書くモデルです。
- マルコフ決定過程（Markov decision process）と、方策勾配（policy gradient）による強化学習（reinforcement learning）の考え方（[世界モデルシリーズ]({{ '/blog/2026/world-models-01-what-is-a-world-model/' | relative_url }})と[身体性 AI シリーズ]({{ '/blog/2026/embodied-ai-01-robotics-foundations/' | relative_url }})で両方を扱っています）。
- GUI エージェントについての予備知識は仮定しません。

数値についての注意です。以下のベンチマークスコアは、異なる評価ハーネス（harness）、ステップ上限、ベンチマークのバージョンを使う論文、ベンダーのページ、リーダーボードから取っているため、出典をまたいだ比較はおおまかにしかできません。各数値には出典と日付を添えています。「二次情報」は報道やアグリゲーターを通じてしか知られていない数値を示します。2025〜2026 年の産業界のシステムの多くは査読を経ていない arXiv 上の技術報告であり、その旨を明記しています。

## 1. GUI エージェントとは何か

### 1.1 ループ

**GUI エージェント**は、自然言語でタスク（「Wi-Fi をオンにして」「金曜日の大阪行きで一番安い便を予約して」）を受け取り、人が使うのと同じグラフィカルユーザーインターフェース（GUI）を操作してそれを完了させます。画面を見て、何をすべきかを決め、タップ、クリック、キー入力、スクロールを送るのです。したがってタスクは、アプリごとの専用 API ではなく、*インターフェースを通して*解かれます。ここがまさに要点です。人が使えるアプリならどれでも、アプリの開発者が何もしなくても、エージェントが使えるようになります。

形式的には、1 回のエピソードは部分観測の意思決定過程です。ステップ $t$ でエージェントは、指示 $g$、現在の観測 $o_t$（スクリーンショット、画面のテキスト記述、またはその両方）、そしてそれまでの観測、思考、行動からなる自分の履歴 $h_t$ を持っています。方策 $\pi$ が行動 $a_t$ を出力し、デバイスがそれを実行して次の画面 $o_{t+1}$ を生成します。エピソードは、エージェントが `finish` を出力したとき、タスクが実行不可能だと宣言したとき、ユーザーに質問したとき、あるいはステップ数を使い切ったときに終わります。成功は、デバイスの最終状態 $s_T$ で判定されます。

$$
a_t \sim \pi(\,\cdot \mid g,\; o_{\le t},\; a_{<t}), \qquad \text{success} = \mathbb{1}\big[\,\mathrm{check}_g(s_T) = \text{true}\,\big].
$$

$\pi$ の内部では、ほとんどのシステムが下の図のループの何らかの形を実行しています。**観測**し（場合によっては画面を要素に分解し）、次のステップを**計画**し、それを**グラウンディング**（grounding。「Share ボタン」を画面上の具体的な位置に変換すること）し、**行動**し、その結果を**検証または振り返り**（reflection）して、**記憶を更新**します。一見した以上に重要な 2 つの脇道があります。エージェントはユーザーに**尋ねる**ことができ（曖昧さを解消するため、あるいは影響の大きい行動を確認するため）、また**停止する**ことを選べます。

{% include blog_figure.liquid path="assets/img/blog/3d-gui-agent/02-agent-loop.svg" localized="true" caption="2D GUI エージェントの構造。メインループ（紫）は観測、計画、グラウンディング、行動を回し、デバイスが次の画面を返します（緑）。フレームワーク型エージェントは各ボックスを別々のモジュールやプロンプトとして実装し、ネイティブエージェントモデル（破線の枠）は 4 つすべてを 1 つの視覚言語モデルで行います。記憶と振り返り（青）、およびユーザーへの質問・確認の経路（赤）が、システムごとに最も違いが出る部分です。" %}

このループを共有する 2 つのアーキテクチャの系統があります。

- **フレームワーク型エージェント**（framework agent。2023〜2024 年に登場し、今も一般的）：汎用の LLM や VLM に役割ごとのプロンプトを与え、手作りの知覚（アクセシビリティツリー、OCR、アイコン検出器）、記憶ファイル、ときには協調する複数のエージェントを組み合わせます。AppAgent、Mobile-Agent、AutoDroid、UFO、Agent S、SeeAct がその例です。
- **ネイティブエージェントモデル**（native agent model。2024 年末から）：1 つの VLM を、スクリーンショットと履歴から思考と行動への写像としてエンドツーエンドで訓練します。UI-TARS、Aguvis、OpenCUA、GUI-Owl、MAI-UI、そしてフロンティアモデル（Claude、OpenAI の CUA と GPT-5.x、Gemini）のコンピュータ操作モードがここに属します。

この区別は厳密ではありません。ネイティブモデルは軽いフレームワーク（プランナー、振り返り役、記憶）で包まれることが多く、フレームワーク型エージェントも訓練済みのグラウンディングモデルを呼び出すことが増えています。

### 1.2 小史：2016〜2026 年

{% include blog_figure.liquid path="assets/img/blog/3d-gui-agent/02-timeline.svg" localized="true" caption="GUI エージェントの主な出来事（2016〜2026 年）を時系列順に並べたものです（行は等間隔で、時間の縮尺は正確ではありません）。色は流れを表します：UI データと UI 理解（青）、合成 UI 上の強化学習（緑）、LLM/VLM エージェントシステム（紫）、グラウンディングとネイティブモデル（オレンジ）、ベンチマーク（灰）、商用のコンピュータ操作（赤）。下半分の 2024〜2026 年が、最初の 8 年間を合わせたよりも密であることに注目してください。" %}

年表が示すように、歴史は 4 つの段階に分かれます。

**UI データと UI 理解（2016〜2022 年）。** HCI とモバイルシステムの研究グループが、アプリを大規模に収集しました。ERICA（UIST 2016）と Rico（UIST 2017。ビュー階層とインタラクションの記録を伴う 72k+ のユニークな Android 画面）が、画面をデータにしました。モデルはウィジェットのキャプション生成、画面の要約（Screen2Words）、画面の埋め込み（Screen2Vec、UIBert）を学びました。Seq2Act（ACL 2020）は「機内モードをオンにする」のような指示を行動列に写像し、PixelHelp テストセットで 70.59% の完全一致を達成しました。その後、Google の Spotlight（ICLR 2023）と Pix2Struct（ICML 2023）が、**スクリーンショットだけ**を読むモデルが、しばしば欠けていたり誤っていたりするビュー階層を与えられたモデルを上回れることを示しました。アクセシビリティ研究（SUGILITE、そして画素からアクセシビリティのメタデータを再構築する Screen Recognition）は、アクセシビリティ情報を通してアプリを操作する、あるいはその情報を再構築する、という考え方をもたらしました。

**合成 UI 上の強化学習（2017〜2022 年）。** 並行して、強化学習（RL）の研究者たちは、スクリプトで報酬を与える小さな Web タスク（このボタンをクリックする、このフォームを埋める）の集まりである World of Bits / MiniWoB（ICML 2017）と、少数のデモンストレーションで探索を制約する MiniWoB++（ICLR 2018）を作りました。AndroidEnv（2021）は Android エミュレータを RL 環境として包みました。DeepMind の CC-Net（ICML 2022）は画素と DOM から MiniWoB++ で平均的な人間レベルの性能に達しましたが、約 240 万件の人間のデモンストレーションを必要としました。画素レベルの制御は機能したものの、その代償となるデータ量は実際のアプリでは誰にも払えないものでした。

**LLM と VLM のエージェントシステム（2023〜2024 年）。** GPT-4 と GPT-4V の登場とともに、プロンプトで動くエージェントがあらゆるプラットフォームに一斉に現れました。Android では AppAgent、Mobile-Agent、AutoDroid、MobileGPT、デスクトップでは UFO、Cradle、Agent S、Web では MindAct、SeeAct、WebVoyager です。大規模なデータセット（Android in the Wild、AITW：715,142 エピソード）と、最初の現実的なベンチマーク（Mind2Web、WebArena、OSWorld、AndroidWorld）が登場しました。この段階の主な教訓は、ボトルネックは計画ではなく**グラウンディング**だということでした。

**ネイティブモデル、大規模な RL、商用のコンピュータ操作（2024〜2026 年）。** 数百万個の合成要素で訓練したグラウンディングモデル（SeeClick、UGround、OS-Atlas）と、エンドツーエンドのエージェントモデル（UI-TARS、2025 年 1 月）が、手作りの知覚に取って代わりました。Anthropic は Claude のコンピュータ操作を（2024 年 10 月）、OpenAI は Computer-Using Agent と Operator を（2025 年 1 月）、Google は Gemini 2.5 Computer Use を（2025 年 10 月）公開し、GPT-5.4（2026 年 3 月）ではコンピュータ操作が汎用モデルのネイティブな能力になりました。R1 型の強化学習（2025 年）と、数千台の並列仮想マシン上でのマルチターンのオンライン RL によって、いくつかのベンチマークでスコアが人間のベースラインを超え、それらのベンチマークはより難しいもの（ScreenSpot-Pro、OSWorld 2.0）に置き換えられました。

### 1.3 3 つのプラットフォーム

ループはどこでも同じですが、3 つのプラットフォームでは、エージェントが見られるものとできることが異なります。

| プラットフォーム | 典型的な観測 | 行動の経路 | 実験用の環境 |
| --- | --- | --- | --- |
| スマートフォン（Android、iOS） | スクリーンショット、Android のビュー階層 / アクセシビリティツリー | タップ、長押し、スワイプ、文字入力、戻る、ホーム（`adb` またはアクセシビリティサービス経由） | Android エミュレータのスナップショット（AndroidEnv、AndroidWorld）、実機ファーム |
| デスクトップ（Windows、macOS、Linux） | スクリーンショット、OS のアクセシビリティ API（Windows UI Automation、macOS AX） | マウスの移動 / クリック / ドラッグ、キーボード、ホットキー、スクロール；シェルとアプリの API | スナップショット付きの仮想マシン（OSWorld、Windows Agent Arena） |
| Web | スクリーンショット、DOM、ブラウザのアクセシビリティツリー | クリック、文字入力、スクロール、ページ遷移、タブ（Playwright / Chrome DevTools Protocol 経由） | セルフホストのサイト（WebArena）、実際の Web サイト（Online-Mind2Web） |

スマートフォンは画面が小さく、タッチジェスチャーを使い、適切なアクセシビリティラベルを持たないアプリが多くあります。デスクトップは画面が大きく高解像度で、対象が小さく、ウィンドウが重なり合い、専門的なソフトウェアがあります。Web は最も豊かな構造（DOM）を持ちますが、同時に最も敵対的なコンテンツも抱えています。

**3D への示唆。** ループはその形のまま引き継がれ、成功の定義（最終状態に対するチェック）も同様です。変わるのはボックスの中身のすべてです。観測は画面ではなく視点になり、「グラウンディング」は空間内の対象を出力しなければならず、「行動」には連続的な 6 自由度（6-DoF）の動きが含まれ、デバイスは、その状態にユーザーの身体と部屋まで含むヘッドセットになります。第 8 節で各ボックスを順に見ていきます。

## 2. 観測：エージェントは何を見ているか

### 2.1 構造化された観測：ビュー階層、アクセシビリティツリー、DOM

どの GUI ツールキットも、ウィジェットのツリーを保持しています。Android はそれをビュー階層（view hierarchy）として、また支援技術向けには**アクセシビリティツリー**（accessibility tree）として公開します（各ノードはロール、テキストまたはコンテンツの説明、バウンディングボックス、クリック可能やチェック済みといったフラグを持ちます）。Windows には UI Automation、macOS には AX API があり、Web には DOM とブラウザのアクセシビリティツリーがあります。テキストとして直列化すると、ツリーは言語モデルが得意とするものをそのまま与えてくれます。名前と型を持ち、座標の付いた要素のリストです。最初の LLM エージェント（DroidBot-GPT、AutoDroid、UFO、MindAct）はこれを使っており、明確な長所があります。ラベルが正確で、目に見えない状態（チェック済み、無効、リスト内の画面外の項目）も得られ、操作する要素を位置で探すのではなく名前で指定できます。

短所も同じくらい明確で、それが論争の決め手になりました。ツリーは多くのアプリで**欠けているか誤っています**。独自描画のウィジェット、キャンバス、ゲーム、`div` とラベルのないアイコンボタンで作られた Web アプリなどです。ツリーは**長い**のです。現代的なページの生の HTML は、モデルが各ステップで読める量をはるかに超えます。MindAct（Mind2Web のベースライン）が、LLM に尋ねる前に小さなモデルで候補要素を順位付けしたのはそのためです。そしてツリーは**プラットフォームに依存します**。Android のアクセシビリティサービスの上に作ったエージェントは、Windows では動きません。

### 2.2 スクリーンショット

スクリーンショットは普遍的です。どのプラットフォームのどのアプリも画素を描画するからです。VLM はそれを視覚トークンに変換します。2025 年の GUI モデルの多くが土台にしている Qwen2.5-VL 系のパッチ分割では、1 つの視覚トークンが 28 x 28 画素の領域を覆います。したがって 1080 x 2400 のスマートフォンのスクリーンショットは約 $(1080/28)(2400/28) \approx 3{,}300$ トークン、1920 x 1080 のデスクトップは約 2,600 トークンになります。これは十分に扱える量ですが、数パッチしか占めない小さな文字やアイコンは読み取りにくくなります。高解像度のエンコーダ（CogAgent の 1120 x 1120 の分岐）、タイル分割（Ferret-UI の「任意解像度」サブ画像）、トークンの間引き（ShowUI）は、いずれもこの問題に対処するものです。

画素の難しさは、読むことではなく**指し示すこと**にあります。2023 年の汎用 VLM は画面をうまく説明できましたが、保存ボタンが*どこに*あるかは言えませんでした。2 つの答えが現れました。モデルに参照できるラベルを与えること（次の小節）と、座標を出力するようモデルに教えること（第 3 節）です。

### 2.3 Set-of-Mark ラベルと画面パーサー

**Set-of-Mark（SoM）プロンプティング**（Yang ら、2023）は、画像の分割領域に番号付きのマークを重ねて、モデルが座標の代わりに「17」と答えられるようにします。GUI エージェントはすぐにこれを採り入れました。WebVoyager、MM-Navigator、AppAgent、Mobile-Agent は、操作可能な各要素に枠と番号を描きます。要素は、アクセシビリティツリーがあればそこから、なければ検出器から取ります。**OmniParser**（Microsoft、2024）は画素だけからマークを作ります。ファインチューニングした YOLOv8 検出器がアイコンを見つけ、BLIP-2 のキャプション生成器がそれを説明し、OCR が文字を読みます。GPT-4V と組み合わせると、スクリーンショットだけを使う OmniParser エージェントが、ページの HTML を与えられた GPT-4 を Mind2Web で上回りました（ステップ成功率は、サイト横断で 36.5 対 30.1、ドメイン横断で 42.0 対 26.4）。

{% include blog_figure.liquid path="assets/img/blog/3d-gui-agent/02-observations.svg" localized="true" caption="1 つのおもちゃの設定画面を 3 種類の観測で表したもの。(a) スクリーンショットのみ：普遍的ですが、モデルは画素の中から対象を探さなければなりません。(b) Set-of-Mark：クリック可能な要素に番号付きの枠を付け、モデルはマーク番号で答えられます。(c) 直列化したアクセシビリティツリー：正確なラベル、ロール、状態（checked）、ボックスが得られますが、アプリがそれを公開している場合に限られます。第 4 節のインタラクティブなウィジェットも同じ 3 つのビューを使います。" %}

マークにもコストがあります。検出器の誤りが伝播し、密な画面ではマークが散らかって、ラベルを付けた内容そのものを隠してしまうことがあります。また SeeAct（ICML 2024）は、画像への注釈が、GPT-4V に候補要素のテキストリストを与える方法よりも明らかに弱いことを見出しました（オフラインの Mind2Web、タスク横断でのステップ成功率 20.3 対 39.1）。

### 2.4 どの観測が勝ったのか、そしてなぜか

証拠はモデルとともに変わってきました。図は、入力だけを変えた最も明快な比較を集めたものです。

{% include blog_figure.liquid path="assets/img/blog/3d-gui-agent/02-input-evidence.svg" localized="true" caption="同じエージェントで入力を変えたときのタスク成功率（4 つの研究から）。OSWorld（Xie ら、NeurIPS 2024、表 5）：GPT-4V ではスクリーンショットのみで 5.26%、スクリーンショット + アクセシビリティツリーで 12.17%。GPT-4o ではツリーのみで 11.36%、スクリーンショットのみで 5.03%。AndroidWorld（Rawles ら、2024）：GPT-4 Turbo でテキストのアクセシビリティツリーを使うと 30.6%、スクリーンショット + Set-of-Mark では 25.4%。EntWorld（Mo ら、2026）は企業向け Web アプリ上の訓練済みエージェントで、スクリーンショット 15.6%、ツリー 35.2%、両方 53.7%。2024 年の汎用モデルはテキストのほうが成績がよく、ハイブリッドは利用できる場合に最も効果があります。" %}

2024 年には、エージェントとして使われた汎用モデルは画素よりテキストで成績がよく、両方を使うと最もよくなりました。2025 年に変わったのは、**GUI 向けに訓練したモデル**によって、スクリーンショットだけのエージェントが互角になり、やがて主流になったことです。UI-TARS、Aguvis、GUI-Owl、MAI-UI、そしてフロンティアモデルのコンピュータ操作モードは、いずれもスクリーンショットだけから行動します。GPT-5.4 は Online-Mind2Web で「スクリーンショットのみ」で 92.8% を報告しています（OpenAI、2026 年 3 月）。この変化は 3 つの理由で説明できます。

1. **カバー範囲。** 画素はどのアプリにもありますが、ツリーはそうではありません。ツリーを必要とするエージェントは、キャンバス、ゲーム、リモートデスクトップ、ラベルの不十分なアプリで、黙って失敗します。
2. **訓練データ。** グラウンディングのデータは、構造*から*大規模に生成できます（DOM のボックスをスクリーンショットとして描画する。第 3 節）。そのため視覚モデルは、ツリーが知っていたことを学び、その後はツリーなしで動けます。
3. **全プラットフォームで 1 つのモデル。** スクリーンショットと汎用的な入力イベント（タップ、クリック、文字入力）は、Android でも Windows でも Web でも同じインターフェースです。クロスプラットフォームのネイティブモデルが必要としているのはまさにこれです。

ツリーが消えたわけではありません。ツリーがある場所では強力な追加信号であり続けます（EntWorld のハイブリッドの結果）。UFO2 のような Windows エージェントは UI Automation と視覚的なパースを融合し、Apple と Google はアシスタントの行動を画素ではなくアプリインテント（app intent）とアクセシビリティ API を通して実行しています。

**3D への示唆。** スクリーンショット優先という教訓は引き継げます。XR シーンを描画したビューは主要な観測として妥当であり、OmniParser の XR 版（描画フレームに対する検出器とキャプション生成器）も作ることができます。構造化された側の情報は 3D のほうがさらに豊かです。エンジンはすべてのオブジェクトの名前、型、姿勢、操作可能かどうか（シーングラフ（scene graph））を知っており、visionOS と Android XR は 2D のアクセシビリティの仕組みを空間アプリへ拡張しています。壊れるもの：ヘッドセットの視界は自己中心的（egocentric）で、頭を動かすたびに変わるため、1 つの UI 状態から多数の画像が生まれます。フレームには奥行き、ステレオ、遮蔽、そして現実世界のパススルー（passthrough）映像が含まれます。そして多くのイマーシブアプリは、アクセシビリティのメタデータをまったく持たない独自の 3D UI を描画します。これは 2021 年に Screen Recognition が iOS で取り組んだ状況と同じです。エージェントの「画面」をどうするかも選択の問題になります。ユーザーの視界にするのか、別の場所に置いた仮想カメラにするのか、部屋の地図にするのかです。

## 3. グラウンディング：「Share ボタン」から画面上の位置へ

### 3.1 問題とその評価指標

**GUI グラウンディング**（GUI grounding）は、参照表現（「共有メニューを開く」のような指示や、「左下の Share アイコン」のような説明）とスクリーンショットを、操作すべき要素の位置へ写像します。グラウンディングのベンチマークは $N$ 個の三つ組（スクリーンショット、指示、対象のボックス $B_i$）を与え、モデルは点 $\hat p_i$ を出力します。精度は、点がボックスの中に入った割合です。

$$
\mathrm{Acc} = \frac{1}{N}\sum_{i=1}^{N} \mathbb{1}\big[\hat p_i \in B_i\big].
$$

タップやクリックは点なので、点は自然な出力です。この指標は重要な幾何学的事実を隠しています。少しずれた点がそれでも正解になるかどうかは、対象の大きさに依存するのです。予測誤差が各軸について標準偏差 $\sigma$ 画素のほぼガウス分布に従い、対象が真の点を中心とする半幅 $a$、半高 $b$ のボックスだとすると、命中確率は

$$
P(\text{hit}) = \operatorname{erf}\!\Big(\frac{a}{\sigma\sqrt2}\Big)\,\operatorname{erf}\!\Big(\frac{b}{\sigma\sqrt2}\Big).
$$

です。44 x 44 px のスマートフォンのアイコン（$a = b = 22$）で $\sigma = 8$ px なら 0.99 ですが、4K のプロ向けアプリケーションの 12 px のツールバーアイコン（$a = b = 6$）では、同じ誤差で 0.30 になります。同じモデル、同じ誤差でも、スコアは大きく違います。これが第 3.4 節で見る ScreenSpot と ScreenSpot-Pro の差であり、第 4 節のウィジェットのグラウンディングモードで実際に試せます。

### 3.2 位置を出力する 3 つの方法

1. **リストから要素を選ぶ**（マークの番号、要素 ID、DOM ノード）。単純で正確ですが、リストの質がすべてです。ツリーかパーサーが必要になります。
2. **座標をテキストトークンとして書く。** VLM は単に `click(x=412, y=873)` を出力します。SeeClick（ACL 2024）は、約 100 万件のグラウンディングサンプルで Qwen-VL の継続事前学習を行い、これを可能にしました。UI-TARS や後続のほとんどのモデルもこれに従い、座標はベースモデルに応じて正規化値か絶対画素値で表します。パーサーは不要ですが、数字として書かれた座標が受ける空間的な教師信号は弱く（クロスエントロピー損失にとっては、1 画素ずれた答えも画面の反対側の答えも同じくらい「間違い」です）、信頼度を持たない、脆い 1 点しか得られません。
3. **ヒートマップを予測する。** GUI-Actor（NeurIPS 2025）は `<ACTOR>` トークンを追加し、その視覚パッチへのアテンションを出力とします。対象のボックスに重なるすべてのパッチが教師信号を受け、ピークがクリック位置になり、小さな検証器が候補領域を順位付けします。マップの広がりは、自然な信頼度の信号になります。

### 3.5 見てからズームする：探索とカスケード

ScreenSpot-Pro の論文自身が、訓練不要の手順 **ScreenSeekeR** を提案しています。プランナーモデルが対象のありそうな領域を提案し、グラウンディングモデルがその切り出し領域の中を探し、探索を再帰的に繰り返します。何の訓練もなしに 48.1% で、最良の 1 回推論の 18.9% を大きく上回りました。**探索範囲を狭めるほうが、モデルを大きくするより効く**というこの教訓は、後のモデルに明示的なズームのステップとして取り込まれ（GUI-ARP の適応的な領域知覚；MAI-UI のズームモードは 73.5% で、1 回推論の 67.9% を上回る；Qwen-UI-Agent はズームで 81.5%）、反復的な精密化にも取り込まれました（Chain-of-Ground、68.4%）。GroundCascade（2026 年 11 月）は、1 つ目のモデルの予測が信頼できなさそうなときだけ 2 つ目のグラウンディングモデルに尋ね、85.33% に達しています。

「見てからズームする」は、ヘッドセットが**フォービエイテッドレンダリング**（foveated rendering）と視線で行っていることの 2D 版です。対象がありそうな場所に解像度を使うのです。また、テスト時の計算（第 4.6 節）が、計画だけでなく知覚にも効くことを思い出させてくれます。

### 3.6 プランナーとグラウンディングモデルを分ける

グラウンディングがボトルネックなら、強力な汎用モデルに計画させ、専門モデルにグラウンディングさせるという選択肢があります。SeeAct（ICML 2024）は、実際の Web サイトでこのボトルネックを直接測りました。人間がグラウンディングを行う場合（「オラクル」）、GPT-4V はタスクの 51.1% を完了しましたが、最良の自動グラウンディングでは 37.8% にとどまりました。Jedi は逆方向から示しました。OpenAI の o3 をプランナーとし、そのクリックを 7B の Jedi モデルでグラウンディングすると、OSWorld で 23% から 51% に上がったのです。Agent S2（2025）はこの考えを**グラウンディングモデルの混合**（mixture of grounders。対象ごとに選ばれる視覚、テキスト、構造の専門モデル）へ進め、Phi-Ground（2025）はそうした専門グラウンディングモデルの訓練を体系的に調べました。

**3D への示唆。** グラウンディングはほかのどの部分よりもよく引き継がれ、ある意味ではむしろ易しくなります。最良の 2D グラウンディングモデルはすでにヒートマップを出力したり（GUI-Actor）、2 段階でズームしたりしており、これらはそれぞれ、ヒートマップのピークを通る**レイキャスト**（ray casting）と、視線に導かれたフォービエーションに直接対応します。また、2D では DOM から生成していた合成グラウンディングデータを、3D ではエンジンから生成できます。エンジンは、どのオブジェクトでも、どの視点からでも、正確なラベル付きで描画できるからです。壊れるもの：出力はもはや画素ではなく、オブジェクトや体積になります。1 つの画素が、奥行きの異なる複数のオブジェクトに対応しうるのです。小さい対象、遠い対象、真横を向いた対象は数画素にしか投影されません（ScreenSpot-Pro の問題が、ヘッドセットの光学系によってさらに悪化します）。対象が遮蔽されていたり、視野の外にあったりもします。そして指示はしばしばユーザーの身体を基準にしています（「私の左にあるパネル」）。第 8.2 節でこれを具体的に扱います。

## 4. 計画、振り返り、記憶

### 4.1 行動の前に推論する

ほぼすべてのエージェントは、各行動の前に短い**思考**（thought）を ReAct の形式で書きます。「Wi-Fi のスイッチがオフになっている。タップする」と書いてから `tap(...)` を出すのです。AitZ（2024）は Android のエピソードに chain-of-action-thought（画面に何が表示されているか、行動で何を達成すべきか、何が起きたか）の注釈を付け、UI-TARS は、タスク分解、振り返り、マイルストーン認識を含む「System-2」の推論トレースでネイティブモデルを訓練しました。推論は計画には役立ちますが、純粋なグラウンディングでは害になることがあります。GUI-G1（2025）は、長い思考の連鎖（chain of thought）がグラウンディング精度を下げることを見出しており、多くのグラウンディングモデルは座標を直接答えます。

### 4.2 行動空間

行動空間（action space）は、大きな影響を持つ設計上の判断です。典型的なモバイルの行動空間は `tap(x, y)`、`long_press(x, y)`、`swipe(start, end)`、`type(text)`、`back`、`home`、`wait` に、デバイスを操作しない 3 つの行動を加えたものです。`finish`、`infeasible`（このタスクはここでは実行できない。MoTIF（ECCV 2022）がこれを研究課題にしました）、そして `ask_user(question)` です。デスクトップのエージェントは、マウスの移動、ドラッグ、スクロール、キーボードショートカット、ウィンドウ管理を加えます。

設計レバーの図のパネル (a) は、この選択がどれほど重要かを示しています。AppAgent の成功率は、ほかに何も改善しないうちから、生の行動での 2.2% から、番号付き要素に対する小さな行動空間での 48.9% へ上がりました。Agent S（ICLR 2025）はこの点を一般化して **Agent-Computer Interface（ACI）**としました。エージェントを人間用のインターフェースに無理に通すのではなく、*エージェントのために*インターフェース（即座のフィードバックを伴う、制約されグラウンディングされた行動の集合）を設計する、という考え方です。

最近の最も強いシステムは、**GUI 操作とプログラムによる操作を混ぜて**います。UFO2（2025）は、アプリケーションのネイティブ API があればそれを呼び、なければ GUI のクリックに切り替えます。CoAct-1（2025）は、オーケストレーターに GUI オペレーターとスクリプトを書くプログラマーエージェントのどちらを使うかを選ばせ、OSWorld で 60.76% に達しました。UI-TARS-2 と Qwen-UI-Agent（2026）は、GUI、ターミナル（CLI）、ファイルシステムの操作を統合しています。MAI-UI は、行動空間に Model Context Protocol（MCP）のツール呼び出しと、ユーザーとの明示的なやり取りを加えています。MobileWorld（2025）は、ユーザーへの質問と MCP ツールを採点対象のタスクの種類にしました。インターフェースをまたぐ認可についての研究（2026）は、セキュリティ上の結論を導いています。同意は、行動がクリック、コマンドライン、API のどれを通して発行されたかによらず、その行動の*効果*に結び付けるべきだ、というものです。

### 4.3 振り返りと検証

1 回のタップの誤りで、エージェントは違うアプリに入り込んでしまうことがあります。よいエージェントと悪いエージェントを分けるのは、それに気づけるかどうかです。**Mobile-Agent-v2**（NeurIPS 2024）は、各行動の前後の画面を比べ、その行動を正しい、誤り（違うページ：戻る）、効果なし（何も変わらない：別のことを試す）に分類する振り返りエージェントを追加しました。タスクの進捗の要約を保つ計画エージェントと、注目すべき内容のための記憶ユニットと合わせて、そのベンチマークでの成功率を 43.2%（v1）から 75.0% に引き上げました。UI-TARS は **reflection tuning** を使います。自分自身のオンラインのトレースの中で見つかった誤りを修正と組にし、修正された続きでモデルを訓練するので、回復が方策の一部になります。

検証は候補の中から選ぶことにも使えます。GTA1（ICLR 2026）は複数の計画をサンプリングし、判定役（judge）に 1 つを選ばせます。**Agent S3**（2025、TMLR 2026）はこれを *Behavior Best-of-N* でエピソード全体に拡張しました。完全なロールアウトを複数回実行し、それぞれを画面上で何が変わったかの短い「行動ナラティブ」にまとめ、判定役にナラティブ同士を比べさせるのです。これにより OSWorld で 72.6% を達成し、人間のベースライン 72.36% を超えた最初の公表結果となりました（2025 年 12 月）。

否定的な結果も同じくらい重要です。OSWorld 2.0（2026 年 6 月）の失敗分析によれば、エージェントは今でも「制約を見失い、タスクの途中で届いた情報を見落とし、ユーザーに尋ねずに推測し、検証を省いてしまう」のです。

### 4.4 記憶と探索

エージェントには 2 種類の記憶が必要です。**タスクの中では**、進捗を追い、ある画面で読んだ情報を別の画面で必要になるまで覚えておかなければなりません（Mobile-Agent-v2 の記憶ユニット、Mobile-Agent-v3 のノートテイカー）。**タスクをまたいでは**、アプリについての知識を蓄積できます。

- **探索ドキュメント。** AppAgent は、まずエージェントにアプリを探索させ（あるいは人間の操作を見せ）、次に各要素が何をするかを説明する文書を書かせます。成功率は、自己探索による文書で 48.9% から 73.3% に、デモンストレーションに基づく文書で 84.4% に、手書きの文書で 95.6% に上がりました（設計レバーの図、パネル a）。
- **UI 遷移グラフ。** AutoDroid（MobiCom 2024）は、LLM を使わずにオフラインでアプリを探索し、どの行動がどの画面につながるかのグラフを作って、実行時にそれをプロンプトのヒントに変えます。DroidTask ベンチマークで GPT-4 を使ってタスク成功率 71.3% を達成し、問い合わせコストを 51.7% 削減しました。
- **再利用できるスキル。** MobileGPT はサブタスクを保存します。Agent Workflow Memory（ICML 2025）は過去のエピソードから再利用可能なワークフローを導き出します（Mind2Web と WebArena で相対的に +24.6% と +51.1%）。Mobile-Agent-E（2025）は各タスクの後に「Tips」と「Shortcuts」を書き出します（Mobile-Eval-E で絶対値 +22%）。AppAgentX は繰り返される行動の連鎖を新しい高レベルの行動に圧縮します。Agent S4（2026 年 10 月）は最も先まで進んでいます。メタエージェントがエージェント自身のツール、スクリプト、使い方の知識を進化させ、27B のオープンモデルで OSWorld V2 の 21.3% に達しました（インターフェースを固定した同じモデルの 3.8 倍）。

### 4.5 マルチエージェント設計

いくつかのシステムは、仕事を役割ごとのエージェントに分割しています。Mobile-Agent-v2 は計画、意思決定、振り返りのエージェントを使い、Mobile-Agent-E はマネージャーと知覚担当を加え、Mobile-Agent-v3 は GUI-Owl モデルをマネージャー、ワーカー、振り返り役、ノートテイカーの役割で包んでいます。デスクトップでは、UFO の HostAgent がタスクを分解してアプリケーションごとの AppAgent に振り分け、Agent S2 は汎用のプランナーと専門のグラウンディングモデルを組み合わせ、Magentic-One のオーケストレーターはタスクと進捗の台帳を保ちながら、Web サーファー、ファイルサーファー、コーダー、ターミナルを指揮します。UFO3（2025）は、Windows、Linux、Android のデバイスをまたいでエージェントを統括します。Minitap の 5 役割のシステム（計画、サブゴールの追跡、状態の取得、意思決定、実行）は AndroidWorld で pass@3 100% を報告しており、タスク分解を外すと 26.1 ポイントを失います。

役割を分ける代償はレイテンシです。役割ごとにモデル呼び出しが 1 回増え、OSWorld-Human（2025）は、エージェントが要する時間の大半を計画、振り返り、判定の呼び出しが占めていることを見出しました。

### 4.6 テスト時のスケーリングと先読み

環境をリセットできるなら、エージェントはいくつかのことを試して最良のものを残せます。Best-of-N のロールアウト（Agent S3）、判定役付きの計画のサンプリング（GTA1）、あるいは Web の状態に対する最良優先の**木探索**（tree search。Koh ら、2024；VisualWebArena で 26.4%）です。リセットできないなら、**世界モデル**（world model）で候補行動の結果を想像できます。WebDreamer は、各候補のクリックで何が表示されるかを LLM にシミュレートさせて予測を採点し、実際のサイト上で木探索の 4〜5 倍の効率を得ています（第 5.5 節）。

### 4.7 試してみよう：1 つのエージェント、3 つの観測、1 つのミス

## 5. GUI エージェントの訓練

2026 年までに、強いエージェントの多くは 4 段階のレシピに従うようになりました。データを集めるか合成し、グラウンディングと軌跡（trajectory）で教師ありファインチューニング（supervised fine-tuning、SFT）を行い、ルールベースの報酬でグラウンディングの強化学習を行い、多数の並列環境でオンラインのマルチターン RL を行う、というものです。世界モデルはいくつかの場面で登場します。図は各段階の対応関係を示しています。

### 5.1 データ

最初に来たのは**人間のデモンストレーション**でした。AITW（NeurIPS 2023）は 30,378 個の指示について 715,142 個の Android エピソードを集めました。AndroidControl（NeurIPS 2024）は 833 個のアプリにわたる 15,283 個のデモンストレーションを、高レベルとステップレベルの両方の指示付きで集め、厳しい結果を示しました。ドメイン内の性能はデータとともに伸びるが、未知のアプリでの性能ははるかにゆっくりとしか伸びない、というものです。OpenCUA（2025）は、3 つの OS と 200 以上のアプリケーションにわたるデスクトップのデモンストレーション集 AgentNet を、注釈ツールとともに公開しました。

デモンストレーションは高価なので、今ではほとんどのデータが**合成**されています。

- **チュートリアルから。** Synatra は間接的な知識（ハウツー記事）を約 10 万件のデモンストレーションに変換し、1 件あたりのコストはおよそ USD 0.031 です。AgentTrek は Web のチュートリアルを VLM エージェントで再現し、1 軌跡あたり約 USD 0.55 です。TongUI はマルチモーダルなチュートリアルから 143K の軌跡を作ります。Explorer は約 USD 0.28 で 94K を生成します。Fara-7B の FaraGen パイプラインは、検証済みの軌跡を 1 件約 USD 1 で生成します。
- **探索から。** OS-Genesis（ACL 2025）は通常の順序を逆にします。タスクを書いてから実行を試みるのではなく、まず探索し（ルールベースのクリック、文字入力、スクロール）、次に GPT-4o に観測された各遷移を低レベルの指示として記述させ、それらを高レベルのタスクに組み立てさせます（「逆タスク合成」（reverse task synthesis））。その後タスクを再実行し、報酬モデルで軌跡をふるいにかけます。こうした軌跡約 1000 件で、Qwen2-VL-7B は AndroidWorld で 17.41% に達しました。タスクを先に決める合成では 6.25% でした。
- **構造から作るグラウンディングラベル。** UGround は Web ページを描画し、その DOM を使って約 1000 万個の要素にラベルを付けました。OS-Atlas は 5 つのプラットフォームにわたって 1358 万個を作りました。Jedi はインターフェースをウィジェットの種類に分解し、400 万個の例を合成しました。これは 3D にとって最も重要なデータの経路です。3D ではエンジンが DOM の役割を果たすからです。

### 5.2 教師ありファインチューニング

一般的な SFT のレシピは、**まずグラウンディング、次に行動**を訓練します。Aguvis（ICML 2025）はこの 2 段階を明示しています。1 ステップの（指示、スクリーンショット、点）データでのグラウンディング段階と、内的独白（inner monologue）付きのマルチステップの軌跡での計画・推論段階です。UI-TARS はさらに、大規模な知覚データセット（要素のキャプション、密な画面記述、状態遷移）、統一されたクロスプラットフォームの行動空間、推論トレース、reflection tuning を加えています。SFT の結果は、有能ではあるが脆い方策です。データの中の経路を模倣するだけで、自分自身の誤りを経験したことがないのです。

### 5.3 ルールベースの報酬による強化学習

2025 年の初め、推論モデルの「R1」レシピ（Group Relative Policy Optimization、GRPO と検証可能な報酬）が GUI に届きました。最初はグラウンディングと 1 ステップの行動に対してです。1 つの訓練例について、モデルは $G$ 個の答え $o_1, \dots, o_G$ をサンプリングし、それぞれが報酬 $r_i$ を受け取ります。GRPO は価値ネットワークを必要としません。各答えのアドバンテージ（advantage）は、グループ内で標準化した報酬です。

$$
A_i = \frac{r_i - \operatorname{mean}(r_1, \dots, r_G)}{\operatorname{std}(r_1, \dots, r_G)},
$$

そして方策は、アドバンテージが正の答えのほうへ押し動かされます（PPO と同様に、クリップした確率比と参照モデルへの KL ペナルティを伴います）。グラウンディングでは、報酬は学習したモデルではなくルールです。

$$
r = r_{\text{format}} + \mathbb{1}\big[\hat p \in B\big] \quad\text{or}\quad r = r_{\text{format}} + \mathrm{IoU}(\hat B, B).
$$

報酬が正確で無料なので、数千個の例で十分です。UI-R1（2025 年 3 月）は 136 個のタスクを使って 3B モデルを ScreenSpot で 22.1 ポイント、ScreenSpot-Pro で 6.0 ポイント改善しました。GUI-R1 は約 3K サンプルで OS-Atlas を上回り、SE-GUI は 3K サンプルで ScreenSpot-Pro の 47.3% に達しました（7B）。0/1 の点報酬が抱える明らかな問題には、2 つの改良が対処しています。GUI-G1 は、モデルがボックスを予測するときに**報酬ハッキング**（reward hacking）が起きる（巨大なボックスを予測すると IoU 型の報酬が安く上がる）ことを見出し、ボックスの大きさに制約を加えました。GUI-G² は 2 値の命中判定を**ガウス報酬**（Gaussian reward）に置き換えました。要素の中心で最も高く、要素の大きさに応じて広がる滑らかなスコアで、「ほぼ正解」が「大きく外れ」より多く報われるようにするものです。

### 5.4 オンラインのマルチターン強化学習

1 ステップの報酬では、回復や長期的な計画は教えられません。そのためには、エージェントが実際の環境で行動し、エピソードの終わりに報酬を受ける必要があります。**DigiRL**（NeurIPS 2024）は、実際の Android アプリでこれを説得力をもって示した最初の研究です。既存データでのオフライン RL から始め、並列のエミュレータ上で、アドバンテージ重み付きの更新、自動カリキュラム、成功を判定する VLM を使ってオンラインで続けます。1.3B のモデルは AitW のタスクで 17.7% から 67.2% に上がり、CogAgent（38.5%）やフィルタ付きの行動クローニング（57.8%）を上回りました。**WebRL**（ICLR 2025）はエージェントの失敗から新しいタスクを生成し、結果報酬モデル（outcome reward model）を訓練して、WebArena-Lite で Llama-3.1-8B を 4.8% から 42.4% に引き上げました。

自由度の高いタスクの報酬は、プログラムによるチェッカーがあればそこから、なければ VLM の判定役や批評役（critic）から得ます（OS-Themis（2026）はマルチエージェントの批評役を使い、AndroidWorld で +10.3% を報告しています）。2026 年の慎重な研究（Gu ら）は注意を付け加えています。同じアルゴリズムでも、テストタスクが訓練から離れるほど RL による向上は小さくなるのです。UI-TARS-7B-SFT では、訓練タスクの未知のインスタンスで +17.5 ポイント、未知のタスクテンプレートで +11.1、未知のアプリケーションで +4.2 でした。Qwen3-VL-8B では +10.3、+7.4、+0 でした。対象アプリの中で数ステップの適応を行うと、+22.9 を取り戻せました。

### 5.5 GUI のための世界モデル

**世界モデル**は、現在の観測と行動が与えられたときに次の観測を予測します。GUI では 3 つの用途があります。行動前の先読み、RL のための想像上の環境、そしてデータ合成です。表現はさまざまです。

- **テキスト。** WMA（ICLR 2025）は、行動の後で*何が変わるか*を自然言語の記述として予測し、方策を訓練することなく、WebArena と Mind2Web で行動選択に使います。WebDreamer は、LLM 自身に各候補の結果を想像させます。
- **コード。** Code2World（2026）は次の画面を描画可能な HTML として予測するので、テキストとレイアウトが正確に保たれます。Gemini-2.5-Flash に組み込むと、AndroidWorld で 9.5% 向上します。Generative Visual Code Mobile World Models（ICML 2026）は同じことをモバイル向けに行います。
- **画素。** ViMo はテキストのプレースホルダー付きで次のスクリーンショットを生成します。NeuralOS（ICLR 2026）は、再帰的な状態トラッカーと拡散モデルのレンダラーで、デスクトップ全体をシミュレートします。
- **訓練用。** DynaWeb と WM-R1（2026）は想像上のロールアウトの中で方策を訓練し、WebWorld は Web シミュレータを 100 万回以上のインタラクションへと拡大しています。

これらは、[世界モデルシリーズ]({{ '/blog/2026/world-models-01-what-is-a-world-model/' | relative_url }})で取り上げた動画や 3D の世界モデルの GUI 版にあたります。

**3D への示唆。** このレシピは引き継げ、その一部はむしろ易しくなります。レイとコライダーの判定は正確で無料のグラウンディング報酬なので、空間的な対象に対する R1 型のグラウンディング RL を、人手のラベルなしにエンジンのデータから立ち上げられます。逆タスク合成はエンジンとよく合います。ランダムな探索が生み出す状態遷移を、VLM がタスクとして記述できるからです。そしてシーン記述の差分（USD や glTF の変換の変更）を予測することは、Code2World の HTML の 3D 版です。壊れるもの：XR の軌跡コーパスはまったく存在しません（AITW も AndroidControl もありません）。XR シミュレータはインスタンスごとに GPU を必要とするため、20,000 の並列環境は高くつきます。そして汎化の研究が警告するように、RL による向上は未知の XR アプリへ移ると残らないかもしれません。XR アプリが共有するウィジェットの慣習は、スマートフォンのアプリよりはるかに少ないからです。

OSWorld の曲線は、この分野の最も明快な要約です。公開時（2024 年 4 月）は 12.24%、コンピュータ操作付きの Claude 3.5 Sonnet が 14.9%（2024 年 10 月；ステップ数を増やすと 22.0%）、OpenAI の CUA が 38.1%（2025 年 1 月）、Claude Sonnet 4.5 が OSWorld-Verified で 61.4%（2025 年 9 月）、Agent S3 が 72.6%（2025 年 12 月）、GPT-5.4 が 75.0%（2026 年 3 月）、GPT-5.5 が 78.7%（2026 年 4 月）で、2026 年半ばには産業界のモデルが約 80% に達し、二次情報では Claude Opus 4.8 について 83.4% が報告されています。2 年でおよそ 6.5 倍の伸びです。その後、長期的なタスクを扱う OSWorld 2.0 が、スケールを約 20% にリセットしました。

なぜ長いタスクではこれほど急激に崩れるのでしょうか。大ざっぱなモデルが役に立ちます。各ステップが独立に確率 $q$ で成功し、タスクに $n$ ステップが必要なら、タスクが成功する確率は $q^n$ です。$q = 0.99$ のとき、30 ステップのタスク（OSWorld 1.0 の規模）は 74% の確率で成功しますが、318 ステップのタスク（OSWorld 2.0 でのツール呼び出し数の平均）は 4% しか成功しません。実際のエージェントはいくつかの誤りから回復するので、これは悲観的な見積もりですが、長いタスクの成否を決めるのが 1 ステップの精度ではなく、検証と回復であることを説明してくれます。

### 6.4 数値をどこまで信じるか

2D の研究分野は、評価についていくつかの教訓を痛い目に遭いながら学びました。

1. **オフライン評価は過大評価する。** Online-Mind2Web、すなわち「An Illusion of Progress?」（COLM 2025）は、以前のベンチマークでは強く見えた多くの Web エージェントが、実際のタスクでは 2024 年の SeeAct のベースラインを上回れないことを見出しました。
2. **評価器にはバグがある。** OSWorld-Verified（2025 年 7 月）は 300 を超える問題を修正しましたが、その多くは評価スクリプトの問題でした。修正の前後のスコアは直接比較できません。評価ハーネス、ステップ上限、思考の予算によって、スコアは数ポイント動きます。
3. **自己申告と飽和。** AndroidWorld のリーダーボードには自己申告の 100% の項目がいくつも並び、このベンチマークは飽和と明記されています。ScreenSpot、ScreenSpot-v2、WebVoyager も飽和しています。
4. **信頼性は能力ではない。** 1 回の試行が確率 $p$ で成功するとき、$k$ 回の試行のうち少なくとも 1 回が成功する確率は $\text{pass@}k = 1-(1-p)^k$、$k$ 回すべてが成功する確率は $\text{pass}^k = p^k$ です。$p = 0.9$、$k = 3$ では、それぞれ 0.999 と 0.729 になります。ユーザーが必要としているのは後者です。Minitap は AndroidWorld で両方を報告しています。pass@3 100%、pass^3 94.0% です。
5. **効率。** OSWorld-Human（2025）は、最良のエージェントでも必要なステップ数の 2.7〜4.3 倍を費やし、後半のステップは序盤のステップの最大 3 倍の時間がかかり、タスクに数十分を要することを見出しました。
6. **判定役はノイズを含む。** WebVoyager の GPT-4V 判定役と Online-Mind2Web の WebJudge は、人間と約 85% の割合で一致します。

**3D への示唆。** ベンチマークの設計は引き継げます。リセット可能な環境、プログラムによるチェックを伴うパラメータ化されたタスク（AndroidWorld）、評価用に取り分けたアプリ、信頼性（pass^k）と効率の指標、人間が検証した判定役です。壊れるもの：リセット可能な VM は、GPU 上でヘッドレスかつ並列に動かさなければならない XR シミュレータやエンジンのビルドになります。成功の判定には空間的な許容誤差（5 cm 以内に配置されている、ユーザーの方を向いている）が必要です。描画された 1 枚のフレームを見る判定役には、遮蔽された結果が見えません。そして実機でのテストには、人の身体と部屋が関わります。2D ベンチマークの文献にある XR の素材は、VR、AR、MR インターフェースの 393 本の画面録画からなる GUI-World だけで、それも動画の質問応答として評価されています（多肢選択で GPT-4o が 84.3%）。エージェントが XR インターフェースを操作するインタラクティブなベンチマークは、2D の文献には見当たりません。XR の側に何があるかは[第 4 回]({{ '/blog/2026/3d-gui-agent-04-agents-in-xr-and-the-gap/' | relative_url }})で見ていきます。

## 7. 人間の関与、アクセシビリティ、安全性、プライバシー

### 7.1 委任、監督、そして質問

人のために行動するエージェントは、いつその人を関与させるかを決めなければなりません。**Morae**（UIST 2025）は、黙って行われた選択が見えない、全盲・ロービジョン（blind and low-vision、BLV）のユーザーを対象にこれを調べました。予備調査では、実行可能な 576 件の依頼のうち 484 件でエージェントが「完了」と報告しましたが、正しかったのは 189 件だけで、182 件の失敗は曖昧さ（どの便か、どのサイズか）に関わるものでした。Morae は判断の分岐点を検出して一時停止し、アクセシブルな選択インターフェースを生成します。一時停止が必要なタスクでは 65.6% の確率で成功し、OpenAI の Operator は 50.8% でした。10 人の BLV 参加者による研究では、ユーザーは Morae を使うとより多くのタスクを完了できましたが、実行は遅くなりました。

どのくらいの頻度で尋ねるかは、スケジューリングの問題です。「When Should Users Check?」（CHI 2026）は、マルチステップのタスクにおける確認の頻度をモデル化しました。48 人の参加者の 81% が、最後にだけ確認するよりも途中で確認するほうを好み、スケジュールされた確認によってタスク時間が 13.54% 短縮されました。2026 年のほかの研究は、ライブセッションでの監督戦略を比較し（48 人の参加者、192 セッション）、実際のユーザーがいつ介入するかを予測し（CowCorpus）、エージェントの実行中に生じる短い「マイクロ待ち時間」のための設計を行っています。Operator と Manus のユーザビリティ研究（CAIS 2026）は、業界の掲げる理想と、ユーザーが実際にこなせたこととの間に大きな隔たりがあることを見出しました。

すべてのユーザーがエージェントに行動してほしいわけではありません。スクリーンリーダーのユーザーに向けた文脈に応じた*ガイダンス*（CHI 2026）は、人が自分でソフトウェアを操作するのを助けます。また「Beyond Chat and Clicks」（2026）では、エージェントがクリックして進むのではなく、ユーザーの周りの実際のインターフェースを作り変えます。こうした「案内してほしい」モードや「UI を作り変える」モードは、完全な自律の代わりになる選択肢です。

### 7.2 アクセシビリティ

GUI エージェントはしばしばアクセシビリティの技術として宣伝されますが、エージェント自身が、示唆に富む形でアクセシブルではありません。A11y-CUA データセット（CHI 2026）は、タスクの 78.3% に成功するコンピュータ操作エージェントが、キーボードのみの操作に制限すると 41.67% に、画面拡大鏡を使うと 28.3% に落ちることを見出しました。これらは多くの障害のあるユーザーが頼っている設定です。8 人の全盲のユーザーによる 1,258 件の実際のデスクトップ操作の指示では、GPT-5 の成功率は 52.5% でした（EMNLP 2026）。ElderBench（2026）は、高齢者から集めた 249 個のタスクをまとめています。

### 7.3 セキュリティ：画面上のすべてが入力になる

GUI エージェントは表示されているものを何でも読むので、**すべての画素が入力経路になります**。攻撃者が書いたコンテンツも含めてです。攻撃は実際に効果を上げています。

- **ポップアップ。** OSWorld と VisualWebArena 上の敵対的なポップアップは 86% の攻撃成功率に達し、タスク成功率を 47% 下げました。ポップアップを無視するようエージェントに指示しても効果はありませんでした（ACL 2025）。
- **ページに注入されたコンテンツ。** EIA は最大 70% のケースで特定の個人データを盗みます（ICLR 2025）。ページの画素の 5% 未満を摂動させるだけで、最大 67% のケースでエージェントを乗っ取れます（ICLR 2025）。
- **視覚的なプロンプトインジェクション（visual prompt injection）。** VPI-Bench は、コンピュータ操作エージェントで最大 51%、ブラウザエージェントで 100% に達します（ICLR 2026）。RedTeamCUA は Web 経由のインジェクションで OS レベルの操作を狙い、能力の高いエージェントほど悪用されやすい場合があることを見出しました（ICLR 2026）。StepJack はインジェクションを複数のステップに分散させ、成功率を 41.7% から 72.9% に引き上げます（2026）。
- **適応的な攻撃。** 21 通りの防御の構成に対して、適応的な視覚的インジェクションは今でも約 92% の確率で成功します（2026 年 11 月）。

有害性のベンチマークはもう一方の側を測ります。OS-Harm（NeurIPS 2025）は 150 個の OSWorld タスクで悪用、インジェクション、不適切な振る舞いをテストし、MobileSafetyBench は同じことを Android で行います。SEAM（2026）は有害なタスクを複数の画面に分割し、エージェントがその最大 92% を完了してしまうことを見出しました。

製品に搭載された防御は、完璧ではなく多層的です。OpenAI の Operator のシステムカードは、607 タスクでの確認の再現率（recall）92%、再現率 99%・適合率（precision）90% のプロンプトインジェクション監視、そして対策ありで 23%、対策なしで 62% というインジェクションへの脆弱性を報告しています。Google の Gemini Computer Use は、提案された各行動に安全性の判定（許可、要確認、ブロック）を付けます。Anthropic は、最小権限の VM と、影響の大きい行動の確認を推奨しています。Microsoft の Windows エージェントワークスペースと UFO2 のピクチャー・イン・ピクチャーのデスクトップは、エージェントをユーザーのセッションから隔離します。

### 7.4 プライバシー

スクリーンショットには画面上のすべてが写っています。PriMobiBench（ACM CCS 2026）は、VLM で動くモバイルエージェントが、最大 82.5% のケースで画面上の機微なデータを抽出でき、約 70% の確率でユーザーのプロファイルを推測できることを見出しました。タスクに無関係なインターフェースの部分をマスクすると、タスク性能を約 8% 犠牲にして、プロファイリングを最大 58% 減らせました。

**3D への示唆。** 曖昧なときの一時停止、スケジュールされた確認、影響の大きい行動の確認、認証情報の入力時のユーザーによる引き継ぎ、そして「代わりにやる」のではなく「案内する」モードは、どれも引き継げます。空間的な参照（「それをあそこに置いて」）があるため、曖昧さは 2D よりも頻繁に生じます。壊れるもの：確認と引き継ぎは、マウスとキーボードなしで、しかも臨場感（presence）を損なわずに機能しなければなりません。ユーザーの空間でコンテンツを動かすエージェントは、ユーザーを驚かせたり、ユーザーが手を伸ばしているものを動かしてしまったりしかねません。パススルーは、制御されていない現実世界の文字（ポスター、画面、標識）をエージェントの入力に持ち込み、2D の防御ですら塞げていないインジェクションの攻撃面をさらに広げます。そしてヘッドセットのカメラ、視線追跡、部屋のスキャンは、スクリーンショットよりはるかに機微な情報です。

## 8. 2D から 3D へ：何が引き継げて、何が壊れるか

この節では、「3D への示唆」の各段落を 1 つの議論にまとめます。問題は、2D エージェントのアイデアが XR で役に立つかどうか（明らかに役に立ちます）ではなく、2D エージェントのどの前提が成り立たなくなるかです。それらの破綻こそが、3D GUI エージェントの研究課題を定めるからです。

| 観点 | 2D の最先端（2026 年 11 月） | 3D へ引き継げるもの | 3D で壊れるもの |
| --- | --- | --- | --- |
| 観測 | スクリーンショットのみのネイティブモデル；ツリーは追加の信号 | 描画したビューを主入力に；より豊かなツリーとしてのシーングラフ；オブジェクトに固定したマーク | 自己中心的で変化する視点；奥行き、ステレオ、遮蔽、パススルー；アクセシビリティツリーがほとんどない |
| グラウンディング | 点がボックス内；ScreenSpot-Pro で 1 回推論 74%、カスケードで 85% | ヒートマップはレイに；ズームはフォービエーションに；エンジンが生成するラベル；正確なレイ命中報酬 | 対象はオブジェクトや体積；1 画素に複数のオブジェクト；小さく遠い対象；身体基準の参照 |
| 行動空間 | タップ、文字入力、スワイプ、キー；GUI + API + MCP のハイブリッド | 設計された小さな行動集合；インテントと API を優先 | 6-DoF の姿勢、レイ、ピンチ、つかむ、両手、視線、音声、移動；命中ではなく許容誤差 |
| 視野 | すべてが 1 つの画面上にある（残りはスクロール） | 能動的な知覚、探索の記憶 | ユーザーの背後、遮蔽された場所、別の部屋にある対象；空間的な記憶が必要 |
| レイテンシ | 1 ステップ 2.5〜4 秒；タスクに数十分 | 量子化、バッチ化、小型モデル、デバイスとクラウドの分担 | ユーザーはインターフェースの中で待つ；1 フレーム 8〜14 ms の描画予算が同じデバイスを共有 |
| 訓練 | SFT、ルール報酬 RL、1 万台以上の VM でのオンライン RL | レシピ全体；無料の空間的報酬；逆タスク合成 | 軌跡コーパスがない；GPU を大量に使うシミュレータ；未知のアプリへの転移が弱い |
| 評価 | 実行によるチェック、パラメータ化、pass^k | 設計原則 | 大規模なヘッドレス XR ランタイム；空間的な許容誤差；遮蔽された結果 |
| 人間と安全性 | 確認、一時停止、引き継ぎ、隔離 | これらのパターン | ユーザーの手と視界の引き継ぎ；物理的な驚き；パススルー経由のインジェクション；部屋と視線のプライバシー |

### 8.1 観測

2D エージェントの観測は、ユーザーにとってもエージェントにとっても同じスクリーンショットです。ヘッドセットでは観測の候補がいくつもあり、合意されたものはありません。ユーザーが見ているステレオのフレーム、単眼の描画、奥行き、エンジンのシーングラフ、空間アプリ向けのプラットフォームのアクセシビリティ情報、ユーザーの頭・手・視線の姿勢、あるいはエージェントが選んだ視点から描画した「エージェントビュー」です。2D の教訓（カバー範囲のために画素を、利用できるところでは構造を）はハイブリッドを示唆しますが、視点の問題は新しいものです。1 つの UI 状態が、ユーザーが動くたびに異なる画像を生み出すのです。

### 8.2 奥行きのあるグラウンディング

図は、実際の可視性の計算を使って 2 つの状況を対比しています。

{% include blog_figure.liquid path="assets/img/blog/3d-gui-agent/02-2d-vs-3d.svg" localized="true" caption="左：2D 画面では、すべての対象が見えており、1 つの点が 1 つの要素を指します。右：ユーザーの周りにある 4 枚のパネルで、ユーザーの視錐台（64 x 50 度）は前方を向き、シーンには仮想の箱があります。パーセンテージは、各パネル上の 400 点のうち、視錐台の内側にあり箱に隠されていない点の割合で、ユーザーの頭からのレイキャストで計算しています。正面のパネル A は完全に見え、パネル B は視界に入っているものの 87% が箱に遮蔽され、右の C とユーザーの背後の D は視野の外にあります。赤い線は、A 上の点を選択するハンドレイです。" %}

2D のグラウンディングモデルは画素を出力します。3D のグラウンディングモデルは対象のオブジェクト（またはその上の点）を出力しなければならず、2D モデルからそこへ至る自然な方法は**レイを飛ばす**ことです。内部パラメータ $K$、カメラの回転 $R$、位置 $\mathbf c$ のビューでモデルが画素 $(u, v)$ を予測したとすると、レイは

$$
\mathbf x(t) = \mathbf c + t\,\frac{R K^{-1} [u, v, 1]^\top}{\lVert R K^{-1} [u, v, 1]^\top \rVert}, \qquad t > 0,
$$

であり、対象はそのレイが最初に当たるコライダーです。画素の誤差 $\delta$ は、画素単位の焦点距離 $f$ に対して約 $\delta/f$ ラジアンの角度誤差になり、距離 $z$ では約 $z\,\delta/f$ の横方向の誤差になります。水平視野角 90° で幅 1920 画素のビューなら $f = 960$ px なので、2 m 先での 10 px の誤差は約 2 cm になり、遠くのパネル上の小さなボタンを外すには十分です。ここでは点よりもヒートマップの出力（GUI-Actor）のほうが適しています。その広がりをレイの円錐に変換し、候補オブジェクトの大きさと比べられるからです。遮蔽は、2D のグラウンディングにはなかった失敗をもたらします。レイがより手前のオブジェクトに当たってしまうことがあり（図のパネル B）、正しい行動は、まず頭やパネルを動かすことかもしれません。

### 8.3 行動空間

2D の行動は、2D の点に対する少数の離散的な種類です。XR の入力には、レイとピンチによる選択、直接タッチ、完全な 6-DoF の姿勢（回転と並進、すなわち $SE(3)$ の元）でのつかんで置く操作、回転と拡大縮小、両手のジェスチャー、視線とピンチ、視線の滞留（gaze dwell）、音声、コントローラーのボタン、そして移動やテレポートが含まれます。これらの多くには「クリック」に相当するものがなく、その成功は許容誤差（数度以内にそろっている、数センチ以内に置かれている）で判定されます。言語モデルは、こうした操作列を直接生成するのが苦手です。ComboBench（2025）では、最良のモデルでも VR ゲームの行動を正確なコントローラーとヘッドセットの操作列に変換できたのは 11.7% だけでした。2D での答え、つまり設計された小さな行動空間と、可能な場合の API（AppAgent、Agent S の ACI、UFO2）は、おそらく正しい出発点であり、ClawMobile（2026）がスマートフォンについて主張しているように、言語モデルの下に決定的な低レベルコントローラーを置くのがよいでしょう。

### 8.4 視界の外にある対象

2D エージェントは、隠れたコンテンツをスクロール、タブの切り替え、メニューを開くことで扱い、記憶が見たものを覚えておく助けになります。XR では、ウィンドウがユーザーの背後にあったり、現実や仮想のオブジェクトに遮蔽されていたり、別の部屋にあったりし、ユーザー自身も動きます。エージェントはどこを見るかを決める（あるいはユーザーに振り向いてもらう）必要があり、ウィンドウやオブジェクトがどこにあるかの**永続的な空間記憶**を必要とします。それは画面のリストではなく、アンカーを持つシーングラフです。空間記憶は現在のマルチモーダルモデルの既知の弱点です。VSI-Bench（2024）では、屋内の動画についての空間的な質問で、最良のモデルが 45.4%、人間は約 79% でした。

### 8.5 レイテンシ

{% include blog_figure.liquid path="assets/img/blog/3d-gui-agent/02-latency.svg" localized="true" caption="1 回の判断にかかる時間（対数スケール）。90 Hz の XR フレームは 11 ms です。ゲームエージェント Lumine（2025）は最初の行動を 114 ms で、推論ありでは 234 ms で出します。2D GUI エージェントの 1 ステップは 2.5〜4.0 秒です（UI-TARS-2、量子化版と完全精度版）。公表されている XR の研究プロトタイプは、1 ターンに約 4 秒（DuoZone のウィンドウレイアウト）、9.1 秒（SIAgent の意図推定エージェント）、49 秒（NavAI の VR ナビゲーション）かかります。緑と橙の棒の間の差が、3D GUI エージェントのレイテンシの問題です。" %}

デスクトップでは、1 ステップに 3 秒、1 タスクに 20 分かかるエージェントでも、ユーザーが別のことをしている間にバックグラウンドで動かせます。ヘッドセットでは、ユーザーはインターフェースの*中*にいて、それを見ています。図は数値を並べています。2D エージェントの 1 ステップの時間は、リアルタイムの 3D ゲームエージェントが達成しているものより 2 桁大きく、最初の XR プロトタイプはさらに遅いのです。2D の道具箱（UI-TARS-2 の 1 ラウンドあたりのレイテンシを OSWorld で 3.1 ポイントの犠牲と引き換えに 4.0 秒から 2.5 秒に短縮した量子化、UFO2 の投機的なマルチアクション計画、行動のバッチ化、Ferret-UI Lite や Fara-7B のような小型のオンデバイスモデル、MAI-UI のデバイスとクラウドの振り分け）はすべて使えますが、ヘッドセットには同じチップ上で 1 フレームあたり 8〜14 ms という厳しい描画予算もあります。そして VideoGameBench（2025）は、ゲームが一時停止して待ってくれるときにはうまくいくエージェントも、リアルタイムでははるかに成績が落ちることを示していますが、XR は一時停止できません。作業を分担する設計（ヘッドセットが知覚と描画を行い、スマートフォンやクラウドが計画する）や、エージェントが考えている間にユーザーを*案内する*設計が、おそらく必要になるでしょう。

### 8.6 データと評価

2D の分野はデータの上に築かれました。Rico、AITW、AndroidControl、Mind2Web、そして何百万もの合成グラウンディングラベルです。XR には、指示から行動への軌跡コーパスがなく、公開されている最大の VR の UI 要素データセットでも約 17.7K フレームで（DISCOVR、UIST 2025）、エージェントがタスクを完了するために XR アプリを操作しなければならないインタラクティブなベンチマークは存在しません。それを作るには、第 6.4 節の問題を 3D で解く必要があります。ヘッドレスでリセット可能な XR ランタイム、空間的な許容誤差を伴う成功判定、評価用に取り分けたアプリ、そして信頼性の指標です。[第 4 回]({{ '/blog/2026/3d-gui-agent-04-agents-in-xr-and-the-gap/' | relative_url }})では、そうしたベンチマークを載せられるプラットフォームとツールを概観し、[第 3 回]({{ '/blog/2026/3d-gui-agent-03-why-3d-interfaces-are-hard/' | relative_url }})では、人間の側から見て、どの 3D インタラクションが委任する価値があるほど難しいのかを説明します。

### 8.7 このコラムにとっての意味

3 つの結論が、[研究ビジョン]({{ '/blog/2026/3d-gui-agent-01-research-vision/' | relative_url }})と研究計画へ引き継がれます。

1. **エージェントの構成要素の大半は再利用できる。** スクリーンショット優先のネイティブモデル、プランナーとグラウンディングモデルの分離、振り返り、探索の記憶、ハイブリッドな行動空間、SFT の後に RL を行うレシピ、実行に基づく評価は成熟しており、公開もされています（UI-TARS、GUI-Owl、OpenCUA、MAI-UI の重みとコード）。
2. **新しい問題は空間的なものである。** 視点に依存する観測、奥行きと遮蔽を伴うグラウンディング、空間記憶を必要とする視界外の対象、連続的な 6-DoF の行動空間、そしてインターフェースの中でのレイテンシには、それを解決してくれる 2D の対応物がありません。
3. **欠けているのはインフラである。** 軌跡データセット、空間的な対象のためのグラウンディングベンチマーク、そして XR アプリのための、実行によってチェックするインタラクティブなベンチマークが、2D で Rico、ScreenSpot、OSWorld が果たした役割を担うことになるでしょう。

## まとめ

- GUI エージェントは、観測、計画、グラウンディング、行動、検証、記憶のループを通して、指示を人が使うのと同じインターフェース上の行動に変えます。ネイティブモデルは今や最初の 4 つを 1 つの VLM で行います。
- スクリーンショットは、あらゆるアプリをカバーし、グラウンディングのデータを構造から合成できるという理由で、主要な観測としてアクセシビリティツリーに勝ちました。ツリーは有用な追加の信号として残っています。
- グラウンディングは 2024 年のボトルネックでした。合成データ、ヒートマップヘッド、ルール報酬の RL、ズームやカスケードによる推論によって、ScreenSpot-Pro の成績は 18.9%（2025 年 4 月）から、1 回推論で 74%、カスケードで 85%（2026 年 11 月）に上がりました。
- 行動空間の設計、探索ドキュメント、振り返り、Best-of-N による選択は、モデルを固定したままで、それぞれ成功率を数十ポイント動かしました。
- 訓練は、人間と合成の軌跡での SFT、次にルール報酬による GRPO、そして数千から数万の環境でのオンラインのマルチターン RL です。未知のアプリでは向上幅が小さくなります。
- OSWorld は 2025 年 12 月に人間のベースラインを超え、フロンティアモデルはコンピュータ操作をネイティブに提供しています。長期的な OSWorld 2.0（最高 20.6%）は、残された課題を示しています。制約の追跡、質問、検証です。
- すべての画素が攻撃面です。適応的なインジェクションは現在の防御を破り、製品は確認、監視、隔離に頼っています。
- 3D では、構成要素は引き継げるものの、観測、グラウンディング、行動、視野、レイテンシ、データ、評価がそれぞれ特有の形で壊れます。それがこのコラムの研究課題を定めています。

## 演習

1. **グラウンディング誤差と対象の大きさ。** 第 3.1 節の式を使って、$\sigma = 4$、8、15 px のときの、44 x 44 px のボタンと 12 x 12 px のアイコンに対する命中確率を計算してください。次に、12 px の対象でモデルのスコアが 50% になる $\sigma$ を見積もってください。このことは、2 倍のズームインの価値について何を示唆しているでしょうか。

   <details markdown="1"><summary>ヒント</summary>

   44 px のボタン（$a = b = 22$）では、約 1.00、0.99、0.74 です。12 px のアイコン（$a = b = 6$）では、0.75、0.30、0.09 です。命中率 50% には $\operatorname{erf}(6/(\sigma\sqrt2)) = 0.707$、つまり $6/(\sigma\sqrt2) \approx 0.74$ が必要なので、$\sigma \approx 5.7$ px です。2 倍にズームすると、モデルの画素単位の誤差はほぼ同じまま、対象の画素数が 2 倍になります。そのため 12 px の対象が 24 px の対象のように振る舞います。ScreenSeekeR やズームモードが大きく成績を伸ばすのはこのためです。数値はウィジェットのグラウンディングモードで確かめられます。
   </details>

2. **観測を選ぶ。** 病院の院内向け Windows アプリケーションのためのエージェントを作るとします。このアプリの独自描画のウィジェットは、UI Automation の名前を一切公開していません。第 2 節の観測の選択肢を挙げ、どれを使うか、それはなぜかを述べ、最初にどんなデータを集めるかを述べてください。

   <details markdown="1"><summary>ヒント</summary>

   名前がなければ、ツリーからはせいぜいボックスしか得られないので、意味はスクリーンショットが担わなければなりません。パーサー（OmniParser 型）またはスクリーンショットを入力とするネイティブモデルを主入力とし、存在する構造は何であれ追加の信号として使います。小さなグラウンディング用データセット（アプリケーションでよく行う操作について、対象のボックスにラベルを付けたスクリーンショット）を集めておけば、ほかのものを作る前に、最もボトルネックになりやすいグラウンディングの精度を測れます。
   </details>

3. **信頼性の計算。** あるエージェントが、1 回の試行あたり確率 0.85 でタスクに成功します。pass@3 と pass^3 を計算してください。次に、そのタスクに 40 ステップが必要で、各ステップが確率 $q$ で成功するとします。回復なしで 85% のタスク成功率を得るには、$q$ はいくつである必要があるでしょうか。このことは、ステップの改善と回復のどちらに投資すべきかについて何を示しているでしょうか。

   <details markdown="1"><summary>ヒント</summary>

   pass@3 $= 1 - 0.15^3 = 0.997$、pass^3 $= 0.85^3 = 0.614$ です。$q^{40} = 0.85$ から $q = 0.85^{1/40} \approx 0.9959$、つまり失敗するステップは 240 回に 1 回未満でなければなりません。1 ステップの精度をそこまで高めるのは難しいことです。失敗したステップを検出して取り消すこと（振り返り、第 4.3 節）で要求は緩和されます。各ステップは*最終的に*正しければよくなるからです。
   </details>

4. **3D グラウンディングのための報酬。** 描画された XR のビューと指示が与えられたとき、レイを飛ばすための画素を出力するモデルに対して、GRPO の報酬を設計してください。エンジンのコライダーを使います。遮蔽された対象や、小さく遠い対象をどう扱いますか。また、その報酬はどのようにハッキングされうるでしょうか。

   <details markdown="1"><summary>ヒント</summary>

   自然な報酬は、レイが最初に当たったコライダーが対象に属していれば 1 とし、それに、レイと対象の中心との角度距離に基づく滑らかな項（GUI-G² のガウス報酬のようなもの）を、対象の角度の大きさでスケーリングして加えるものです。こうすれば小さく遠い対象でも望みがなくなりません。遮蔽された対象については、正しい出力が遮蔽物（それを動かすため）なのか、「視点を変える」行動なのか、遮蔽物越しの対象なのかを決め、望む選択に報酬を与えます。ハッキングの例：対象のコライダーを含む大きなオブジェクトにレイを向けること（たとえばボタンの代わりにウィンドウ全体）。そのため、操作可能なコライダーのうち最も小さいものを使います。
   </details>

5. **実践：ウィジェット。** 写真のエピソードのステップ 3（ツールバー）でグラウンディングモードに切り替え、Share アイコンの中心に置いた点が Share に命中する割合が 90% を下回る最小の $\sigma$ を見つけてください。次に、Settings 画面の Wi-Fi の行で同じことをしてください。その違いを第 3.1 節の式で説明してください。

   <details markdown="1"><summary>ヒント</summary>

   Share アイコンのタッチ領域は 44 x 44 px なので、命中率はおよそ $\sigma \approx 11$ px で 90% を下回ります。Wi-Fi の行は 328 x 52 px なので、縦方向だけが問題になり、$\sigma$ は約 16 px を超える必要があります。ウィジェットに表示される割合は 400 個のサンプルによるものなので、式の値の周りに数ポイントのノイズがあると考えてください。
   </details>
