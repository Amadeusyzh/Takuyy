## なぜ重要か

[第 2 回]({{ '/blog/2026/3d-gui-agent-02-gui-agents-on-2d-screens/' | relative_url }})では、GUI エージェント（GUI agent）、つまり画面を読み取り、ユーザーの代わりにタップ、入力、スクロールを行うモデルが、スマートフォン、デスクトップ、Web の上で成熟した研究分野になったことを示しました。[第 3 回]({{ '/blog/2026/3d-gui-agent-03-why-3d-interfaces-are-hard/' | relative_url }})では、ヘッドセットやグラスの 3D インターフェースが平面の画面よりも操作しにくい理由を説明しました。本コラムの[研究ビジョン]({{ '/blog/2026/3d-gui-agent-01-research-vision/' | relative_url }})はこの二つを組み合わせます。すなわち、VR、AR、MR デバイスの 3D GUI をユーザーに代わって操作する、あるいはユーザーをその操作へと案内するエージェントです。

そのようなエージェントが新しいと主張する前に、すでに何が存在するのかを正確に知っておく必要があります。多くの部品はすでに存在します。XR シーンを構築する LLM、見ているものについての質問に答えるアシスタント、VR アプリをクリックして回るテストプログラム、ピクセルから 3D 空間で行動するゲームエージェント、メーカーが "take action on your behalf across your apps"（アプリをまたいであなたの代わりに操作を行う）ことができると説明する出荷済みのヘッドセット用アシスタント、そして LLM エージェントが VR アプリのメニューを操作できるようにするベンダー製ツールです。本記事では、**2026 年 11 月**時点でのこれらすべてを整理し、最も近いものについては数値とともに詳しく検討し、各 XR プラットフォームがエージェントに何を観測・制御させるのかを説明し、利用可能なデータセットを比較し、そして何がまだ欠けているのかを証拠が許す限り正確に述べます。ここでは先行研究に対して公正であることが重要です。ギャップは「XR にエージェントを入れた人はまだいない」よりも狭く、本記事はそれがどれほど狭いのかを正確に述べようとします。

## 0. 何を「近い」とみなすか：作業定義と評価基準

本コラムでは次の作業定義（working definition）を用います。**3D GUI エージェント**（3D GUI agent）とは、次のような AI エージェントです。

1. VR、AR、MR デバイス（ヘッドセットまたはグラス）の**空間ユーザーインターフェース（spatial user interface）を知覚する**：3D 空間に配置されたウィンドウ、ボリューム、メニュー、ウィジェット、インタラクティブな仮想オブジェクトを、レンダリングされた視界および／またはシステムとアプリの構造を通じて捉える。
2. 自然言語（音声またはテキスト）で、場合によっては視線やポインティングと組み合わせて与えられる**ユーザーの意図を理解する**。
3. ユーザーのためにその **3D GUI を操作する**（選択、押下、つかむ、移動、サイズ変更、メニューやアプリの移動）、あるいはユーザーをその操作へと**案内する**。

四つ目の性質が、アイデアとシステムを分けます。それは、命令とアプリの集合に対するタスク成功率を測定する形で、**エージェントとして評価されている**ことです。

大きく異なる研究を一つの尺度で比較するため、本記事の各研究をこれら四つの性質について 3 段階で評価します。評価は論文と製品ページを私が読んだ結果に基づくもので、評価基準（rubric）は次のとおりです。

| 性質 | 2（完全） | 1（部分的） | 0（なし） |
| --- | --- | --- | --- |
| 3D UI の知覚 | 既存の XR アプリの UI 要素を、レンダリングされた視界または UI 構造から見つける | 特権的なメタデータ、シーングラフ、または UI 要素を伴わないピクセルを通じて XR シーンを知覚する | 物理世界のみを知覚する、または何も知覚しない |
| 意図の理解 | ユーザーからの自然言語のゴール | 暗黙の意図（視線、手の動き）、先回りの推論、またはテスト命令 | なし（例えばカバレッジ駆動のテスト） |
| 操作／案内 | XR UI（ウィンドウ、ウィジェット、インタラクタブル）に対する操作を実行する | XR 内で行動するが UI に対してではない（移動、世界の編集、サービス）、案内する、または実行せずに計画する | 回答または予測のみ |
| 評価 | 定量的なタスク結果またはユーザースタディの結果 | 予備的または小規模な研究、合成データのみ | なし、または非公開 |

第 2 節の能力ヒートマップ（capability heat map）は、この評価基準を 23 の研究と製品に適用しています。要点を言えば、いくつかの研究は二つの性質で「完全」に達し、少数は三つで達していますが、四つすべてで達しているものはありません。

### 1.1 XR 世界を構築・編集する LLM

XR における LLM 研究の第一波（2023-2024 年）は、言語を用いて**仮想世界を作成または変更**しました。**LLMR**（De La Torre et al., CHI 2024, Honorable Mention）は Unity 内で複数の GPT-4 の役割を統率します。シーングラフをテキストに要約する *scene analyzer*、*planner*、C# コードを書く *builder*、コンパイル時と実行時のエラーを確認する *inspector*、さらにスキルライブラリです。エラー率は素の GPT-4 の約 4 分の 1（アブストラクトでは 4 倍低いと記載）で、11 名の参加者がユーザビリティ調査で使用しました。**DreamCodeVR**（Giunchi et al., IEEE VR 2024）は音声による要求を、実行中の VR アプリを変更する C# にコンパイルします。**LLMER**（Chen et al., IEEE TVCG 2025）はコードを JSON に置き換え、先行研究と比べてトークン数が 80% 以上少なく、タスク時間が約 60% 短いと報告しています。**VRCopilot**（Zhang et al., UIST 2024）は 3D レイアウトの手動、自動、足場付き（scaffolded）の共同作成を比較し、足場付き（AI がワイヤーフレームを提案し、ユーザーがそれを編集する）がユーザーにより強い主体感（sense of agency）を与えることを見いだしました。これは、人々が XR の AI にどの程度の自律性を求めるかについての初期のデータ点です。**sMoRe**（Xing et al., arXiv 2024）は音声とテキストのコマンドから MR 内の仮想オブジェクトを配置・整理します。

最新のシステムは開発者を対象としています。**XR Blocks**（Li et al., arXiv 2025）と **Vibe Coding XR**（Du et al., arXiv の記載によれば VRST 2026）は、ユーザー、世界、インターフェース、エージェントからなる LLM に扱いやすい「Reality Model」を通じて、プロンプトを WebXR アプリに変換します。**GenXR-Bench**（Huang et al., arXiv, 2026 年 10 月）は 112 の XR 開発タスクでコーディングエージェントを評価します。その評価ハーネス（第 4 節で扱います）には、生成されたアプリを操作する VLM の「アクター（actor）」が含まれています。**ControlAnything**（Ryskeldiev, arXiv, 2026 年 11 月）では、コーディングエージェントが Quest 3 上で使用時に AR コントロールとデバイスコネクタを生成します（10 件中 9 件の要求が利用可能な状態になり、中央値 32.5 s）。

*この系統が 3D GUI エージェントに与えるもの：* LLM が XR のシーン構造を読み取れるという証拠（LLMR の scene analyzer）と、コンパクトな行動形式（LLMER の JSON）。*欠けているもの：* エンジンを通じてコンテンツを構築・編集するのであって、既存アプリのインターフェースを操作するわけではありません。

### 1.2 回答や案内を行う XR アシスタント

第二の系統は、ヘッドセットやグラスの中にマルチモーダルアシスタントを置きます。これらのシステムは**意図**に強く、とりわけ視線とポインティングから直示（deixis）的な参照（「これ（this）」「あれ（that）」「そこ（there）」）を解決することに長けています。

- **GazePointAR**（Lee et al., CHI 2024）は、LLM に問い合わせる前に、音声による質問中の代名詞を、ユーザーが注視またはポインティングしている対象の説明に置き換えます（12 名の参加者による実験室での研究と日記調査）。
- **G-VOILA**（Wang et al., IMWUT 2024）は、情報検索のために視線、視野、音声を用います。
- **EmBARDiment**（Bovo et al., IEEE VR 2025）は、ユーザーが読んでいる XR ウィンドウ（視線で選択）の内容を LLM チャットボットに与えるため、ユーザーは文脈を言い直す必要がありません。マルチウィンドウの XR UI を読み取りますが、回答のためだけです。
- **Satori**（Li et al., CHI 2025）は、信念・願望・意図（Belief-Desire-Intention）ユーザーモデルを持つ HoloLens 2 上の先回り型（proactive）AR アシスタントです。16 名の参加者による研究で、AR デザイナーが設計した Wizard-of-Oz システムに対し、11 のユーザビリティ項目すべてで非劣性を示し、レイテンシは 2-3 s でした。
- **Sensible Agent**（Lee et al., UIST 2025）は、何を提案するかだけでなく、どのように尋ねるか（多肢選択、はい／いいえ、アイコン）、どのチャネルを通じて尋ねるか（視線、頭、手、音声）も決定し、Android XR ヘッドセット上の WebXR で動作します。予備的研究（N=10）では、NASA-TLX のワークロードはベースラインの 43.27 に対して 20.55 でした。
- **Guided Reality**（Zhao et al., UIST 2025）と **AgentHands**（Liu et al., CHI 2026）は、空間内に視覚的な案内を生成します。インタラクション地点に固定されたハイライトや矢印、そしてエージェントが話している間に指し示したり実演したりする、レンダリングされたエージェントの手です。

*この系統が与えるもの：* 視線とポインティングによる意図の接地、空間的な案内のための語彙、そしていつどのように割り込むかのモデル。3D GUI エージェントの**案内モード（guide mode）**にとって最良の根拠です。*欠けているもの：* 出力は回答かオーバーレイであり、これらのシステムはいずれもインターフェースを操作しません。

### 1.3 すでに XR アプリを操作しているプログラム：自動テスト

ソフトウェア工学の研究は、2022 年から別の目的、すなわち**テストカバレッジ（test coverage）**のために VR アプリを自動で操作してきました。**VRTest**（Wang, ICSE 2022 tool demo）は Unity シーンを読み取り、カメラを動かして探索します。**VRGuide**（Wang, Rafi and Meng, ASE 2023）は計算幾何学を用いて、すべてのインタラクタブルなオブジェクトをカバーするカメラ経路を計画します。**VRExplorer**（Zhu et al., ASE 2025）、**XRintTest**（Gu et al., Automated Software Engineering 2026）、**AUTOVR**（Kim et al., USENIX Security 2025）、そして LLM 駆動の **ExploreAI**（Wang et al., arXiv 2026）については 2.7 節で説明します。**VRScout**（Wu et al., arXiv 2025）は人間のデモンストレーションから Action Chunking Transformer を学習し、市販の VR ゲームを 60 FPS でプレイします。これは言語を伴わない、ピクセルから 6-DoF への方策です。

動機は現実的です。オープンソースの Unity VR アプリ 314 本を調べた研究では、79% に自動テストがまったくありませんでした（Rzig et al., ISSTA 2023）。VR/AR ソフトウェア工学に関する 2026 年のサーベイ（Guo et al., arXiv, TSE に投稿）は、VR GUI 探索のための LLM エージェントを未解決問題として挙げており、座標の特定（coordinate localization）は解決されていないとしています。

*この系統が与えるもの：* 実際の VR アプリに対して機能する知覚と行動の仕組み、および 3D インタラクションの実行可能な語彙（fire、grab、socket）。*欠けているもの：* ユーザーの意図です。目標はすべてに触れることであり、ユーザーが求めたことを行うことではありません。

### 1.4 レンダリングされた視界を通じて 3D で行動するエージェント

ゲームエージェントは、**一つのインターフェース、すなわちピクセルを入力とし人間用の入力デバイスを出力とするインターフェースで、多くの 3D 世界にわたって言語に従えること**を示し、そのコストも測定しています。

- **SIMA**（SIMA Team, Google DeepMind, arXiv 2024）は、10 以上の 3D ゲームにわたって、言語条件付きのキーボード・マウス方策を学習しました。No Man's Sky のサブセットでは、人間の 60% に対して 34% の成功率に達し、言語なしのアブレーションでは 11% でした。言語は重要です。
- **SIMA 2**（arXiv, 2025 年 12 月）は Gemini Flash-Lite をファインチューニングして、推論し、会話し、行動する（96 のキー、クリック、離散化されたマウス移動）エージェントにし、SIMA の平均成功率をおよそ 2 倍にしました。Gemini をタスク設定者と報酬モデルとして用いて自己改善しますが、ファインチューニングは汎用的な推論能力を損ないます（AIME -15.4%、GPQA -19.5%）。
- **Cradle**（Tan et al., arXiv 2024）は、スクリーンショットからキーボードとマウスのスキルを書く、学習不要の 6 モジュール構成の GPT-4o フレームワークです。考えている間はゲームを一時停止しなければなりません。
- **Lumine**（Tan et al., arXiv 2025）はリアルタイム側の対照例です。Qwen2-VL-7B が毎秒 5 フレームを見て、30 Hz の行動チャンクを出力し、必要なときだけ推論します。最初の行動までの時間は推論なしで 113.9 ms、推論ありで 234 ms で、5 時間分の Genshin Impact のストーリーを完了します。
- **VideoGameBench**（Zhang et al., arXiv 2025）は、それがなぜ重要かを示しています。最先端の VLM がリアルタイムでプレイした場合にクリアしたのはゲームの 0.48%、ゲームが一時停止して待ってくれる場合でも 1.6% でした。**XR インターフェースはエージェントのために一時停止できません。**
- **Embodied Web Agents**（Hong et al., NeurIPS 2025 Datasets and Benchmarks）は、約 1.5k のタスクで 3D 世界とライブの Web サイトを組み合わせています。料理タスクでは、GPT-4o の失敗の 66.6% が 3D 世界と Web の間の切り替えに起因し、身体側（embodied）のみの失敗は 14.6%、Web のみの失敗は 8.0% でした。XR インターフェースはまさにこの混合、すなわち 3D 空間に浮かぶ平面パネルです。
- 3D ソフトウェアのエージェントは、純粋なピクセル制御に警鐘を鳴らしています。**VideoCAD**（Man et al., NeurIPS 2025 D&B、約 41k の合成 CAD UI 動画）では最先端モデルが長期の CAD UI タスクに失敗し、**ComAct**（Ai et al., arXiv 2026）は産業用 CAD における GUI エージェントの成功率がほぼゼロであると報告し、代わりに API による行動を主張しています。

*この系統が与えるもの：* ピクセルから 3D で行動するエージェントのための行動空間の設計、レイテンシ対策の手法、自己改善ループ。*欠けているもの：* これらの世界はインターフェースではなくゲームであり、ヘッドセット上で動作するものはありません。

### 1.5 ヘッドセットとグラスのアシスタント、そして一人称視点（egocentric）AI

出荷済みのアシスタントはすでに多くを知覚しています。カメラの映像、画面、場合によっては視線です。それをどう使うかは異なります。

- **Samsung Galaxy XR 上の Gemini**（Android XR、2025 年 10 月 21 日発売、1,799 ドル）：Google の発表記事によれば、Gemini Live は "can better understand what you're seeing and doing"（あなたが見ているもの、していることをよりよく理解できる）とされ、"take action on your behalf across your apps"（アプリをまたいであなたの代わりに操作を行う）ことができ、"Hey Google, organize these windows"（OK Google、これらのウィンドウを整理して）で開いているウィンドウを並べ替えます。詳細は 2.8 節で述べます。
- **Apple Vision Pro 上の Siri AI**（2026 年 6 月 8 日の WWDC で発表。visionOS 27 のリリースノートの日付は 2026 年 11 月 9 日）：Siri を見て話しかけ、部屋の中の物体や画面上のコンテンツについて尋ねることができ、Siri はアプリアクションを通じて "get[s] things done across apps"（アプリをまたいで物事を片付ける）とされています。
- **Meta**：Neural Band リストバンド付きの Meta Ray-Ban Display（米国で 2025 年 9 月 30 日発売、799 ドル）は、回答やステップごとのガイドをレンズ内に表示します。Connect 2026 で Meta は、AI グラス向けのパーソナルエージェント **Muse**（ショッピング、決済、予約のコネクタを通じて行動するもので、"in the coming months"（今後数か月のうちに）提供予定）と、OS に Meta AI エージェントを組み込み "play a movie, open an app, adjust your workspace"（映画を再生し、アプリを開き、ワークスペースを調整する）ことができる **Meta VR Glasses**（1,299.99 ドル、2027 年春）を発表しました。執筆時点ではいずれも出荷されていません。
- **研究**：一人称視点 AI は、一人称視点動画に対する質問応答（Ego4D、EgoSchema）から、先回り型の支援（ProAssist, EMNLP 2025；HoloAssist は、指導者が作業者を案内する 166 時間の HoloLens 2 データセット）を経て、タスクを実行するグラス型エージェントへと進んできました。**VisionClaw**（Liu et al., arXiv 2026）は Ray-Ban Meta グラスをエージェントにつなぎ、ショッピングカートへの商品追加、ポスターからのカレンダー予定の作成、IoT デバイスの制御を行います（実験室での研究 N=12、実運用 N=5）。

*この系統が与えるもの：* 実運用されている知覚と、ユーザーが委任を望んでいるという証拠。*欠けているもの：* 行動の経路は API とサービスであり、3D インターフェースの操作ではありません（Galaxy XR 上の Gemini は、詳細が非公開の例外です）。

### 1.6 3D と空間の理解

3D-LLM（3D-LLM、LEO、Video-3D LLM、GPT4Scene）、空間 VLM（SpatialVLM、SpatialRGPT）、シーングラフ（ConceptGraphs、HOV-SG）、3D 参照表現の接地（ScanRefer、SeeGround）は、空間内の**物理的なオブジェクト**を接地します。3D GUI エージェントにとって覚えておく価値のある結果が二つあります。**VSI-Bench**（Yang et al., CVPR 2025）では、屋内動画に関する空間記憶の質問に対して、最良の MLLM の正答率は 45.4% で、人間は約 79% でした。また、明示的な認知地図（cognitive map）は chain-of-thought よりも効果がありました。**SeeGround**（Li et al., CVPR 2025）は 3D シーンのビューをレンダリングし、2D VLM で接地します。これは 2D の GUI 接地モデルを 3D で機能させうる手法です。UI 側の対応物、すなわちステレオ、深度、頭部姿勢を用いて 3D 空間内の *UI 要素*を接地するモデルはまだ存在しません。最も近い研究である Orienter は、片目の 2D スクリーンショット上で動作します。

### 2.1 Orienter：VR フレーム内の操作可能な要素の接地

**Look Before You Leap: Context-Sensitive GUI Grounding for Boosting Automated Extended Reality (XR) Testing**（Shuqing Li et al., FSE 2026、Proceedings of the ACM on Software Engineering 3(FSE) 掲載、[DOI 10.1145/3808134](https://doi.org/10.1145/3808134)；arXiv 2409.10811、その arXiv 版のタイトルは *Grounded GUI Understanding for Vision-Based Spatial Intelligent Agent: Exemplified by Extended Reality Apps*）。手法の名前は **Orienter** です。

*問題。* VR アプリのスクリーンショット中の*操作可能な GUI 要素（interactable GUI elements, IGE）*を見つけること。スマートフォンの GUI と異なり、XR の要素はオープン語彙（open-vocabulary）であり（レバー、浮遊するパネル、ドアノブ）、ある要素が操作可能かどうかは文脈に依存します。同じ木箱でも、つかめる場合とつかめない場合があります。固定された 2D ウィジェットのクラスで学習した検出器は、うまく転移しません。

*手法。* 大規模マルチモーダルモデル（LMM：GPT-4V、GPT-4o、Claude 3.5 Sonnet または Gemini 1.5 Pro）を中心としたゼロショットのパイプラインです。

1. *意味的文脈の理解（semantic context comprehension）*：LMM がフレームと、Steam から収集したアプリ情報を読み取ります。
2. *リフレクション主導の候補検出（reflection-directed candidate detection）*：LMM が候補要素の説明を提案し、オープン語彙の接地モデル APE がそれらをボックスとして位置特定し、LMM の「アドバイザー（advisor）」がループの中でそれらを検証します。
3. chain-of-thought による*文脈依存の操作可能性分類（context-sensitive interactability classification）*。

これは[第 2 回]({{ '/blog/2026/3d-gui-agent-02-gui-agents-on-2d-screens/' | relative_url }})の 2D GUI エージェントの手法（意味のための言語モデルと座標のための接地モデルの組み合わせで、Set-of-Mark プロンプティングや OmniParser と同様）を VR フレームに移したもので、最初の推測がしばしば誤るためリフレクションが追加されています。

*データ。* 100 本の Steam VR アプリから得た 1,552 枚の右目フレーム（960x540）で、766 の意味カテゴリにわたる 4,470 個の操作可能要素のアノテーションを含み、13 名のアノテーターが 3 か月以上かけてラベル付けしました。

*結果。* IoU 0.75 における操作可能性の F1 は 44.10%（Gemini、アプリ単位の分割）で、学習済みの Faster R-CNN は 32.69%、強力な 2D 画面パーサーである OmniParser は 2.21% でした。文脈依存の分割では Orienter が 32.51% に達したのに対し、ベースラインは 0.5% 前後でした。厳しい IoU では適合率が崩れ（IoU 0.95 で 5.64%）、LMM に直接ボックスを求める方法は位置特定に失敗します。77 本のアプリの自動探索を 60 分間誘導するのに用いたところ、要素カバレッジは 0.65 から 0.83 に、有効なインタラクションは 5,911 から 13,038 に増えました（アブストラクトでは、これら本文の数値より大きな相対的向上が述べられています）。

*しないこと。* 片目の 2D 投影上で、深度やステレオなしに動作します。ユーザーのゴールはありません。「行動」はテスト探索のためにフレーム上のインタラクション地点としてシミュレートされたもので、実際の 6-DoF 入力ではありません。**重なり：知覚について大きい。** Orienter は、実際の XR アプリのレンダリングされたフレーム内で GUI 要素を接地する唯一の査読付き研究であり、その arXiv 版のタイトルはすでに "spatial intelligent agent"（空間知能エージェント）について語っています。本コラムは、これをアイデアの知覚側の半分として認めなければなりません。

### 2.2 ComboBench：意味的な行動からコントローラ操作の手順へ

**ComboBench: Can LLMs Manipulate Physical Devices to Play VR Games?**（Shuqing Li et al., arXiv 2510.24706, 2025 年 10 月；プレプリント）は、知覚の次のステップを切り出しています。"reload the gun"（銃をリロードする）のような意味的な行動が与えられたとき、その VR ゲームが要求するヘッドセットとコントローラの物理的な操作の系列を生成することです。

*データと手法。* Half-Life: Alyx、Into the Radius、Moss: Book II、Vivecraft からの 262 のシナリオ。正解の操作系列は Quest 2 で記録されています。7 つの LLM を、テキストのみで、ゼロショットと少数ショットで評価しました。

*結果。* 系列の厳密一致の最高値は 11.7%（Gemini-1.5-Pro、5-shot）で、GPT-4o は 10.9%、GPT-4 は 8.8% でした。オープンモデルは約 0-2% で、ゼロショットで 5.8% を超えたモデルはありませんでした。正規化されたアラインメントスコアは高く（最大 0.832、人間のベースラインは 0.833）、モデルは*どの*ステップが関わるかをおおよそ知っていますが、ステップ順序の正確さは約 0.3 以下にとどまりました。数例を与えると順序の正確さは 10-20 倍に向上しましたが、約 3 ショットを超えると向上はわずかでした。ステップを運動動作に対応づけることが最も弱い能力でした。

*しないこと。* スクリーンショットも実行も閉ループもなく、対象は GUI ウィジェットではなくゲームのメカニクスです。**重なり：行動の接地について大きい。** LLM が 6-DoF コントローラの手順をいかに知らないかを、最もきれいに測定したものです。

### 2.3 NavAI：閉ループ、ただし歩行のため

**NavAI: A Generalizable LLM Framework for Navigation Tasks in Virtual Reality Environments**（Xue Qin and Matthew DiGiovanni, ASE 2025 Workshops, [DOI 10.1109/ASEW67777.2025.00067](https://doi.org/10.1109/ASEW67777.2025.00067)；arXiv 2601.03251, 2026 年 1 月）は、自然言語のゴールと VR のスクリーンショットから実行される行動までを結ぶ、唯一の公開済み閉ループです。

*ループ。* グリッドを重ねた視野のスクリーンショットとユーザーの要求が GPT-4o に送られます。GPT-4o、Grok-2、Gemini-2.5-Flash の投票で次のステップが選ばれ、JSON の関数呼び出し（`move`、`rotate`、`look`、`scan_360`）が Unity シミュレータで実行され、新しい視界が返ってきます。グリッドのオーバーレイは Set-of-Mark プロンプティングの 3D 版の親戚であり、モデルが指し示すための番号付きの場所を与えます。

*結果。* 三つの Unity シーンで、21 個中 21 個の基本行動を実行し、18 個中 16 個のゴールタスク（89%）を完了しました。1 タスクあたり約 8 ターン、1 ターンあたり約 49 s で、1 タスクあたり最大約 395 s かかりました。

*しないこと。* 視点を動かすだけで、メニューやウィジェットには一切触れません。レイテンシはインタラクティブな利用より 2 桁大きいです（2.9 節）。**重なり：ループについて大きいが、GUI 操作についてはなし。**

### 2.4 SIAgent：エージェントが実行し、意図は目と手から

**SIAgent: Spatial Interaction Agent via LLM-powered Eye-Hand Motion Intent Understanding in VR**（Zhimin Wang, Chenyu Gu and Feng Lu, IEEE TVCG 32(7), 2026, [DOI 10.1109/TVCG.2026.3686395](https://doi.org/10.1109/TVCG.2026.3686395)；arXiv 2603.00522, 2026 年 3 月）は、ユーザーがジェスチャーとコマンドの対応づけを学ぶ手間を省けるかを問います。エージェントは自然な目と手の振る舞いを観察し、意図された操作を推論して実行します。

*パイプライン。* 30 Hz でサンプリングした 3 秒間の視線ウィンドウを 18 点に削減し、手の姿勢と指の状態を言語化します。三つの LLM 呼び出し（ChatGLM-4）が順位付きの六つの意図仮説を返し、エージェントが制御する仮想の手が選ばれたものを実行します。

*結果。* 研究 1（N=16、各 54 試行）で、コントローラ入力および視線+ピンチ（gaze+pinch）入力と比較しました。意図認識は 97.2%（視線+ピンチは 93.1%）、実行精度は 86.8%、1 タスクあたりの時間は LLM の時間を*除いて* 7.7 s（コントローラは 5.8 s）、LLM のレイテンシは約 9.1 s、腕の疲労は少なく、参加者の 81% が SIAgent を好みました。top-1 の意図正解率は GLM-4 で 83.3%、GPT-4o で 72.2%、GPT-3.5 で 46.3% で、視線に手を加えると top-1 正解率は 30.2% から 58.3% に上がりました。

*しないこと。* 言語による命令も GUI の知覚もなく、操作はあらかじめ定義されたシーン操作です。**重なり：「エージェントがユーザーのために VR を操作する」について大きい。** エージェントがユーザーに代わって VR コンテンツに対して行動する、最も明確な公開事例です。

### 2.5 Put-That-There 再訪：言語と直示からウィンドウ操作へ

**Revisiting put-that-there, context aware window interactions via LLMs**（Riccardo Bovo et al., OpenAlex によれば ISMAR 2025 Adjunct；arXiv 2511.02378）は、Bolt による 1980 年の "put that there"（それをそこに置け）をヘッドセット向けに刷新したものです。

*手法。* ファインチューニングなしでプロンプトのみを与えた GPT-4 が、ウィンドウのメタデータ（id、サイズ、位置）、Quest Scene API から得た部屋の平面（約 10 の自動クラスと約 30 の手動アノテーションのクラス）、ユーザーの発話、ポインティングのホバーイベント、頭の向きを受け取ります。出力は JSON の三つ組 `["place"|"remove", windowId, surface]` です。明示的なコマンド（"put Maps on the coffee table"（Maps をコーヒーテーブルに置いて））、直示的なコマンド（"put that there"（それをそこに置いて））、ゴールレベルのコマンド（"I need to send a message"（メッセージを送りたい）で、適切なアプリを開いて配置する）を、一対多の行動も含めて扱います。

*しないこと。* 定量的な結果はまだありません（ユーザースタディが計画されています）。GUI を知覚するのではなくウィンドウマネージャのメタデータを通じて行動し、ウィンドウを配置するだけでアプリ内部の操作は行いません。**重なり：意図と XR ウィンドウ層の操作について大きい。** 知覚の代わりに特権的なメタデータを用いた、「LLM がマルチモーダルな意図から XR UI に対して行動する」ことの最もきれいな定式化です。

### 2.6 DuoZone：評価済みの混合主導（mixed-initiative）ウィンドウレイアウト

**DuoZone: A User-Centric, LLM-Guided Mixed-Initiative XR Window Management System**（Jing Qian et al., IEEE TVCG、OpenAlex によれば 2026 年 11 月 3 日にオンライン公開；arXiv 2511.15676）は、言語が XR UI を動かすシステムの中で最もよく評価されたものです。

*手法。* GPT-4.1 サーバーと組み合わせた Apple Vision Pro 上で、ユーザーは空間内にゾーンを定義し、ゴールを述べます。LLM は各アプリがゴールにどの程度関連するかをスコア付けし、コスト行列（ポインティング距離、頭の回転、手の移動）を用いてアプリをゾーンに割り当てます。LLM だけではウィンドウのサイズをランダムに変えてしまったため、LLM ではない最適化器がウィンドウのサイズを決めます。何かが変わる前にユーザーが確認し、1 回の要求には約 4 s かかります。

*結果。* N=16 の専門職を対象とした、ネイティブの visionOS ウィンドウ管理との参加者内比較です。レイアウトの一致作業は 34.5% 速く、ワークスペースの構築には 168.3 s（対して 218.1 s）かかり、NASA-TLX のワークロードは報告された二つの比較のどちらでも低くなりました（33.3 対 47.7、22.4 対 34.2）。参加者はアプリ推薦の 90.3%、サイズ決定の 82.8%、順序決定の 76.5% を受け入れました。満足度には差がありませんでした。

*しないこと。* ウィンドウ層のみであり、GUI の知覚の代わりにアプリのメタデータを用い、すべての変更をユーザーが確認します。**重なり：混合主導（mixed initiative）のもとでの XR ウィンドウ層の操作について大きい。** また、その確認してから適用する（confirm-then-apply）設計は、共有制御（shared control）のモデルとなります。

二つの教訓が転用できます。第一に、**構造が実行を信頼できるものにします**。シーングラフにアクセスできる XRintTest は、ランダム入力が 8% のところで 93% のカバレッジに達します。第二に、**サードパーティのアプリは閉じています**。AUTOVR は、バイナリを計装することによってのみ市販の Quest アプリを操作できましたが、これはエンドユーザー向けのエージェントにはできないことです。XRBench3D は実行可能な XR インタラクションのベンチマークに最も近いものでもありますが、命令もピクセルの知覚もありません。

### 2.8 製品：Galaxy XR 上の Gemini、Meta XR Operator、visionOS 上の Siri

**Samsung Galaxy XR 上の Gemini。** 発表記事（blog.google, 2025 年 10 月）は、Gemini Live があなたの見ているものやしていることを理解し、"take action on your behalf across your apps"（アプリをまたいであなたの代わりに操作を行う）ことができ、"Hey Google, organize these windows"（OK Google、これらのウィンドウを整理して）で開いているウィンドウを並べると主張しています。技術報告、ベンチマーク、仕組みはいずれも公開されていません。Android XR の開発者向けガイダンスは、アプリ内の制御について別の方向を示しています。"To let your users navigate your app using their voice, use the Gemini live API along with function calling"（ユーザーが音声でアプリを操作できるようにするには、Gemini live API を関数呼び出しと組み合わせて使ってください）とあり、つまり各アプリが関数呼び出しを通じて独自の音声制御を構築するということです。カバー範囲と成功率が非公開であるため、Galaxy XR 上の Gemini は、このアイデアが時宜にかなっていることを示す最も強い**産業界のシグナル**ですが、問題を解決した先行技術として評価することはできません。製品を論文と並べて*主張された*範囲で順位付けすれば、最上位に位置するでしょう。

**Meta XR Operator。** 2026 年 8 月 18 日に "an OpenXR API layer, now available as an experimental component in the Meta XR SDK (v205)"（Meta XR SDK (v205) で実験的コンポーネントとして利用可能になった OpenXR API レイヤー）として発表されました。ランタイムの MCP（Model Context Protocol）サーバーがアプリのプロセス内で動作し、プロキシがアプリの再起動をまたいでエージェントの接続を維持します。これを通じてエージェントは、ブログの言葉によれば、"Screenshot the running app as rendered in Meta XR Simulator"（Meta XR Simulator でレンダリングされた実行中のアプリのスクリーンショットを撮る）、"Read room geometry (walls, floors, furniture)"（部屋のジオメトリ（壁、床、家具）を読み取る）、"Read the Unity scene hierarchy, check components"（Unity のシーン階層を読み取り、コンポーネントを確認する）、"Press buttons, move thumbsticks, pull triggers, point and aim"（ボタンを押し、サムスティックを動かし、トリガーを引き、指し示して狙う）、"Press buttons, work through menus, and navigate multi-step flows autonomously"（ボタンを押し、メニューを操作し、複数ステップのフローを自律的に進む）ことができます。ブログは制限も挙げています。エージェントは "uses a single aim-ray per hand with no per-finger data"（片手につき一本のエイムレイを使い、指ごとのデータはない）、"has no access to audio"（音声にアクセスできない）、"works from screenshots only and cannot watch animations play out"（スクリーンショットのみで動作し、アニメーションが再生される様子を見ることはできない）、"operates too slowly for real-time interaction"（リアルタイムのインタラクションには遅すぎる）とされています。その目的は、コーディングエージェントを使う開発者のためにビルド・テスト・検証のループを閉じることです。このレイヤーを組み込んだアプリでのみ動作するため、システムシェルや他のアプリは操作できず、公開された評価もありません。**これは、汎用の LLM エージェントが VR アプリを見て、コントローラ入力でその UI を操作できる最初のベンダー提供のチャネルです**。そして、明記されている制限（手の関節表現、リアルタイムの速度、動くコンテンツ）は、まさに 3D GUI エージェントの研究課題です。

**visionOS 27 上の Siri AI。** Apple のニュースルーム（2026 年 6 月 8 日）によれば、Siri は "answer questions related to the content on a user's screen"（ユーザーの画面上のコンテンツに関する質問に答える）ことができ、"get things done across apps with even more systemwide app actions"（さらに多くのシステム全体のアプリアクションで、アプリをまたいで物事を片付ける）ことができます。WWDC26 の App Intents に関するセッションで説明されている仕組みは意味的なもので、アプリは App Intents、App Entities、ビューのアノテーションを通じてエンティティと行動を宣言します。Apple は、アプリがこれらの API を採用しない限り、"Siri has an understanding of text on screen, but it's limited to exactly what's in the pixels. For example, Siri can't act on the tracks shown"（Siri は画面上のテキストを理解するが、それはピクセルに含まれるものそのものに限られる。例えば、Siri は表示されているトラックに対して行動できない）と明言しています。Apple の設計は、ピクセルベースの GUI エージェントの**対極**にあります。アシスタントは開発者が公開したものに対してのみ行動します。これはオプトインしたアプリをカバーし、インターフェースの残りの部分はユーザーに委ねられます。

$$

## 3. プラットフォームとツール：エージェントは何を観測・制御できるか

3D GUI エージェントには、デバイスへの二つのチャネルが必要です。**観測**（何を見られるか）と**行動**（何ができるか）です。現在の XR プラットフォームでは、それぞれをどれだけ得られるかは主に**エージェントが誰であるか**によって決まります。

### 3.1 エージェントは誰か：四つのアクセスレベル

| レベル | 例 | 観測 | 行動 | 状況（2026 年 11 月） |
| --- | --- | --- | --- | --- |
| L0：自分のアプリ内のテストハーネス | Meta XR Operator、IWSDK MCP ツール、Jetpack `compose-testing`、Unity XRI シミュレータ | ピクセル、シーングラフ、ECS の状態 | デバイスレベルの入力、コンポーネントへの書き込み | 存在する、実験的 |
| L1：自分のアプリ内のエージェント | visionOS アプリ内のオンデバイスのプランナー；EmBARDiment | 自アプリの UI と許可されたセンサー | 自アプリの UI | 現在でも実現可能 |
| L2：OS アシスタント | Siri AI、Galaxy XR 上の Gemini Live、Meta VR Glasses の Meta AI エージェント | システム全体 | 意味的な行動；ベンダーのみ | ベンダーのみ |
| L3：サードパーティのアプリ横断エージェント | "AppAgent for headsets"（ヘッドセット向けの AppAgent） | Android XR 上の 2D パネルのアクセシビリティツリー（未検証）；visionOS ではなし | アクセシビリティのジェスチャー（Android、ポリシーで制限） | デバイス上では不可；エミュレータと WebXR では可能 |

本コラムの研究課題は **L3** の問題（他者のアプリを操作する）ですが、プラットフォームが開いているのは L0-L2 だけです。実践的な結論は、自分で制御できる環境、すなわち WebXR、Unity、Android XR エミュレータで L3 の問題を研究することです。

### 3.2 Apple visionOS

- **観測。** シミュレータのスクリーンショットは容易です。デバイス上では、カメラフレームと画面キャプチャ内のパススルーには、ライセンスファイルを伴う**エンタープライズ向けエンタイトルメント（enterprise entitlements）**が必要で、これは組織のみが、非公開配布のためにのみ利用できます。ブロードキャストは毎回ユーザーが開始し、どのビューも `contentCaptureProtected` によってキャプチャを拒否できます。アプリには、ユーザーがどこを見ているかは一切知らされません。視線はシステム内部にとどまります。ARKit の手と世界のデータには Full Space が必要なため、エージェントアプリが他のアプリを見ることはできません。
- **構造。** SwiftUI のウィンドウは標準的なアクセシビリティ要素を公開しますが、RealityKit の 3D コンテンツは、開発者が `AccessibilityComponent`（ラベル、値、トレイト、システムアクションとカスタムアクション、カスタムローター）を追加しない限り VoiceOver から見えません。このコンポーネントは、「3D アクセシビリティノード」が何を含むべきかについての、現存する最良のテンプレートです。
- **行動。** サードパーティによる入力注入はできません。Apple の XCUIAutomation の概要には "UI testing isn't available to apps you build using the visionOS SDK"（visionOS SDK で構築したアプリでは UI テストは利用できない）とあります。支援モード（Pointer Control、Dwell Control、Switch Control、Voice Control）は、UI が一本のレイと滞留（dwell）だけで操作できることを証明していますが、サードパーティがそれらをプログラムから動かすことはできません。
- **意味的な経路。** App Intents と App Schemas により、アプリは Siri 向けの行動を宣言できます。Foundation Models フレームワークは、ツール呼び出しに対応した約 3B パラメータ（2 ビット量子化）のオンデバイスモデルを提供し、L1 のアプリ内エージェントに使えます。

visionOS は最も洗練された 3D UI を持ちながら、自動化研究にとっては最も弱いプラットフォームです。ユーザースタディと意味的な経路に使うのが最適です。

### 3.3 Android XR

- **エミュレータ。** Android XR エミュレータ（ヘッドセット、有線グラス、AI グラス）は、Jetpack SceneCore および ARCore for Jetpack XR とともに 2026 年 11 月 6 日に安定版になりました。ヘッドセットエミュレータでは、手は "automatically direct their raycasts toward your mouse pointer position"（レイキャストを自動的にマウスポインタの位置へ向ける）とされ、ドラッグでピンチが行われ、視線はマウスに追従し、視点は WASD/QE で移動します。存在するのは右手のピンチだけです。"Left-hand controls and alternative gestures, such as grabbing and poking, aren't currently supported."（左手の操作や、つかむ、つつくといった別のジェスチャーは、現在サポートされていません。）
- **構造。** Compose for XR は、あらゆるプラットフォームの中で空間 UI の最も明確な公式の構造を文書化しています。コンテナ（空間パネル、オービター）からなる 3D のサブスペースのセマンティクスツリーと、各パネル内部の個別の 2D セマンティクスツリーで、後者は "operate as distinct hierarchies"（別個の階層として機能する）とされています。エージェントの観測はこの 2 段階の構造を反映すべきです。すなわち、姿勢を持つパネルとボリュームのノードがあり、それぞれが 2D ウィジェットツリーを保持します。プロセス内のテスト API（`compose-testing`、`scenecore-testing`）は、自分のアプリについてこれを公開します。
- **行動。** 2D の Android では、オープンな GUI エージェントは `AccessibilityNodeInfo` ツリーを読み取り、`AccessibilityService.performAction` と `dispatchGesture` で行動します。これが 3D 空間に配置されたパネルで機能するかどうか、そしてジェスチャーの座標がパネル空間にどう対応づけられるかは**文書化されていません**。エミュレータで 1 日実験すれば決着がつくでしょう。Android の意味的な行動経路である AppFunctions は特権的な呼び出し元パーミッションを必要とするため、実際にはシステムアシスタントのためのものです。2026 年 2 月 25 日にスマートフォン（Galaxy S26 と一部の Pixel 10）でプレビュー公開された Gemini の UI 自動化は、再利用可能な安全設計を提供しています。ライブビュー、任意の時点での手動による引き継ぎ、そして機密性の高い行動の前の警告です。この発表は XR に言及していません。

2D の Android アプリは変更なしでパネルとして動作するため、Android XR エミュレータは、AndroidWorld 形式のタスクを用いて「2D GUI エージェントは 3D に移されても生き残るか」を問うのに自然な場所です。

### 3.4 Meta Horizon OS（Quest）

- **観測。** MediaProjection は、同意ダイアログの後に "the user's whole view or a single panel"（ユーザーの視界全体または単一のパネル）をキャプチャします。没入型アプリは OpenXR を通じてキャプチャをブロックできます。Passthrough Camera API は `HEADSET_CAMERA` パーミッションによりカメラフレーム（Quest 3/3S で最大 1728x1728、60 Hz、20-40 ms のレイテンシ）を提供します。カメラフレームは Device User Data として扱われ、監視や人物の特定は禁止されています。カメラフレームに映るのは部屋であり、仮想 UI ではありません。MRUK はラベル付きのアンカー（TABLE、COUCH、DOOR_FRAME）を持つ部屋モデルを提供します。
- **構造。** Horizon OS の視線ベースの「Look and Pinch」入力は "infers interactable elements from your app's view hierarchy and accessibility information"（アプリのビュー階層とアクセシビリティ情報から操作可能な要素を推定する）とされています。OS 自身がアクセシビリティのメタデータを用いて 2D パネル上で視線を接地しているわけで、これはアクセシビリティツリーが 3D 入力のための実用的な接地基盤であることの直接的な証拠です。しかし `BIND_ACCESSIBILITY_SERVICE` は Meta の禁止パーミッションのリストに含まれているため、AppAgent 形式のアクセシビリティサービスによるエージェントはストアで配布できません。
- **行動。** それを組み込んだアプリには Meta XR Operator（2.8 節）。ヘッドセットなしで実行するには、合成された部屋、キーボード／マウス／ゲームパッド入力、セッションの記録と再生を備えた OpenXR ランタイムである Meta XR Simulator。無人実行のために境界（boundary）とスリープを無効にするスクリプト可能なテストサービス（これは、そのような制御を装着中のデバイス上の自律エージェントに決して公開してはならないことも示しています）。

### 3.5 OpenXR、WebXR、エンジン

- **OpenXR API レイヤー**はアプリとランタイムの間に位置し、姿勢やボタンの状態を記録したり書き換えたりできます（OpenXR-Toolkit の手からコントローラへの再マッピングは、変更されていないアプリの下での入力の書き換えが機能することを示しています）。Meta XR Operator 自体もそのようなレイヤーです。オープンソースのランタイムである **Monado** には、キーボードで操作する HMD と、TCP 経由で姿勢を受け付けるリモートドライバがあります。これは PC 上の任意のサードパーティ OpenXR アプリで機能する唯一のチャネルですが、OpenXR には UI という概念がないため、構造はピクセルから得なければなりません。
- **WebXR** は最も開かれた経路です。**IWER**（Meta、MIT ライセンス）は `navigator.xr` を、スクリプトで制御可能なヘッドセット、コントローラ、手に置き換えます。three.js 上の Meta の ECS フレームワークである **IWSDK** は、32 のツールを持つ MCP サーバーを実行します。ピクセル（`capture_canvas`、`browser_screenshot`）、構造（`get_scene_hierarchy`、`ecs_snapshot`、`ecs_diff`、`ui_inspect`）、入力（`set_transform`、`look_at`、`select`、`set_input_mode`）、時間制御（`ecs_pause`、`ecs_step`）で、管理された Playwright ブラウザを用いるヘッドレスの「agent」モードで動作します。以前の Immersive Web Emulator 拡張機能は 2026 年 10 月 1 日にアーカイブされました。新しい作業は IWER/IWSDK の上に構築すべきです。
- **Unity**（XR Interaction Simulator 付きの XR Interaction Toolkit 3.5、Input System のテストフィクスチャ）は、市販の XR UI の大半が構築される場所であり、XRintTest のインタラクショングラフとオラクルが存在する場所でもあります。**Godot** には Control ノード向けの実験的な AccessKit スクリーンリーダー対応があり、**Unreal** には実験的な Slate アクセシビリティがありますが、どちらにも特筆すべき XR テストフレームワークはありません。

### 3.6 プライバシー、セキュリティ、ストアの規則

ユーザーの自宅で、ユーザーが見ているものを見るエージェントは、各プラットフォームの最も厳しい規則を引き継ぎ、さらに 2D エージェントにはないリスクを加えます。

- **周囲の人々と部屋。** カメラフレームには他の人が映り込みます。Meta はそこから人物を特定することを禁じています。1,036 名の回答者によるクラウドソーシング調査では、位置データが、XR の対話エージェントが使いうる最も機密性の高いデータと評価されました（Bozkir and Kasneci, arXiv 2025）。
- **生体情報。** 頭と手の動きは人物を特定します。Nair et al.（USENIX Security 2023）は、100 s の動きから 55,541 名のユーザーの 94.33% を特定しました。エージェントのトレースは個人データです。
- **物理的な安全。** ウィンドウを動かすと現実の障害物が隠れることがあり、境界やパススルーのレベルを変えると危険が見えなくなることがあります。
- **欺瞞的な UI とインジェクション。** MetaScanner（Lee et al., arXiv の記載によれば Computers & Security に採録）は、ソーシャル VR における四つの欺瞞的 UI（deceptive UI）攻撃を実証しており、クリックするエージェントにとって直接的な脅威です。部屋の中や他のアプリのパネルに見えるテキストは、2D エージェントではあまり直面しないプロンプトインジェクション（prompt injection）のチャネルです（推論であり、XR に特化した研究は見つかりませんでした）。
- **過度の依存。** 32 名の参加者による研究で、AI の出力を AR の X 線可視化で示すと、2D のミニマップよりも不適切な依存（主に過度の依存）が多く生じました（Liu et al., CHI 2026）。現実的な現場（in-situ）での出力には説得力があります。
- **取り消せない行動**には確認が必要です。Gemini の機密性の高いタスクの前の警告や、DuoZone の確認してから適用する設計のようにです。

### 3.7 実現可能性マトリクスと三つのプロトタイプ構成

マトリクスは、プラットフォームごとに、エージェントがピクセルと UI 構造を観測できるか、入力を注入できるか、自動化フレームワークを使えるか、エミュレータでデータを収集できるかをまとめたものです。

{% include blog_figure.liquid path="assets/img/blog/3d-gui-agent/04-feasibility.svg" localized="true" caption="3D GUI エージェントを構築・テストするための実現可能性マトリクス（2026 年 11 月時点の状況）。緑：機能し、文書化されている。ベージュ：部分的、制限付き、または自分のアプリのみ。赤：利用できない。灰色：文書化されていない。すべて緑なのは IWER/IWSDK を用いた WebXR の行だけですが、これは OS シェルのない合成アプリが対象です。visionOS が最も閉じており、Android XR と Horizon OS はその中間に位置し、それぞれエミュレータまたはシミュレータと自分のアプリの構造を備えています。" %}

本記事の背後にあるプラットフォームの調査資料（dossier）は、最初のプロトタイプのために三つの構成を、次の順序で推奨しています。

1. **IWER/IWSDK 上の WebXR を Playwright で駆動。** 3D GUI を持つ 10-20 本の小さな WebXR アプリ（設定メニュー、ウィンドウマネージャ、モデルビューア、メディアプレーヤー、キーボード付きのフォーム）。テスト対象のエージェントは目ごとの RGB のみを見て（オプションで Set-of-Mark のオーバーレイ付き）、デバイスレベルの入力（頭部姿勢、コントローラまたは手のレイ、選択またはピンチ）を通じて行動します。チェッカーは成功判定のために特権的な ECS アクセスを保持します。オープン、無料、決定的、ヘッドレスで、正確な正解データがありますが、アプリは合成であり、システム UI はありません。
2. **AccessibilityService を用いた Android XR エミュレータ。** AndroidWorld 形式のタスクを移植します。本物の Android、パネルとして動く本物のアプリ、システム UI があり、2D の数値と直接比較できます。しかし空間的なアクセシビリティは文書化されておらず、エミュレータには右手のピンチしかありません。
3. **XR Interaction Simulator を用いた Unity XRI シーン、オプションで Meta XR Simulator と Operator。** XRBench3D のつかむ、ソケット、操作のタスク、オラクルとしての XRI イベント、記録された人間のデモンストレーション。現実的ですが重く、Operator は実験的で遅いです。

どの構成であれ、エピソードログが後で何を学べるかを決めます。既存のツールから組み立てた妥当なスキーマは、単一の単調増加クロック上で、ティックまたはイベントごとに 1 行の JSON を記録します。

| フィールド | 内容 | 似たものを記録する既存ツール |
| --- | --- | --- |
| `head_pose`、`hands`、`controllers` | 位置とクォータニオン；26 個の OpenXR 手関節、またはボタンと軸 | BOXRR-23 XROR フォーマット、Meta XR Simulator の VRS キャプチャ、IWER `ActionRecorder` |
| `gaze` | 原点、方向、ヒットしたエンティティ（許可されている場合のみ） | GazeBaseVR、Aria |
| `ui_tree` | エンティティ id、ロール、ラベル、値、ワールド座標の姿勢とボックス、可視、操作可能、親 | IWSDK `ecs_snapshot`/`ui_inspect`、Jetpack のサブスペースセマンティクス、RealityKit `AccessibilityComponent` |
| `action` | 生のデバイス行動（姿勢の差分、選択、ピンチ）と意味的な行動（動詞＋対象 id） | GenXR-Bench のアクター API、IWSDK MCP ツール、Meta XR Operator |
| `frames` | 目ごとの RGB、深度、エンティティ id マスク、Set-of-Mark オーバーレイ、内部パラメータと外部パラメータ | GenXR-Bench のスクリーンショット、Orienter のフレーム |
| `outcome` | チェッカーの結果、理由、最終状態のハッシュ | OSWorld のスクリプト、AndroidWorld の init/check/teardown |

内部パラメータと外部パラメータを保存することが重要なのは、画像上のクリックを 3D のレイに戻す必要があるからです。ちょっとした幾何学が、XR でのポインティングがなぜ難しいかを示します。距離 $d$ にある幅 $s$ の対象は、次の視角をなします。

$$
\theta = 2\arctan\frac{s}{2d},
$$

したがって、1.5 m 先のパネル上の 2 cm のボタンは約 0.76° になります。スマートフォンのスクリーンショットで数ピクセルずれる 2D の接地モデルは、ヘッドセットのフレームでは 10 分の数度ずれることになり、それだけで対象を外すのに十分です。

## 4. XR インターフェースのためのデータセットとベンチマーク、そしてデータのギャップ

2D GUI エージェントは、人間のデモンストレーションのデータセットの上に構築されました。AITW（715,142 エピソード）、AndroidControl（833 アプリにわたる 15,283 のデモンストレーション）、Mind2Web（137 の Web サイト上の 2,000 以上のタスク）、そして AndroidWorld（116 タスク）や OSWorld（369 タスク）のような実行可能なベンチマークです。XR にはこれらに相当するものがありません。存在するのは次のものです。

| データセット | 内容 | 規模 | 発表先 |
| --- | --- | --- | --- |
| Orienter IGE セット | 操作可能要素のボックス付きの、右目の Steam VR スクリーンショット | 1,552 画像、100 アプリ、4,470 ボックス、766 カテゴリ | FSE 2026 |
| DISCOVR（VRSight） | menu、button、ui-text、HUD を含む 30 クラスのソーシャル VR フレーム | 17,691 画像、17 アプリ、約 92K インスタンス | UIST 2025 |
| StereoID スクリーンショット | VR アプリのステレオスクリーンショット | 171K スクリーンショット、288 アプリ | FSE 2024 |
| GUI-World（XR サブセット） | QA 付きの画面録画 GUI 動画 | 393 本の XR 動画、3,930 QA（全 12,379 本の動画のうち） | ICLR 2025 |
| ComboBench | 意味的な行動と記録されたコントローラ／HMD の系列、テキストのみ | 262 シナリオ | arXiv 2025 |
| XRBench3D | 実行可能なインタラクションを持つ Unity シーン | 10 シーン、456 インタラクション | Automated Software Engineering 2026 |
| MineXR | ヘッドセット上で作成された個人化 XR レイアウト | 31 名の参加者、695 ウィジェット、109 レイアウト | CHI 2024 |
| GenXR-Bench | スクリプトと VLM のアクターを伴う WebXR 開発タスク | 112 タスク | arXiv 2026 |

VRSight の DISCOVR セットでは、小さな YOLOv8n 検出器が 67.3 mAP50、46.3 mAP50-95 に達します（menu 62.2、button 45.9）。したがって、ピクセルからの VR UI 要素の検出は可能ですが、解決にはほど遠い状況です。行動データセット（behaviour datasets）は豊富にあります（105,852 名のユーザーによる 4.7M のモーション記録を持つ BOXRR-23、250 Hz で記録された 407 名の参加者の GazeBaseVR、Aria と Quest 3 による手とオブジェクトの HOT3D）が、UI のラベルは含まれていません。

{% include blog_figure.liquid path="assets/img/blog/3d-gui-agent/04-datasets.svg" localized="true" caption="XR データセット（紫）と、それらが匹敵すべき 2D GUI エージェントのデータセット（灰色）。左：対数スケールでの規模（単位は異なります）。右：各セットが含むもの。2D のセットはフレーム、UI ラベル、自然言語のタスク、行動を組み合わせていますが、XR のセットはどれもこのうち最大二つしか持ちません。例外は GenXR-Bench で、そのタスクは開発者向けタスクであり、行動はスクリプト化されたテストアクター（リング）によるものです。" %}

**XR GUI 上の命令から行動への軌跡（instruction-to-action trajectories）の公開データセットは存在しません**。AndroidControl、AITW、Mind2Web、OSWorld の XR 版はないのです。最も近い基盤は、GUI-World の XR 動画（タスクではなく QA）、XRBench3D（命令のないインタラクション）、ComboBench（スクリーンショットのないテキスト）、そして Orienter と DISCOVR のスクリーンショット（行動のないボックス）です。アーキテクチャの面で最も近いのは GenXR-Bench のハーネスです。その VLM アクターは、安定した id を持つ刈り込まれたオブジェクトツリーと Set-of-Mark のスクリーンショットを観測し、ビューア、手、ターゲティング、選択の API（`navigateTo`、`setHandPose`、`pointTo`、`rayClick`、...）を通じて行動し、プログラムによるアサーションでチェックされます。ただし、評価しているのは GUI エージェントではなくコーディングエージェントです。正確なエンティティラベルを伴う合成レンダリング（WebXR、Unity、Jetpack のテスト API）は、2D において Jedi の UI 合成がそうであったように、接地データへのスケーラブルな経路です。

## 5. ギャップ

### 5.1 まだどの研究も行っていないこと

本コラムの背後にある検索（arXiv、OpenAlex、ACM DL、IEEE Xplore、会議録、公式の製品ページ、2026 年 11 月 24 日まで）を経ても、**次のようなエージェントを提示する査読付き論文もプレプリントも見つかりませんでした**。

- ヘッドセットのユーザーから**自然言語**（または音声に視線とポインティングを加えたもの）による要求を受け取る。
- **既存の XR アプリの 3D GUI**（奥行き方向に配置され、一部が遮蔽されていたり視野外にあったりするウィンドウ、ボリューム、メニュー、ウィジェット）を、レンダリングされた視界および／または UI 構造から**知覚する**。
- XR 入力（レイとピンチ、コントローラ、視線、ウィンドウマネージャ）を用いて、**アプリをまたぐ複数ステップの操作を計画・実行する**。
- 命令とアプリの集合に対するタスク成功率をもって、**GUI エージェントとして評価されている**。

また、**XR GUI 上の命令から行動への軌跡のベンチマークやデータセット**も見つかりませんでした。本コラムの調査における二つの独立した検索パスがこの結論に達しており、Guo et al. による 2026 年のソフトウェア工学のサーベイも、VR GUI 探索のための LLM エージェントを未解決として挙げています。通常の注意書きが当てはまります。検索で証拠が見つからないことは不在の証明ではなく、産業界のシステム（とりわけ Galaxy XR 上の Gemini）は、公表することなくすでにその一部を行っているかもしれません。

{% include blog_figure.liquid path="assets/img/blog/3d-gui-agent/04-gap.svg" localized="true" caption="三つの重なり合う集合として見たギャップ：既存の XR アプリの 3D UI を知覚する研究（青）、自然言語によるユーザーの意図を理解する研究（橙）、XR UI を操作する研究（緑）。二つずつの重なりはそれぞれ埋まっています（NavAI：ピクセルと言語、ただし移動。Meta XR Operator：ピクセルと操作、開発者のテスト向け。Put-That-There と DuoZone：言語とウィンドウ操作、メタデータ経由）。公開された記録の中では中央は空です。Galaxy XR 上の Gemini はそこにあると主張していますが、その仕組みと評価は非公開です。" %}

### 5.2 このアイデアが加えるもの、そして重なりを認めるべき点

**部品ごとに存在するもの：** ピクセルからの XR GUI 要素の知覚（Orienter、DISCOVR）、実行を伴わない言語からコントローラ行動計画への変換（ComboBench）、言語とスクリーンショットから VR での移動への閉ループ（NavAI）、視線と手からの意図に基づく VR 操作の実行（SIAgent）、メタデータを通じた言語と直示からのウィンドウ配置（Put-That-There；確認付きの DuoZone）、意図を伴わない 3D インタラクションの自動実行（VRExplorer、XRintTest、AUTOVR）、エージェントが VR アプリを見て操作するためのインフラ（Meta XR Operator、IWSDK、XARP Tools）、そしてアプリ横断の行動とウィンドウ配置の詳細が非公開の出荷済みアシスタント（Galaxy XR 上の Gemini）。

**3D GUI エージェントのアイデアが加えるもの：**

1. これらの部品を、既存の XR アプリの GUI 上で評価された一つの知覚・理解・操作のループへと**統合**すること。
2. どの部品も扱っていない **3D 特有**の部分：奥行き、遮蔽、視野外の UI；ウィンドウとボリュームの 6-DoF 操作；平面パネルと 3D コンテンツの混合（Embodied Web Agents の失敗モード）；そして命令の一部としての視線と手による直示。
3. 同じエージェントが、行動する代わりに空間的な手がかりを用いて UI の操作方法をユーザーに示す**案内モード**。
4. 操作の複雑さが 3D 端末の普及を妨げているという**動機**。どの研究もこれを自らの問題として位置づけていません。
5. **ベンチマークと軌跡データ**。

**本コラムが重なりを認める点。** Orienter の arXiv 版のタイトルはすでに、XR アプリのための "Vision-Based Spatial Intelligent Agent"（視覚ベースの空間知能エージェント）について語っています。Put-That-There と DuoZone はすでに、LLM が言語から XR ウィンドウ層に対して行動することを可能にしています。Google は、Galaxy XR 上の Gemini がアプリをまたいで行動し、ウィンドウを配置すると公に主張しています。Meta はエージェントが VR のメニューを操作できるツールを提供しています。したがって、このアイデアは**時宜にかなっており、部分的には先取りされています**。その新規性は、「XR におけるエージェント」一般にあるのではなく、一般的な 3D GUI のための、統合され、評価され、ユーザーの意図によって駆動されるエージェント、3D 特有の知覚と行動、そしてベンチマークにあります。

### 5.3 未解決問題

1. **タスクベンチマーク。** 固定されたアプリ、自然言語によるユーザータスク、デバイスレベルの行動、視点の変動、状態ベースのチェッカー。XRBench3D、GenXR-Bench のハーネス、AndroidWorld の init/check/teardown がテンプレートです。
2. **UI の 3D 知覚。** ゼロショットの操作可能要素 F1 は IoU 0.75 で 50% 未満であり、より厳しい IoU では崩れます。ステレオ、深度、頭部姿勢を用いて UI 要素を 3D で位置特定する研究はありません。
3. **6-DoF の行動接地。** LLM が正確なコントローラ系列を生成できるのは 11.7% にとどまります。タップ／スワイプ／入力に相当する標準的な XR の行動空間はありません。候補：対象 id と動詞、レイとピンチ、または 6-DoF の姿勢の差分。
4. **レイテンシ。** 公開されている XR エージェントは 1 ターンに 4-49 s かかります。インタラクティブな利用で許容されるのは約 4 s、リアルタイムの 3D 制御には 0.1-0.25 s が必要です。階層的な制御（遅いプランナーと速いローカルなポインティング）、経験の再利用（PastForward はオンデバイスのステップが 1.63-2.36 倍速くなると報告）、身体化された待機フィードバック（Arora et al. は VR ではスピナーよりジェスチャーのほうがよいことを見いだしました）が手段となります。
5. **視野外の記憶。** ユーザーの背後にあるウィンドウや遮蔽されたボリュームには空間記憶が必要ですが、VSI-Bench は MLLM がこれを苦手とすることを示しています。
6. **API 行動と GUI 行動。** Apple と Google はアシスタントの行動をアプリインテントと関数呼び出しを通じて実行しており、カバーするのはオプトインしたアプリのみです。GUI 操作はすべてをカバーしますが脆弱です。CAD エージェントで役立つハイブリッドな行動空間は、XR では未開拓です。
7. **アクセス。** デバイス上のサードパーティアプリは閉じています。3D アクセシビリティツリー（RealityKit の `AccessibilityComponent`、Jetpack のサブスペースセマンティクス）は十分に活用されておらず、W3C の XR Accessibility User Requirements の精神に沿った、可搬な「3D アクセシビリティノード」のスキーマは存在しません。
8. **空間における共有制御。** エージェントがこれから行うことをどう示すか（ゴーストハンド、ハイライト、プレビュー）、いつ尋ねるか、どう制御を返すかは、案内とウィンドウレイアウトについては研究されています（DuoZone、Sensible Agent、AgentHands）が、GUI 操作については研究されていません。Vision Pro の研究（Zhang et al., arXiv 2026, n=24）は、完全に自律的なエージェントのプレイがワークロードを最小化する一方で、挑戦、自律性、没入感、楽しさを低下させることを見いだしました。「代わりにやって」がいつもユーザーの望むことではないのです。
9. **安全性とプライバシー。** 欺瞞的な UI、部屋からのプロンプトインジェクション、周囲の人々、生体情報のトレース、コンテンツを動かすことによる物理的な副作用。
10. **データ。** UI のアノテーションと行動を伴う、人間の XR GUI 使用の記録はありません。

本コラムがこれらの問題にどう取り組むかは[研究計画]({{ '/blog/2026/3d-gui-agent-05-research-plan/' | relative_url }})の主題であり、動機と研究課題は[研究ビジョン]({{ '/blog/2026/3d-gui-agent-01-research-vision/' | relative_url }})にあります。

## 演習

1. 第 0 節の評価基準を、ヒートマップにない研究、例えば LLMER、AssistVR、Guided Reality に適用してください。どの性質が最も評価しにくく、それはなぜでしょうか。

   <details markdown="1"><summary>ヒント</summary>

   システムの出力から考え始めてください。世界を変更するコードや JSON（LLMER）、音声とレイキャストによる編集（AssistVR）、または案内のオーバーレイ（Guided Reality）です。通常は「操作（operate）」の列が難しくなります。世界の編集、インタラクタブルの操作、案内の間の境界は定義の問題だからです。本記事がそうしたように、どの規則を用いたかを書き留めてください。
   </details>

2. ヘッドセットのユーザーが 60°/s で頭を回し、エージェントの 1 ターンには 4 s かかるとします。スクリーンショットから行動までの間に、視界はどれだけ回転するでしょうか。これは画像座標をクリックするエージェントにとって何を意味し、代わりに実行器（executor）に何を送るべきでしょうか。

   <details markdown="1"><summary>ヒント</summary>

   240° です。対象はもうユーザーの背後にあるかもしれません。古い画像上の座標は意味を持ちません。頭の動きに左右されない対象、例えばエンティティ id や、部屋に固定されたワールド空間のレイまたは点を送り、実行時に速いローカルなコントローラに狙いを付け直させてください（2.9 節）。
   </details>

3. $\theta = 2\arctan(s/2d)$ を用いて、0.5 m、1.5 m、3 m の距離にある 2 cm のボタンの視角を計算してください。960 ピクセルのヘッドセットのフレームが水平方向に約 100° をカバーするとき、それぞれの場合でボタンは何ピクセル幅になるでしょうか。

   <details markdown="1"><summary>ヒント</summary>

   約 2.29°、0.76°、0.38° で、1 度あたり 9.6 ピクセルとするとそれぞれ約 22、7、4 ピクセルです。3 m ではボタンは 2D の接地モデルが信頼できなくなる大きさに近づき（大きなスクリーンショット中の小さな対象を扱う ScreenSpot-Pro と比べてください）、2 ピクセルの誤差がボタンの半分に相当します。
   </details>

4. 3.7 節の WebXR 構成上で、3D GUI エージェントのベンチマーク用のタスクを一つ設計してください。命令、初期状態、エージェントが得る観測、その行動空間、成功判定を書いてください。チェッカーはどの IWSDK ツールを使い、どれをエージェントから隠さなければならないでしょうか。

   <details markdown="1"><summary>ヒント</summary>

   例えば「背後にある音楽プレーヤーをブラウザの左に移動して、曲を一時停止して。」初期状態：二つのパネルがあり、一つは視野外にある。エージェント：目ごとの RGB に加えて頭部姿勢と、選択機能付きのコントローラのレイ。チェッカー：パネルの姿勢とプレーヤーの状態を得るための `ecs_snapshot`。`ecs_set_component`、`get_scene_hierarchy`、`ui_inspect` はエージェントから隠してください。さもないと知覚を迂回できてしまいます。
   </details>

5. Galaxy XR 上の Gemini と visionOS 上の Siri は、アプリ内で行動するために異なる経路をとっています。エンドユーザーにとっての API 優先（API-first）の経路の利点を二つ、GUI 優先（GUI-first）の経路の利点を二つ挙げ、ハイブリッドな方針を提案してください。

   <details markdown="1"><summary>ヒント</summary>

   API 優先：信頼性が高く速く、何を公開するかを開発者が制御できます。しかしカバーするのはオプトインしたアプリと、それらが宣言した行動だけです。GUI 優先：すべてのアプリと目に見えるすべてのコントロールをカバーし、ユーザーは何が起きているかを見ることができます。しかし遅く脆弱です。ハイブリッドは、まず宣言されたインテントを試し、確認付きの GUI 操作にフォールバックします。CAD エージェントが API 呼び出しとクリックの間でフォールバックするのと同じ方法です。
   </details>
