Why this matters

Over five posts we built an engine from the frame loop up: architecture, GPU APIs and render graphs, a mini engine, production engines and physics and simulation. Every box in those diagrams was hand-written code. In 2026, neural networks sit inside many of those boxes. Some of them are in shipping games, such as upscaling and frame generation; others are maturing in SDKs, such as neural materials and texture compression. A new class of models, interactive world models, generates the whole frame from the player’s input with no engine underneath.

This final post maps that landscape: what is replaced, what is assisted, what actually ships and what is still research. It ends by handing you over to the world-models and embodied-ai series. Everything product-related is dated as of November 2026 and cites official sources. This area changes monthly.

Prerequisites

  • The real-time pipeline: G-buffers, temporal anti-aliasing, ray-traced effects and denoising (graphics 06, graphics 11).
  • 3D Gaussian Splatting (neural-rendering 04).
  • Basic deep learning: MLPs, transformers, diffusion models (world-models 02).

1. The spectrum: from classical to neural

It helps to place every engine component on a four-step scale:

  1. Classical: hand-written algorithms (rasterizer, shadow maps, a PGS solver).
  2. ML-assisted: a network helps a classical stage but can be removed, for example ML denoising of a path-traced image or an ML-based upscaler on top of TAA inputs.
  3. Hybrid: a network is a component of the pipeline with an engineered interface: a neural texture decoded inside a shader, a radiance cache trained on the fly, a splat-based scene drawn next to meshes.
  4. Fully neural: the network is the engine. It maps past frames and actions to the next frame, with no explicit geometry, physics or game logic.

The figure below places each engine component on this scale: every row is one component, and the column its bar reaches shows how neural it is today.

Why now? Three things came together. First, tensor hardware in every GPU: RTX tensor cores, the RDNA 4 ML accelerators and Intel XMX units execute small matrix multiplies far faster than the shader ALUs do. Second, a pixel cost wall: 4K at high frame rates with path tracing costs far more than a GPU can afford per pixel, so reconstructing pixels became cheaper than rendering them. Third, generative models that can now produce images, video, 3D assets and code at useful quality. The rest of the post follows the components from the top of the figure to the bottom.

2. Neural rendering inside real-time engines

Upscaling and frame generation

Super resolution renders at a lower internal resolution (for example 67 % of the output width and height, so 45 % of the pixels) and reconstructs the output resolution from the current frame, motion vectors, depth and a history of past frames. It is temporal anti-aliasing (TAA) with a learned accumulation and rectification step (graphics 11). Frame generation synthesizes extra frames between two rendered frames, from optical flow, motion vectors and the two images. Multi-frame generation inserts several of them.

The trade-off is easiest to see in a model. Let $t_n$ be the GPU time to render a frame at native resolution, and split it into a part that does not depend on resolution, $t_f$, and a part proportional to the pixel count. With a resolution scale $s$ per axis, an upscaler cost $t_u$, a frame-generation factor $k$ (1 = off) costing $t_g$ per generated frame, and CPU time $t_c$ (pipelined with the GPU):

\[t_{\text{gpu}} = t_f + (t_n - t_f)\,s^2 + t_u + (k-1)\,t_g, \qquad t_{\text{frame}} = \max(t_{\text{gpu}}, t_c),\] \[\text{fps}_{\text{shown}} = \min\!\Big(\frac{1000\,k}{t_{\text{frame}}},\ f_{\text{refresh}}\Big), \qquad L \approx t_c + t_{\text{gpu}} + [k>1]\,t_{\text{frame}} + \tfrac{1}{2}\,\frac{1000}{\text{fps}_{\text{shown}}}.\]

Symbols: $t_{\text{gpu}}$ is the total GPU time per rendered frame; $t_{\text{frame}}$ is the interval between consecutive rendered frames (CPU and GPU run pipelined, so the slower one sets the pace); $f_{\text{refresh}}$ is the display refresh rate in Hz; the factor 1000 converts milliseconds to seconds, so $1000/t_{\text{frame}}$ is the rendered frame rate and multiplying by $k$ gives the displayed one; $t_u$ is counted only when $s<1$ (native resolution needs no upscaler); $[k>1]$ is an indicator that equals 1 when the condition holds and 0 otherwise.

The latency $L$ (in ms) counts the CPU work for the input, the GPU work, the extra frame held back for interpolation when $k > 1$, and on average half a display interval. It ignores the OS, the display and techniques such as NVIDIA Reflex, so take it as an illustration, not a measurement.

Worked example. Take $t_n = 20$ ms (50 fps native), $t_f = 2$ ms, $t_c = 4$ ms, $t_u = t_g = 1$ ms, and no refresh cap:

  • Native, $k=1$: $t_{\text{gpu}} = 20$ ms, so 50 fps and $L = 4 + 20 + 10 = 34$ ms.
  • $s = 0.67$, $k = 1$: $t_{\text{gpu}} = 2 + 18 \times 0.4489 + 1 = 11.08$ ms, so 90 fps and $L = 4 + 11.08 + 5.54 = 20.6$ ms. Upscaling makes the game both smoother and more responsive.
  • $s = 0.67$, $k = 4$: $t_{\text{gpu}} = 14.08$ ms, so 71 rendered fps and 284 displayed fps, but $L = 4 + 14.08 + 14.08 + 1.76 = 33.9$ ms, the same latency as native 50 fps.

The same model in Python:

def frame_model(scale, k, t_native=20.0, t_fixed=2.0, t_up=1.0, t_gen=1.0, t_cpu=4.0, refresh=1e9):
    render = t_fixed + (t_native - t_fixed) * scale ** 2
    gpu = render + (t_up if scale < 0.999 else 0.0) + (k - 1) * t_gen
    frame = max(gpu, t_cpu)
    fps = min(k * 1000.0 / frame, refresh)
    latency = t_cpu + gpu + (frame if k > 1 else 0.0) + 0.5 * 1000.0 / fps
    return 1000.0 / frame, fps, latency          # rendered fps, displayed fps, latency (ms)

for scale, k in [(1.0, 1), (0.67, 1), (0.67, 4)]:
    print(scale, k, [round(v, 1) for v in frame_model(scale, k)])

Neural radiance cache

Path tracing in real time needs many bounces, which is too expensive. The neural radiance cache (NRC; Müller et al., SIGGRAPH 2021) trains a small MLP while the game runs: a few paths are traced longer to provide training targets, and the network learns outgoing radiance as a function of position, direction and material. All other paths stop after one or two bounces and query the cache instead. The paper reports about 2.6 ms per frame at 1080p. It is the learned cousin of the irradiance caches and probes of graphics 06. AMD’s Radiance Caching in FSR Redstone follows the same idea.

Neural materials and neural texture compression

Film-quality layered materials (car paint with flakes, coated fabrics, ceramics) need many texture lookups and long BRDF evaluations. Real-Time Neural Appearance Models (Zeltner et al., SIGGRAPH 2024) replace the whole layered BRDF by a latent texture plus a small MLP decoder that runs inside the shader. The authors report over an order of magnitude faster evaluation than the non-neural layered materials they approximate. This is a hybrid component: the engine still rasterizes or ray traces, and a network evaluates the material.

Neural texture compression (NTC; Vaidyanathan et al., SIGGRAPH 2023) compresses all channels of a material together (albedo, normal, roughness, metalness, ambient occlusion). It stores low-resolution grids of latent features and a tiny MLP per material. To shade a pixel, the shader samples the latents at the texel’s UV and runs the MLP, which outputs all channels at once. Because it is evaluated per texel, it keeps random access, which video codecs do not offer. The paper’s profiles range from 0.2 to 1.0 bits per pixel per channel (BPPC), against about 4 BPPC for its block-compressed (BCn) baseline. It reports 16 times more texels at about 30 % less memory than that baseline.

In the figure below, the left half shows the decoding inside the shader and the right half compares storage:

Worked example. The channel count varies with the material set (the figure sketches 8); assume a 4096 × 4096 material with 9 channels, which has $4096^2 \times 9 = 150{,}994{,}944$ channel-texels. At 4 BPPC that is $603{,}979{,}776$ bits $= 72$ MiB; at 1.0 BPPC, 18 MiB; at 0.2 BPPC, 3.6 MiB. Multiply by hundreds of materials and the difference decides whether a scene fits in an 8 GB GPU.

texels, channels = 4096 * 4096, 9
for name, bppc in [("BCn baseline", 4.0), ("NTC high", 1.0), ("NTC low", 0.2)]:

The cost is computation: every texture sample becomes a small network evaluation. That is where tensor cores in shaders come in.

Neural shaders and cooperative vectors: API status

To run an MLP inside a pixel shader efficiently, the shader must hand small matrix-vector products to the tensor units. The APIs are still settling:

  • Vulkan has the vendor extension VK_NV_cooperative_vector (spec source), which NVIDIA’s samples use.
  • DirectX: Microsoft previewed “cooperative vectors” for HLSL, but its September 2025 post announced that the feature would not ship in Shader Model 6.9. It is being replaced by a unified matrix/vector (“LinAlg”) design planned for Shader Model 6.10, which is in preview. SM 6.9 itself shipped in February 2026 with long vectors, shader execution reordering, opacity micromaps and DXR 1.2.
  • NVIDIA RTX Kit (overview) bundles RTX Neural Shaders and the Neural Texture Compression SDK, both labelled beta. The RTXNTC SDK v0.10 adds inference through the DX12 SM 6.10 path and warns that it is not yet for shipping products. RTX Neural Materials was listed as not yet released.

So as of November 2026: neural upscaling and frame generation are in hundreds of shipping games; neural materials and texture compression are mature research with beta SDKs, waiting for standard shader-model support.

3. Gaussian splats in engines

Splats (neural-rendering 04) are attractive for engines because they are rendered by rasterization (project, sort, alpha-blend), with no network at run time. Captured real places become game-ready backdrops within hours. The home page’s Gaussian World demo renders them in WebGL 2, and neural-rendering 06 walks through capture to VR.

The ecosystem as of November 2026:

  • Standard: Khronos announced a glTF extension, KHR_gaussian_splatting, as a release candidate in February 2026. The extension README now lists its status as ratified. Niantic’s open SPZ format (repo, MIT), about 10 times smaller than PLY, is widely used for compressed splats.
  • Web: PlayCanvas’s engine renders splats natively, including streamed level of detail, and its open-source SuperSplat editor (repo) cleans and edits captures in the browser. Spark (sparkjs.dev, from World Labs) is a three.js-based splat renderer that reads PLY, SPZ and other formats.
  • Game engines: there is no built-in splat renderer in Unreal, Unity or Godot as far as their official notes show. There are many plugins: for Unity, Aras Pranckevičius’s UnityGaussianSplatting (MIT; the author says it is no longer actively developed); for Unreal, plugins from Luma, Volinga and others; for Godot, community add-ons.

The engineering problem is hybrid rendering: splats must coexist with meshes, lights, shadows and post-processing. The standard recipe is in the figure: render the mesh G-buffer first; project and sort the splats; and composite them with a depth test against the mesh depth, so that a character can walk behind a captured statue. Splats are pre-lit (their colors bake the capture’s lighting) and do not cast correct shadows. Relighting and shadowing splats is an active research topic (neural-rendering 05).

4. Generative content pipelines

Image and text to 3D

Asset creation is the biggest cost in game production, so 3D generators get a lot of attention. Open models as of November 2026:

Commercial services (Meshy, Tripo, Hyper3D Rodin and others) wrap similar models with retopology, UV unwrapping and PBR baking. Inside the engine, the useful question is not “can it make a mesh?” but “can it make a game-ready asset?”: clean topology with a sensible triangle budget, UVs without overlaps, separate PBR maps without baked lighting, correct scale and pivot, collision proxies and levels of detail (graphics 08 covers remeshing and simplification). As of 2026, generated assets are production-ready for props, prototypes and background content, and need artist cleanup for hero assets and anything that deforms.

Materials, motion and procedural generation

  • PBR textures and materials: diffusion models generate tileable albedo, normal and roughness maps from text or photos (Adobe’s Substance 3D tools ship Firefly-based text-to-texture). Hunyuan3D’s Paint model and TRELLIS.2 output PBR maps directly.
  • Motion: text-to-motion diffusion models such as MDM (Tevet et al., ICLR 2023, arXiv 2209.14916) generate skeletal animation that feeds the animation runtime of post 05; graphics 09 covers the rest.
  • Procedural generation plus LLMs: rather than generating geometry directly, an LLM writes parameters or code for a classical procedural system (a Houdini graph, a Blender script, a level-layout grammar). The output stays editable, deterministic and within budget, which is why this pattern is popular in production.

5. LLM agents in engines and editors

The Model Context Protocol (MCP; open-sourced by Anthropic in November 2024, specification) lets an LLM call tools exposed by a server. An editor MCP server exposes operations such as creating objects, editing components, running the game or reading the console. The agent can then build a scene, write a script, run it, read the error and fix it. Separate official tools from community projects:

AI NPCs run language models at play time. NVIDIA’s ACE stack (speech recognition, a small language model, text-to-speech, animation) powers PUBG Ally, a voice-controlled AI teammate that ran as a public beta in June 2026 on RTX GPUs with at least 8 GB of memory, with on-device speech-to-text and a 2B-parameter language model. NVIDIA also released an ACE Game Agent SDK in beta with Unreal Engine 5 plugins. The hard engineering is not the model but the interface: a small model must call game actions through a fixed tool schema, stay within a latency budget of a few hundred milliseconds, and share the GPU with rendering.

6. Neural game engines and interactive world models

At the far end of the spectrum, the engine is replaced by a network that predicts the next frame from past frames and the player’s action:

\[\mathbf{o}_{t+1} \sim p_\theta\big(\mathbf{o}_{t+1} \,\big\vert\, \mathbf{o}_{t-c+1:t},\ \mathbf{a}_{t-c+1:t}\big),\]

where $\mathbf{o}_t$ is a frame (usually a latent from an autoencoder), $\mathbf{a}_t$ the action (keys, mouse, camera pose or text), $c$ the context length, and $p_\theta$ the conditional distribution represented by a network with parameters $\theta$ ($\sim$ means sampling from it, so the same input can yield different next frames). Most models are autoregressive video diffusion models: a diffusion or flow model generates the next latent frame conditioned on a window of past latents and actions, and it is distilled to a few denoising steps to reach real time. World-models 03 explains the generative machinery, and world-models 04 covers 3D-consistent world generation. Here we look at them as engines.

How do they compare with the engine of this series?

  • What they learn: rendering, physics, game rules and even other players’ behavior, implicitly, from video plus actions. Nothing is specified by hand. That is the appeal (any world you have video of) and the problem (no guarantees).
  • Control: keys and mouse map to learned action embeddings. Newer systems add text (“make it rain”), camera poses, or spatial memories. There is no API for “set door 3 to open”; editing has to go through prompts or conditioning.
  • Frame rate and latency: real time requires distilling the diffusion model to a few steps, caching past activations, and often custom hardware (Oasis on Etched’s chip, GameNGen on TPU). Every frame costs a large network evaluation, compared with a few milliseconds of rasterization, so energy and serving cost per player-hour remain far above a classical engine.
  • Memory and consistency: a finite context window means the world drifts. Turn around and the room may have changed. Remedies include longer contexts, retrieval of posed past frames as spatial memory (RTFM, WorldPlay), and explicit 3D intermediates (Marble exports splats and meshes, which a classical engine then renders).
  • Failure modes: objects morph or vanish, physics violations (interpenetration, objects floating), quality drift over long rollouts, actions with delayed or no effect, and degradation outside the training distribution.

So the realistic 2026 picture is convergence rather than replacement. World models generate content, prototypes and training environments. Classical engines provide persistence, exact rules and cheap rendering. 3D outputs (splats, meshes) are the bridge between them.

7. Engines as data factories

The last role of the engine is the one that connects this series to embodied AI: generating training data for world models and robot policies (post 05, Section 10).

  • Simulation and synthetic data: Isaac Sim with Omniverse Replicator (docs), Genesis and the GPU simulators of post 05 render millions of labelled frames and robot trajectories. Matrix-Game 3.0 explicitly trains on Unreal Engine renders as part of its data engine, so classical engines now produce training data for neural ones.
  • World foundation models: NVIDIA’s Cosmos platform (Agarwal et al., arXiv 2501.03575) provides open video world models for physical AI. Cosmos-Predict2.5 and Cosmos-Transfer2.5 (arXiv 2511.00062) predict future video and turn simulator renders (segmentation, depth, edges) into photoreal video. That closes the sim-to-real appearance gap with a generative model instead of a better renderer. In May 2026 NVIDIA released the Cosmos 3 family (repository).
  • Synthetic robot experience: NVIDIA’s GR00T-Dreams blueprint post-trains a Cosmos model on a robot, generates task videos from single images and extracts actions from them. Cosmos Policy (arXiv 2601.16163) fine-tunes a video world model directly into a robot policy.

8. Open problems and a learning path

Open problems, as of late 2026:

  1. Controllability and persistence of neural engines: exact game state, saving and loading, multiplayer consistency, deterministic replays. All of this is easy for the engine of post 01 and unsolved for world models.
  2. Cost: the energy and serving cost per player-hour of neural frames, compared with rasterization; distillation, caching and dedicated hardware.
  3. Artifacts of reconstruction: ghosting and disocclusion errors in frame generation; temporal stability of neural materials; relighting and shadows for splats.
  4. Standard APIs for neural shaders (SM 6.10 LinAlg, a cross-vendor Vulkan extension) and standard formats (KHR_gaussian_splatting, compressed splat extensions).
  5. Evaluation: how to measure a world model’s physical correctness and consistency, not just its visual quality (world-models 05).
  6. Sim-to-real: when are generative “transfer” models better than a better renderer, and how do we make sure that they do not hallucinate physics?

  • Generative 3D: the TRELLIS and Hunyuan3D-2.1 repositories.
  • Agents: the MCP specification; read an editor MCP server such as unity-mcp to see how editor operations become tools.
  • World models: the GameNGen and DIAMOND project pages (DIAMOND’s code runs locally), the open HY-WorldPlay code, and the world-models series on this site.

Exercises

  1. Using frame_model (other parameters as in the worked example), find for $t_n = 30$ ms the internal resolution scale at which $k = 1$ reaches 60 fps, and compare its latency with that of $s = 1$, $k = 2$.
  2. Extend the model with a display refresh cap and a “frame pacing” rule: generated frames are only useful if $k \cdot F \le R$, where $F$ is the rendered frame rate and $R$ the refresh rate. What is the best $k$ for 144 Hz when the rendered frame rate is 70 fps?
  3. Compute the texture memory of a scene with 300 unique 2048² materials of 9 channels at 4 BPPC and at 0.5 BPPC. How many additional materials fit into the saved memory?
  4. Write a pseudo-MCP tool schema (name, description, JSON parameters) for “spawn prefab at position” and “set material parameter”. Which validation should the editor perform before executing an LLM’s call?
  5. Pick one world model from the table and list three experiments that would test persistence (for example, look away and back, open a door and leave the room, return to a start position). What would a classical engine guarantee in each case?
Hints
  1. 60 fps means $t_{\text{gpu}} = 1000/60 \approx 16.7$ ms; solve $2 + 28 s^2 + 1 = 16.7$ for $s$ (about $0.70$); the latency is about $4 + 16.7 + 8.3 = 29$ ms. With $s = 1$, $k = 2$: $t_{\text{gpu}} = 31$ ms, 32 rendered fps (65 displayed), about $4 + 31 + 31 + 7.8 \approx 74$ ms of latency.
  2. $k = 2$ (140 fps); $k = 3$ would exceed the refresh rate, so the extra frames would never be shown.
  3. $300 \times 2048^2 \times 9 \times 4 / 8$ bytes $\approx 5.3$ GiB versus about $0.66$ GiB; the 4.6 GiB saved holds about 2,100 more materials at 0.5 BPPC (2.25 MiB each).
  4. Check that the prefab exists, that positions are within level bounds, and that the parameter type matches; require an undo step.
  5. Persistence of object identity, state changes and position; a classical engine stores them explicitly in its scene and game state.
