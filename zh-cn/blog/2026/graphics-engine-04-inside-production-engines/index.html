为什么重要

在上一篇中，我们搭建了一个迷你引擎：一个主循环、一张阴影贴图、一个恒定的环境光项，以及一个为每个物体发出一次绘制调用（draw call）的 CPU 循环。生产级引擎面对的是同样的问题，但规模大到这些简单的答案全部失效：数十亿的源三角形、动态全局光照、在任何距离都清晰的阴影、无法整体放进内存的开放世界，以及需要工具链支持的数百人团队。本文打开四个引擎和另外几个引擎，借助它们的官方文档和作者们讲解设计的演讲，看看它们是如何解决这些问题的。当某个算法是关键思想时（Nanite 的 LOD 切割、球体追踪、虚拟阴影贴图页），我们会重建一个玩具版本，让你亲眼看到它如何工作。

所有版本信息均截至 2026 年 11 月；引擎迭代很快，请查阅所附的发布说明。

1. Unreal Engine 5

Unreal Engine 5（UE5）用 C++ 编写，上层有 Blueprint 可视化脚本，任何接受 Unreal Engine EULA 的人都可以在 GitHub 上获取其完整源码。它的渲染围绕 2021-2022 年一同推出的三个系统构建：Nanite（虚拟几何体，virtualized geometry）、Lumen（动态全局光照，dynamic global illumination）和 Virtual Shadow Maps（虚拟阴影贴图）。它们是作为一个整体来设计的：Nanite 生成微细节几何的可见性缓冲（visibility buffer），Virtual Shadow Maps 把同样的几何渲染到超高分辨率的阴影页中，而 Lumen 则无需预计算地为其打光。

1.1 Nanite：虚拟几何体

问题。 一个电影级品质的资产可能有数百万个三角形。当物体只占几百个像素时，把它们全部绘制出来是浪费；而经典的离散 LOD（每个网格预先计算几个版本，按距离切换）会出现明显的跳变，并且仍然无法简化一个大物体，因为它的近端需要完整细节，远端却几乎不需要细节。Nanite 的答案由 Karis、Stubbe 和 Wihlidal 在 SIGGRAPH 2021 Advances 课程中提出（A Deep Dive into Nanite Virtualized Geometry）：让细节层次以簇（cluster）为单位，并在每一帧于 GPU 上选择，这样绘制的三角形数量就与像素数量挂钩，而不是与源资产的大小挂钩。

构建层级（离线）。 网格被切分成最多 128 个三角形的簇。然后逐层进行：

  1. 把相邻的簇组合成组（group）；
  2. 把每个组合并后简化到大约一半的三角形数，同时锁定组的外边界（边界顶点不得移动）；
  3. 把简化后的组重新切分成新的、更粗的簇，作为下一层的输入。

由于下一层会形成不同的分组，在某一层被锁定的边界，在下一层会落在某个组的内部，并在那里被简化。这就是锁定并不会让边界永远保持完整分辨率的原因。这也是一个粗簇可以有多个父组的原因：该层级是一个有向无环图（directed acyclic graph，DAG），而不是树。每个簇存储创建它的那次简化的几何误差（geometric error，以世界单位计），并且误差被设为单调（monotonic）的：父节点的误差永远不小于其子节点的误差。

我们可以在一维中重建这一思想的本质。我们的“网格”是一条有 128 个线段的地形剖面（每个线段扮演三角形的角色），被切成 16 个簇，每个簇 8 个线段。每一层合并相邻的兄弟对，通过贪心的顶点删除把线段数减半，同时锁定组的两端，并把到原始剖面的最大竖直距离记录为误差。

import numpy as np

xs = np.linspace(0.0, 16.0, 129)                 # 128 segments, 8 per cluster
h = (1.2 * np.sin(0.45 * xs) + 0.5 * np.sin(1.7 * xs + 1)
     + 0.18 * np.sin(4.3 * xs + 2) + 0.07 * np.sin(9.1 * xs + 0.5))

def max_dev(a, b):
    """Largest vertical distance between the original samples a..b and the segment a-b."""
    t = (xs[a:b + 1] - xs[a]) / (xs[b] - xs[a])
    return float(np.max(np.abs(h[a:b + 1] - (h[a] + t * (h[b] - h[a])))))

def simplify(verts, target_segments):
    """Greedy vertex removal; the first and last vertex are locked."""
    verts = list(verts)
    while len(verts) - 1 > target_segments:
        costs = [max_dev(verts[i - 1], verts[i + 1]) for i in range(1, len(verts) - 1)]
        del verts[1 + int(np.argmin(costs))]
    err = max(max_dev(verts[i], verts[i + 1]) for i in range(len(verts) - 1))
    return verts, err

# Level 0: 16 clusters of 8 segments with error 0. Each level: merge pairs, halve, lock the ends.
levels = [[dict(verts=list(range(8 * c, 8 * c + 9)), err=0.0, children=[]) for c in range(16)]]
while len(levels[-1]) > 1:
    prev, nxt = levels[-1], []
    for g in range(0, len(prev), 2):
        a, b = prev[g], prev[g + 1]
        verts, err = simplify(a["verts"] + b["verts"][1:], 8)
        nxt.append(dict(verts=verts, err=max(err, a["err"], b["err"]), children=[a, b]))
    levels.append(nxt)

for i, lv in enumerate(levels):
    print(f"level {i}: {len(lv):2d} clusters, max error {max(c['err'] for c in lv):.4f} m")

在一维中，每个组的内部只有一个顶点，所以我们的层级恰好是一棵树；在曲面上，跨越旧边界的重新分组才会产生 DAG。对正确性起决定作用的两个性质，即锁定的组边界和单调的误差，则是相同的。下图画出了这段代码构建的层级：自下而上看簇数如何减半，并留意黑色刻度在各层的位置，它们对应锁定的边界。

选择切割（每一帧，在 GPU 上）。 簇的世界空间误差 $\varepsilon$ 通过透视投影变成屏幕空间误差。设垂直分辨率为 $H$ 像素、视场角为 $\theta$，距离 $d$ 处的一个世界单位覆盖 $K/d$ 个像素，其中 $K = H / (2 \tan(\theta/2))$。于是

\[\varepsilon_{\text{px}} = \frac{\varepsilon\, K}{d}, \qquad d = \max\big(\lVert \mathbf{c} - \mathbf{e} \rVert - r,\ d_{\min}\big),\]

这里使用的是从眼睛 $\mathbf{e}$ 到簇包围球（球心 $\mathbf{c}$，半径 $r$）最近点的距离，这是保守的做法；$d_{\min}$ 是一个很小的下限，防止相机落进包围球内部时除以零。当且仅当一个簇自身的误差足够小而其父节点的误差不够小时，才绘制这个簇：

\[\varepsilon_{\text{px}}(\text{cluster}) \le \tau \;<\; \varepsilon_{\text{px}}(\text{parent}),\]

阈值 $\tau$ 约为一个像素。被绘制的簇的集合称为 DAG 上的切割（cut）。由于误差是单调的，从根到叶的每条路径恰好穿过切割一次，因此曲面的每一部分只以一种分辨率绘制一次。又因为同一个组内的簇共享它们的父误差，它们总是一起切换（前提是同组的簇用同一个包围球来计算 $d$），所以被锁定的边界能够对齐：不会出现裂缝。关键在于，这个测试是局部的：每个簇都可以在一个计算着色器线程中独立求值，无需从根开始遍历（Nanite 仍然在簇包围体上使用一个层级结构来快速剔除）。

算例。 取 $H = 1080$、$\theta = 60°$，则 $K = 1080/(2 \tan 30°) \approx 935$ 像素。一个 $\varepsilon = 0.05$ m 的簇在 $d = 0.05 \cdot 935 \approx 47$ m 处投影为 1 个像素。比这更近时，它必须细化为它的子节点；更远时，它的父节点（比如 $\varepsilon = 0.12$ m，在 112 m 处切换）可以接管。

K = 1080 / (2 * np.tan(np.radians(30)))         # pixels per world unit at distance 1

def select_cut(node, cam, tau=1.0):
    v = node["verts"]
    lo, hi = v[0], v[-1]
    hmin, hmax = h[lo:hi + 1].min(), h[lo:hi + 1].max()
    cx, cy = (xs[lo] + xs[hi]) / 2, (hmin + hmax) / 2
    r = 0.5 * np.hypot(xs[hi] - xs[lo], hmax - hmin)
    d = max(np.hypot(cx - cam[0], cy - cam[1]) - r, 1e-3)
    if node["err"] * K / d <= tau or not node["children"]:
        return [node]
    return [c for child in node["children"] for c in select_cut(child, cam, tau)]

for D in (5.0, 60.0, 500.0):                     # camera to the left of the terrain, 2 m high
    cut = select_cut(levels[-1][0], cam=(-D, 2.0))
    print(f"camera {D:5.0f} m away: {len(cut):2d} clusters, {sum(len(c['verts']) - 1 for c in cut):3d} segments")

对于一维玩具，我们从根开始遍历；GPU 版本则并行地对每个簇求值同一个不等式。运行这段脚本：近处的相机会在靠近它的地方保留细的簇，而在远端保留粗的簇，随着相机远离，线段数量下降。如下图所示：上半部分的折线按所选簇的层级着色（颜色越深，层级越细），下半部分是层级结构，被选中的簇用高亮方块标出，请对照着看两幅子图。紧接着的第二幅图把不等式 $\varepsilon K / d \le \tau$ 画了出来：请看每一层的直线在多远的距离处穿过 $\tau = 1$ px 的虚线。

现在来玩一玩。这个小组件用 JavaScript 运行同样的构造过程。移动相机并调整阈值，然后切换到独立 LOD 层级：此时每个 1 m 的区域会从一份单独简化的整条剖面副本中选取自己的层级，这就是朴素的按物体或按块 LOD 的做法，只要相邻区域选择了不同的层级，就会出现裂缝。小组件之后的静态图把其中一处裂缝放大来看。

一维的 Nanite 风格层级。拖动相机滑块（对数刻度）和以像素为单位的误差阈值 τ；所选切割（上，按层级着色）、层级结构（下）和线段数会实时更新。切换到独立 LOD 层级，可以看到相邻区域意见不一致的区域边界处出现裂缝（红色）；使用锁定边界的层级结构则不可能出现裂缝。

剔除、光栅化与着色。 在 LOD 选择之后，Nanite 分两个阶段对簇进行视锥剔除和针对层次深度缓冲（hierarchical depth buffer，HZB）的剔除：先对照上一帧的深度（上一帧可见的东西现在很可能也可见），然后把剩下的簇对照刚刚绘制出的内容的深度重新测试，这样新近露出的部分就不会丢失。可见的簇随后被光栅化到可见性缓冲（第 02 篇）中：每个像素写入一个 64 位的值，包含深度以及簇和三角形的 ID，通过原子操作写入。材质着色稍后进行，每个像素一次，通过读取这些 ID 完成。

光栅化被一分为二。GPU 硬件光栅化器对大三角形很高效，但对微小三角形会浪费工作：它们以 2x2 像素的四元组（quad）着色，并且每个三角形都有设置开销，因此一个只覆盖一个像素的三角形，其开销几乎与覆盖许多像素的三角形相当。因此 Nanite 用计算着色器中的软件光栅化器来光栅化含小三角形的簇（使用 64 位原子操作写入可见性缓冲），并把含大三角形的簇送往硬件路径。演讲中描述了 32 像素的边长阈值（摘要），我们在下一幅图中使用它。

最后，Nanite 会对其数据进行流送（streaming）：DAG 被切成页，只有当前切割所需的页才驻留在 GPU 内存中，更粗的数据则始终存在作为后备。这就是名字中的“虚拟化”，类比于虚拟内存。Nanite 文档列出了它当前的限制（例如只支持不透明和遮罩材质，不支持前向渲染器、MSAA 或变形目标）以及自 2021 年以来新增的功能，比如骨骼网格。

1.2 Lumen：动态全局光照

Lumen 每一帧都计算间接漫反射光照和反射，不需要烘焙，所以灯光、几何和一天中的时间都可以自由变化。它由 Wright、Narkowicz 和 Kelly 在 SIGGRAPH 2022 Advances 课程中介绍（Lumen: Real-time Global Illumination in Unreal Engine 5），而 Lumen Technical Details 页面记录了当前的行为。下图给出了整体流程，可以从左向右读：左列是“光线能命中什么”（场景表示），中列是“怎么追踪”，右列是“怎么把结果变成每个像素的光照”。其核心难点在于，全局光照需要能命中场景中任何东西（包括屏幕之外的东西）的光线，并且还需要命中点处的已打光颜色，而这一切都要在几毫秒内完成。

不用三角形的追踪。 使用软件光线追踪时（在没有光追单元的硬件上这是默认方式），Lumen 针对有向距离场（signed distance field，SDF）进行追踪。每个网格都有一个预先计算好的网格距离场（mesh distance field）：一张小的 3D 纹理，在每个点存储到最近表面的距离。Lumen 对最初的几米（据文档所述为 2 m）针对各个网格的 SDF 进行追踪，更远的光线则针对合并后、更粗的全局距离场（global distance field）进行追踪。在这两者之前，它会先尝试对深度缓冲做一次廉价的屏幕追踪（screen trace）。启用硬件光线追踪后，光线-三角形追踪会取代距离场步进。

追踪 SDF 使用球体追踪（sphere tracing，Hart 1996）：在点 $\mathbf{p}$ 处，到最近表面的距离 $f(\mathbf{p})$ 意味着以该距离为半径的球是空的，所以光线可以安全地前进 $f(\mathbf{p})$：

\[\mathbf{p}_{k+1} = \mathbf{p}_k + f(\mathbf{p}_k)\, \boldsymbol{\omega}, \qquad \text{stop when } f(\mathbf{p}_k) < \epsilon .\]

其中 $\boldsymbol{\omega}$ 是光线的单位方向，$\epsilon$ 是判定命中的容差（与上文的几何误差 $\varepsilon$ 无关）。

算例。 原点处的单位球，$f(\mathbf{p}) = \lVert\mathbf{p}\rVert - 1$，以及一条从 $(-3, 0.5, 0)$ 出发沿 $+x$ 方向的光线。各步长依次为 $2.041,\ 0.081,\ 0.0099,\ 0.0013$，四步之后到达 $x \approx -0.8662$，而精确的命中点为 $x = -\sqrt{0.75} = -0.86603$。远离表面时步长很大；靠近表面时收敛很快。擦着表面经过却没有命中的掠射光线是较慢的情形，而且薄墙的 SDF 并不准确，这就是文档要求墙至少 10 cm 厚的原因。

import numpy as np

def sphere_trace(f, origin, direction, eps=1e-3, max_steps=64):
    p = np.asarray(origin, float)
    d = np.asarray(direction, float) / np.linalg.norm(direction)
    for k in range(max_steps):
        dist = f(p)
        if dist < eps:
            return p, k
        p = p + dist * d
    return None, max_steps

unit_sphere = lambda p: np.linalg.norm(p) - 1.0
hit, steps = sphere_trace(unit_sphere, (-3.0, 0.5, 0.0), (1.0, 0.0, 0.0))
print(hit, steps)   # about [-0.8662, 0.5, 0.0] after 4 steps

命中点处是什么？表面缓存。 距离场只能告诉你光线在哪里命中，却不知道那里的材质。Lumen 维护一个表面缓存（surface cache）：每个网格被几张卡片覆盖，卡片是从几个方向对网格做的正交捕获（文档给出的默认值是每个静态网格 12 张卡片、每个骨骼网格 6 张），存储反照率、法线、深度以及计算出的光照。一次光线命中会查找最近的卡片并读取它们缓存的光照，因此一次命中只需要几次纹理读取，而不是一次完整的材质求值。缓存会在若干帧内被增量地重新打光，并且由于缓存的光照包含来自上一帧的间接光，多次反弹会随时间累积。下图用一个玩具物体演示卡片：右侧每张小图是一张卡片捕获的深度，灰色越暗表示离卡片越近，白色表示光线没有打到物体。

最终聚集。 为每个像素都追踪光线代价太高，因此据演讲所述，Lumen 从放置在可见表面上的一组稀疏的屏幕空间探针（screen-space probes）出发进行追踪，利用上一帧的光照对它们的方向做重要性采样，把远处的辐射度缓存在更粗的世界空间辐射度缓存（world-space radiance cache）中，然后把探针辐射度积分并滤波为逐像素的间接漫反射光照。反射复用同样的追踪机制，只是光线沿着镜面波瓣（specular lobe）发出。这种“稀疏追踪、缓存、插值”的结构与光照探针（辐照度探针，irradiance probes）和 DDGI（图形学第 11 篇）的思路相同，只是被做成了能根据屏幕上的内容自适应。

UE 5.8（2026 年 6 月）加入了 Lumen Lite（测试版），一种更廉价的 Lumen 模式，见 UE 5.8 发布说明。

1.3 Virtual Shadow Maps

第 03 篇中的单张阴影贴图在整个场景中只有一种纹素密度：相机附近模糊，远处则浪费。级联阴影贴图（cascaded shadow maps）用几张不同尺度的贴图改善了这一点。Virtual Shadow Maps（VSM）则走得远得多。根据文档，每盏灯有一张 16k × 16k 纹素的虚拟阴影贴图，划分成 128 × 128 纹素的页。只有被某个可见像素实际需要的页才会在物理页池中分配并渲染（使用 Nanite，因此几何细节与纹素密度相匹配），并且除非页内有东西移动，否则页会在帧与帧之间被缓存。平行光使用剪辑图（clipmap）：以相机为中心的一叠这样的虚拟贴图，每一层覆盖的半径是前一层的两倍；文档中记录的层级范围大约从 64 cm 到约 40 km。

选择层级。 距离为 $d$ 的像素覆盖的世界空间足迹约为 $\varphi = d \cdot 2\tan(\theta/2)/H$。剪辑图第 $k$ 层覆盖半径 $2^k$ cm，直径上有 $16384$ 个纹素，所以它的纹素大小是 $s_k = 2^{k+1}/16384$ cm。为了让每个像素至少有一个阴影纹素，该像素需要纹素不大于其足迹的最粗层级，即 $s_k \le \varphi$，也就是 $k = \lfloor \log_2(16384\, \varphi / 1\,\text{cm}) \rfloor - 1$（限制在可用层级范围内），其页为 $\lfloor \mathbf{x} / (128\, s_k) \rfloor$（$\mathbf{x}$ 是该点在剪辑图平面内的世界坐标，单位 cm；每页 128 个纹素，所以页宽为 $128\, s_k$）。

算例。 在 $d = 10$ m、$H = 1080$、$\theta = 60°$ 时，$\varphi \approx 1.07$ cm。第 14 层的 $s_{14} = 2^{15}/16384 = 2$ cm，太粗；第 13 层的 $s_{13} = 1$ cm，所以 10 m 处的像素采样第 13 层，其页宽 $128 \times 1$ cm $= 1.28$ m。（Unreal 真实的层级选择还取决于到剪辑图中心的距离以及质量设置；这里给出的是原理。）如下图所示，把同样的选择应用到整片可见地面上：左图看颜色如何随距离变化，右图看每一层需要多少页。

在下面的小部件中移动和转动相机，它运行的是同一个模型。红框标出的页在上一次更新中没有被请求：有了页缓存，只有这些页需要渲染，这就是为什么缓慢移动的相机的开销远小于总页数所暗示的。

1.4 Temporal Super Resolution、World Partition 与 MetaHuman

  • 时间性超分辨率（Temporal Super Resolution，TSR）是 UE5 内置的时间上采样器（temporal upscaler）：它以较低的内部分辨率渲染，每帧使用不同的亚像素抖动（jitter），用运动向量重投影一份高分辨率的历史，并累积样本，在历史不再匹配的地方将其拒绝。它的前身是 Karis 在 UE4 中的时间抗锯齿（SIGGRAPH 2014 Advances）。TSR 文档解释了它的设置，例如 16 的历史样本数，以及在 50 % 屏幕百分比下需要多少帧才能收敛。时间累积也是让 Lumen 和 VSM 负担得起的原因：三者都是把工作分摊到多个帧上。
  • World Partition 用一个单一的持久世界取代手动拆分的关卡，该世界被划分成网格并按距离流送，配合 One File Per Actor 使许多人可以无冲突地编辑同一张地图，配合 Data Layers 处理变体，并为远处的单元格自动生成 HLOD（层级 LOD 代理，hierarchical LOD proxies）（文档）。
  • MetaHuman：自 UE 5.6 起，用于制作逼真数字人的工具 MetaHuman Creator 可以在引擎内运行，并配有用于面部表演捕捉的 MetaHuman Animator（文档）。

2. Unity 6

Unity 是一个用 C# 编写脚本的 C++ 引擎，核心闭源。Unity 6 始于 2024 年的 6.0 LTS，如今持续发布常规更新：6.3 LTS（2025 年 12 月）是当前的长期支持版本，6.6（2026 年 8 月）是最新的受支持更新。2024 年，Unity 取消了运行时费用（该费用曾在 2023 年引发强烈反对），并回到按席位计费的定价方式。

可编程渲染管线（Scriptable Render Pipeline，SRP）。 Unity 的渲染循环本身是用 C# 在可编程渲染管线（SRP）之上编写的，这是一个用于调度和配置渲染命令的薄 API。它自带两条管线：可从手机扩展到 PC 的 Universal Render Pipeline（URP），以及面向高端平台的 High Definition Render Pipeline（HDRP）。Unity 的 2026 年渲染管线策略把新的工作放进 URP（包括计划中的实时 GI 和屏幕空间反射），让 HDRP 处于维护状态、不再增加新功能，并从 6.5 起弃用旧的 Built-in 管线。

Render Graph。 在 Unity 6 中，URP 的各个 pass 是基于渲染图（render graph）编写的：每个 pass 声明自己的资源，系统会移除输出未被使用的 pass，在每个资源第一次写入前才分配它、在最后一次读取后释放它，并在基于分块（tile-based）的移动 GPU 上把兼容的 pass 合并为原生渲染 pass。这恰好就是第 03 篇中玩具 PassList 的三项工作。

GPU Resident Drawer。 GPU Resident Drawer 把实例数据保存在 GPU 上（基于 BatchRendererGroup API），并用 GPU 实例化绘制兼容的渲染器，降低有大量物体的场景的 CPU 开销，也就是第 03 篇帧预算图中的那个拐点。它要求使用 Forward+ 路径和支持计算的图形 API。在此之上，GPU 遮挡剔除会针对来自当前帧和上一帧的降采样深度缓冲测试包围球，与 Nanite 的 HZB 剔除是同样的两阶段思路。STP（Spatial-Temporal Post-processing）上采样器扮演 TSR 的角色，而 Adaptive Probe Volumes 提供逐像素的烘焙探针光照。

DOTS 与 Entities。 Unity 的数据导向技术栈（Entities ECS、Burst 编译器和 C# Job System）是第 01 篇思想的生产级范例。自 Unity 6.4（2026 年 3 月）起，Entities、Entities Graphics 和 Collections 成为与编辑器同步版本的核心包，而 6.5 把 Netcode for Entities 移入了引擎。

3. Godot 4

Godot 是一个完全开源的引擎，采用 MIT 许可证，用 C++ 编写，可以用 GDScript、C# 或原生扩展编写脚本。截至 2026 年 11 月，最新的稳定版本是 4.7.2（2026 年 8 月），它之前是 2026 年 6 月的功能版本 4.7（HDR 输出、面光源、Vulkan 注视点渲染支持）。

RenderingDevice。 Godot 4 围绕 RenderingDevice 重写了渲染器，这是对现代显式 API 的一层低级抽象，也就是 Unreal 称为 RHI、第 02 篇介绍过的那种渲染硬件接口（render hardware interface，RHI）。它背后是 Vulkan、Direct3D 12（自 4.3 起）和 Metal（自 4.4 起，面向 Apple 芯片）。RenderingDevice 也向脚本公开，所以你可以在 GDScript 中编写计算着色器。

三个渲染器。 Forward+（面向桌面的分簇前向渲染，clustered forward rendering）和 Mobile 都运行在 RenderingDevice 上；Compatibility 运行在 OpenGL 上，是网页端唯一的选择。一个引擎要维护三个渲染器，本身就是一个很好的教训：功能集是平台的函数。

全局光照选项。 Godot 提供了一份GI 技术菜单，各有不同的权衡：VoxelGI（实时、基于体素，用于有界区域）、SDFGI（有向距离场 GI，在相机周围使用级联，由 Juan Linietsky 于 2020 年提出；它不需要 UV 展开或烘焙；动态物体会接收它的光，但不会对它有贡献）、屏幕空间间接光照（SSIL）、烘焙的 LightmapGI 以及反射探针。把 SDFGI 与 Lumen 作比较很有启发：两者都用距离场来低成本地追踪，但 Lumen 又加入了表面缓存和屏幕探针，以达到更高的质量并让动态物体也能贡献光照。

为什么要研究 Godot。 Godot 的渲染器小到可以读完。基于 RenderingDevice 的渲染器位于代码仓库的 servers/rendering/renderer_rd/ 中，每一个设计决策都在公开的拉取请求和提案中讨论过。

4. Bevy

Bevy 是一个用 Rust 编写的引擎，采用 MIT 或 Apache-2.0 双重许可，并且是 ECS 优先的：一切，包括渲染，都是实体（entity）、组件（component）、资源（resource）和系统（system）。截至 2026 年 11 月，它的最新版本是 Bevy 0.20（2026 年 10 月）；它仍处于 1.0 之前，每个版本都会破坏 API。

wgpu。 Bevy 通过 wgpu 渲染，这是 WebGPU API（第 03 篇所用的 API）的 Rust 实现，可以运行在 Vulkan、Metal、D3D12、OpenGL 上，也可以通过 WebGPU 或 WebGL2 在浏览器中运行。

渲染应用与提取阶段。 Bevy 在一个单独的子应用（sub-app）中运行渲染，该子应用有自己的 ECS 世界。每一帧，一个简短的 ExtractSchedule 会把渲染所需的数据（变换、网格句柄、灯光、相机）从主世界复制到渲染世界；然后主世界就可以开始模拟第 $n+1$ 帧，同时渲染世界准备并提交第 $n$ 帧。这就是流水线化（pipelining）：设模拟时间为 $S$、渲染准备时间为 $R$，帧时间从 $S + R$ 降到约 $\max(S, R)$，代价是多出一帧的延迟。文档要求让提取保持简短，因为它是两个世界唯一同步的地方。我们的迷你引擎的 render(world, ...) 直接读取 ECS；提取就是让它能够并行运行的方式。

Bevy 近期的渲染工作显示了开源引擎可以多快地前进：自 0.14 起的实验性虚拟几何（meshlets），自 0.17 起的实验性光线追踪光照项目 Solari，0.19 中被改造成普通 ECS 系统的渲染 pass，以及 0.20 中的网格着色器（mesh shaders）。要研究它，请从 crates/bevy_render 和 crates/bevy_pbr 入手。

5. 其他值得了解的引擎

  • O3DE（Open 3D Engine），亚马逊 Lumberyard 的开源继任者，采用 Apache-2.0 / MIT 许可；它的模块化渲染器称为 Atom。
  • Filament（GitHub，Apache-2.0）是 Google 面向 Android、iOS、桌面和 WebGL2 的实时 PBR 引擎。它的设计文档是关于如何实现 PBR 的最好的免费文本（我们在第 03 篇中用过）。
  • Frostbite（EA）并不公开，但它的演讲塑造了整个行业：FrameGraph 演讲（GDC 2017）普及了渲染图，而 Moving Frostbite to Physically Based Rendering（SIGGRAPH 2014 课程）是生产环境中 PBR 的参考。
  • id Tech 8 是 id Software 为《DOOM: The Dark Ages》（2025）打造的引擎，围绕光线追踪构建：这款游戏原生使用光线追踪渲染，后来又加入了路径追踪模式（NVIDIA），这表明硬件光线追踪正在成为基线。
  • NVIDIA Falcor（GitHub）是一个基于 D3D12 和 Vulkan 的研究框架，专为实时渲染研究的原型开发而设计，是连接论文与引擎的良好桥梁。
  • RTX Remix（GitHub）会拦截旧的固定功能 DirectX 8/9 游戏的绘制调用，重建场景并用路径追踪重新渲染，使模组作者可以替换资产和灯光。它的运行时是开源的，是围绕别人的引擎打造引擎的一个迷人范例。

7. 从每个引擎学到什么，以及如何阅读它们的源码

  • 从 Unreal 学：如何让开销正比于像素而不是内容（Nanite、VSM），以及时间摊销能走多远（Lumen、TSR、VSM 缓存）。先读 SIGGRAPH 的演讲，再读着色器：在 GitHub 源码中，Engine/Shaders/Private/Nanite/ 和 Engine/Shaders/Private/Lumen/ 比驱动它们的 C++ 更易读。编辑器视口中的 Nanite 和 Lumen 可视化模式，是实时观察切割、簇和过度绘制（overdraw）的最快方式。
  • 从 Unity 学：如何把渲染器公开为一个 API，让用户可以编写自己的管线和 pass（SRP、渲染图），以及如何在面向对象的引擎上后期引入数据导向设计（Entities、GPU Resident Drawer）。URP 的 C# 源码随包附带，很容易在调试器里单步跟踪。
  • 从 Godot 学：一个小团队如何让可移植的渲染器保持可理解，以及如何提供多种 GI 方法并如实说明各自的权衡。从 RenderingDevice 入手，然后读 servers/rendering/renderer_rd/ 中的一个渲染器。
  • 从 Bevy 学：“一切皆 ECS”能走多远，以及提取和流水线化如何把模拟与渲染解耦。它的 examples 文件夹是一套由小程序组成的测试集，它的发布说明解释了每一次设计变更。

如何阅读一个引擎的源码。 不要从 main 开始。选定一个帧和一个功能：用 RenderDoc 捕获一帧（第 03 篇），列出它的各个 pass，然后通过搜索每个 pass 的调试标签（每个引擎都会给它的 pass 加标签）找到发出该 pass 的代码。跟踪一个资源（例如阴影贴图）从创建到最后一次使用的全过程。让官方演讲与代码并排放在一起：演讲解释为什么，代码展示演讲略去的数以百计的特殊情况。

    靠近表面时，安全步长就是到表面的那段很小的距离，所以掠射光线只能缓慢向前爬行；对于光滑表面，步数大致与未命中距离的平方根的倒数成比例增长。

  4. VSM 预算。 扩展页分配模型，为一个每秒转动 90° 的相机统计物理页数，缓存会把页保留 30 帧。每帧必须渲染多少新页？
  5. 阅读源码。 在 Godot 的仓库中，找到 Forward+ 构建其分簇灯光列表的位置；或者在 Bevy 中，找到提取点光源的系统。写下从场景传递到渲染器的数据。
