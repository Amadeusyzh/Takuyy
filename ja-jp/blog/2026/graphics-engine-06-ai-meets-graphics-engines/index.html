なぜ重要か

これまでの 5 回で、フレームループからエンジンを組み立ててきました。アーキテクチャ、GPU API とレンダーグラフ、ミニエンジン、商用エンジン、物理とシミュレーションです。それらの図の箱はどれも手書きのコードでした。2026 年には、その多くの箱の中にニューラルネットワークが入っています。アップスケーリングやフレーム生成のように発売済みのゲームに入っているものもあれば、ニューラルマテリアルやテクスチャ圧縮のように SDK の中で成熟しつつあるものもあります。さらに新しい種類のモデルである対話型の世界モデル（world models）は、プレイヤーの入力からフレーム全体を生成し、その下にエンジンはまったくありません。

この最終回では、その全体像を描きます。何が置き換えられ、何が補助され、何が実際に出荷され、何がまだ研究段階なのか。最後に世界モデルと身体性 AIのシリーズへ橋渡しします。製品に関する記述はすべて 2026 年 11 月時点のもので、公式の情報源を引用しています。この分野は毎月変わるからです。

前提知識

  • リアルタイムパイプライン：G バッファ、テンポラルアンチエイリアス、レイトレーシング効果とデノイズ（グラフィックス第 06 回、グラフィックス第 11 回）。
  • 3D ガウシアンスプラッティング（ニューラルレンダリング第 04 回）。
  • 深層学習の基礎：MLP、Transformer、拡散モデル（世界モデル第 02 回）。

1. スペクトル：従来手法からニューラルへ

エンジンの各コンポーネントを 4 段階の目盛りに置いてみると分かりやすくなります。

  1. 従来手法：手書きのアルゴリズム（ラスタライザ、シャドウマップ、PGS ソルバ）。
  2. ML 支援：ネットワークが従来の段階を助けますが、取り外すこともできます。たとえばパストレース画像の ML デノイズや、TAA の入力を使う ML アップスケーラです。
  3. ハイブリッド：ネットワークが、設計されたインタフェースを持つパイプラインの部品になります。シェーダ内でデコードするニューラルテクスチャ、実行中に学習する放射輝度キャッシュ、メッシュと並べて描くスプラットのシーンなどです。
  4. 完全ニューラル：ネットワークそのものがエンジンです。過去のフレームと行動を次のフレームに写像し、明示的な幾何、物理、ゲームロジックはありません。

次の図は、各エンジンコンポーネントをこの目盛りに置いたものです。1 行が 1 つのコンポーネントで、棒がどの列まで伸びているかが現在のニューラル化の段階を表します。

なぜ今なのでしょうか。3 つのことが重なりました。第一に、すべての GPU にテンソル演算ハードウェアが載ったこと。RTX のテンソルコア、RDNA 4 の ML アクセラレータ、Intel の XMX ユニットは、小さな行列積をシェーダ ALU よりはるかに速く実行します。第二に、画素コストの壁。高フレームレートの 4K とパストレーシングは、GPU が 1 画素あたりに払える以上のコストがかかるので、画素を描くより再構成するほうが安くなりました。第三に、生成モデルが画像、動画、3D アセット、コードを実用的な品質で作れるようになったことです。この後は、図の上から下へとコンポーネントを順に見ていきます。

2. リアルタイムエンジンの中のニューラルレンダリング

アップスケーリングとフレーム生成

超解像（super resolution）は、低い内部解像度（たとえば出力の幅と高さの 67%、つまり画素数で 45%）で描画し、現在のフレーム、モーションベクトル、深度、過去フレームの履歴から出力解像度を再構成します。これは、蓄積と補正のステップを学習モデルにしたテンポラルアンチエイリアス（TAA、グラフィックス第 11 回）です。フレーム生成（frame generation）は、オプティカルフロー（optical flow）、モーションベクトル、2 枚の画像から、描画された 2 つのフレームの間に追加のフレームを合成します。マルチフレーム生成（multi-frame generation）はそれを複数枚挿入します。

2026 年 11 月時点の状況です（各社の発表より）。

次の図はアップスケーリングとフレーム生成を時間軸に並べたものです。灰色の矢印に比べて赤い矢印がどれだけ長いかに注目してください。

このトレードオフはモデルで見ると最も分かりやすくなります。ネイティブ解像度で 1 フレームを描画する GPU 時間を $t_n$ とし、解像度に依存しない部分 $t_f$ と画素数に比例する部分に分けます。軸ごとの解像度スケールを $s$、アップスケーラのコストを $t_u$、フレーム生成の倍率を $k$（1 はオフ）、生成フレーム 1 枚あたりのコストを $t_g$、CPU 時間を $t_c$（GPU とパイプライン化）とすると、

\[t_{\text{gpu}} = t_f + (t_n - t_f)\,s^2 + t_u + (k-1)\,t_g, \qquad t_{\text{frame}} = \max(t_{\text{gpu}}, t_c),\] \[\text{fps}_{\text{shown}} = \min\!\Big(\frac{1000\,k}{t_{\text{frame}}},\ f_{\text{refresh}}\Big), \qquad L \approx t_c + t_{\text{gpu}} + [k>1]\,t_{\text{frame}} + \tfrac{1}{2}\,\frac{1000}{\text{fps}_{\text{shown}}}\]

となります。記号の補足です。$t_{\text{gpu}}$ は描画 1 フレームあたりの GPU 時間の合計、$t_{\text{frame}}$ は連続する描画フレームの間隔（CPU と GPU はパイプライン化されているので遅いほうで決まります）、$f_{\text{refresh}}$ はディスプレイのリフレッシュレート（Hz）です。1000 はミリ秒を秒に換算する係数で、$1000/t_{\text{frame}}$ が描画フレームレート、それに $k$ を掛けると表示フレームレートになります。$t_u$ は $s<1$ のときだけ加えます（ネイティブ解像度ではアップスケーラは不要です）。$[k>1]$ は条件が成り立つとき 1、そうでなければ 0 になる指示関数です。

遅延 $L$（ms）は、入力を処理する CPU の仕事、GPU の仕事、$k > 1$ のとき補間のために保持する 1 フレーム、そして平均で半分の表示間隔を数えています。OS、ディスプレイ、NVIDIA Reflex などの技術は無視しているので、測定値ではなく説明のための例として扱ってください。

計算例。 $t_n = 20$ ms（ネイティブで 50 fps）、$t_f = 2$ ms、$t_c = 4$ ms、$t_u = t_g = 1$ ms、リフレッシュレートの上限なしとします。

  • ネイティブ、$k=1$：$t_{\text{gpu}} = 20$ ms なので 50 fps、$L = 4 + 20 + 10 = 34$ ms。
  • $s = 0.67$、$k = 1$：$t_{\text{gpu}} = 2 + 18 \times 0.4489 + 1 = 11.08$ ms なので 90 fps、$L = 4 + 11.08 + 5.54 = 20.6$ ms。アップスケーリングでゲームは滑らかになり、しかも応答も速くなります。
  • $s = 0.67$、$k = 4$：$t_{\text{gpu}} = 14.08$ ms で描画は 71 fps、表示は 284 fps ですが、$L = 4 + 14.08 + 14.08 + 1.76 = 33.9$ ms で、ネイティブ 50 fps と同じ遅延です。

同じモデルを Python で書くと次のとおりです。

def frame_model(scale, k, t_native=20.0, t_fixed=2.0, t_up=1.0, t_gen=1.0, t_cpu=4.0, refresh=1e9):
    render = t_fixed + (t_native - t_fixed) * scale ** 2
    gpu = render + (t_up if scale < 0.999 else 0.0) + (k - 1) * t_gen
    frame = max(gpu, t_cpu)
    fps = min(k * 1000.0 / frame, refresh)
    latency = t_cpu + gpu + (frame if k > 1 else 0.0) + 0.5 * 1000.0 / fps
    return 1000.0 / frame, fps, latency          # rendered fps, displayed fps, latency (ms)

for scale, k in [(1.0, 1), (0.67, 1), (0.67, 4)]:
    print(scale, k, [round(v, 1) for v in frame_model(scale, k)])

次の図では、4 通りの $s$ について $k$ を 1 から 6 まで変え、表示 fps と遅延がどう変わるかを読み取ります。

このため各社はフレーム生成を遅延低減技術と組み合わせています（NVIDIA Reflex。完成したフレームを最新のマウス入力で再投影する Reflex 2 の「Frame Warp」は、NVIDIA のページではまだ近日提供とされています）。また、フレーム生成はすでにプレイ可能なベースフレームレートから使うことが推奨されています。ここでトレードオフを体感してみてください。

フレーム予算エクスプローラ（上のモデルを使用）。マウスやタッチでスライダを動かし、内部解像度スケール、ネイティブの描画コスト、アップスケーラのコスト、フレーム生成倍率 $k$ を変え、ディスプレイのリフレッシュレートを選びます。表示 fps、描画 fps、推定遅延、描画フレームあたりの GPU 時間の内訳、遅延の内訳、そして 100 ms 分のフレーム帯（青が描画フレーム、緑が生成フレーム）が読み取れます。試してみましょう：ネイティブ 20 ms、スケール 1、k = 1。次にスケール 0.5。最後に 240 Hz 上限で k = 4。

ニューラル放射輝度キャッシュ

リアルタイムのパストレーシングには多数のバウンスが必要ですが、それでは高すぎます。ニューラル放射輝度キャッシュ（neural radiance cache, NRC、Müller et al., SIGGRAPH 2021）は、ゲームの実行中に小さな MLP を学習します。一部のパスを長く追跡して学習の目標値とし、ネットワークは出射放射輝度を位置、方向、マテリアルの関数として学びます。その他のパスはすべて 1〜2 回のバウンスで止め、代わりにキャッシュに問い合わせます。論文は 1080p で 1 フレームあたり約 2.6 ms と報告しています。これはグラフィックス第 06 回の放射照度キャッシュやプローブの学習版の親戚です。AMD の FSR Redstone の Radiance Caching も同じ考え方にもとづいています。

ニューラルマテリアルとニューラルテクスチャ圧縮

映画品質の多層マテリアル（フレーク入りの車の塗装、コーティングされた布、陶磁器）は、多くのテクスチャ参照と長い BRDF の評価を必要とします。Real-Time Neural Appearance Models（Zeltner et al., SIGGRAPH 2024）は、多層 BRDF 全体を、潜在テクスチャと、シェーダの中で動く小さな MLP デコーダで置き換えます。著者らは、近似対象の非ニューラルな多層マテリアルより 1 桁以上速く評価できると報告しています。これはハイブリッドの部品です。エンジンは引き続きラスタライズやレイトレースを行い、マテリアルの評価をネットワークが担います。

ニューラルテクスチャ圧縮（neural texture compression, NTC、Vaidyanathan et al., SIGGRAPH 2023）は、マテリアルのすべてのチャンネル（アルベド、法線、ラフネス、メタルネス、アンビエントオクルージョン）をまとめて圧縮します。マテリアルごとに低解像度の潜在特徴グリッドと小さな MLP を保存します。画素をシェーディングするときは、テクセルの UV で潜在量をサンプリングして MLP を実行し、全チャンネルを一度に出力します。テクセル単位で評価するので、動画コーデックにはないランダムアクセス性を保っています。論文のプロファイルは画素・チャンネルあたり 0.2〜1.0 ビット（bits per pixel per channel, BPPC）で、比較対象のブロック圧縮（BCn）のベースラインは約 4 BPPC です。そのベースラインと比べて、約 30% 少ないメモリで 16 倍のテクセルを保持できると報告しています。

次の図では、左半分がシェーダ内でのデコード、右半分が記憶容量の比較です。

計算例。 チャンネル数はマテリアルセットによって異なります（図の模式図では 8 つ）。ここでは 4096 × 4096、9 チャンネルのマテリアルを仮定すると、$4096^2 \times 9 = 150{,}994{,}944$ チャンネル・テクセルです。4 BPPC なら $603{,}979{,}776$ ビット $= 72$ MiB、1.0 BPPC なら 18 MiB、0.2 BPPC なら 3.6 MiB です。マテリアルが数百あれば、この差はシーンが 8 GB の GPU に収まるかどうかを決めます。

texels, channels = 4096 * 4096, 9
for name, bppc in [("BCn baseline", 4.0), ("NTC high", 1.0), ("NTC low", 0.2)]:
    print(f"{name:13s} {texels * channels * bppc / 8 / 2**20:6.1f} MiB")

代償は計算量です。テクスチャのサンプル 1 回ごとに、小さなネットワークの評価が必要になります。そこでシェーダの中のテンソルコアが登場します。

ニューラルシェーダと cooperative vectors：API の状況

ピクセルシェーダの中で MLP を効率よく動かすには、シェーダが小さな行列ベクトル積をテンソルユニットに渡す必要があります。API はまだ固まっていません。

  • Vulkan には、NVIDIA のサンプルが使うベンダー拡張 VK_NV_cooperative_vector（仕様のソース）があります。
  • DirectX：Microsoft は HLSL の「cooperative vectors」をプレビューしていましたが、2025 年 9 月の記事で、この機能を Shader Model 6.9 には入れないと発表しました。代わりに、Shader Model 6.10 に予定されている行列・ベクトルの統一設計（「LinAlg」）に置き換えられ、現在はプレビュー段階です。SM 6.9 自体は 2026 年 2 月にリリースされ、ロングベクトル、シェーダ実行の並べ替え、オパシティマイクロマップ、DXR 1.2 を含んでいます。
  • NVIDIA RTX Kit（概要）は RTX Neural Shaders とニューラルテクスチャ圧縮 SDK をまとめたもので、どちらもベータ扱いです。RTXNTC SDK v0.10 は DX12 SM 6.10 経由の推論を追加し、まだ製品には使わないよう警告しています。RTX Neural Materials は未リリースとされていました。

つまり 2026 年 11 月時点では、ニューラルなアップスケーリングとフレーム生成は数百本の発売済みゲームで使われています。ニューラルマテリアルとテクスチャ圧縮は成熟した研究でベータ版の SDK もありますが、標準のシェーダモデルでのサポートを待っている段階です。

3. エンジンの中のガウシアンスプラット

スプラット（ニューラルレンダリング第 04 回）がエンジンにとって魅力的なのは、ラスタライズ（投影、ソート、アルファブレンド）で描画でき、実行時にネットワークが要らないからです。撮影した実在の場所が、数時間でゲームに使える背景になります。ホームページの Gaussian World デモは WebGL 2 でスプラットを描画しており、ニューラルレンダリング第 06 回では撮影から VR までを順に解説しています。

2026 年 11 月時点のエコシステムは次のとおりです。

  • 標準：Khronos は glTF 拡張 KHR_gaussian_splatting をリリース候補として 2026 年 2 月に発表しました。拡張の README では現在、状態が批准済み（ratified）となっています。Niantic のオープンな SPZ 形式（リポジトリ、MIT）は PLY より約 10 分の 1 の大きさで、圧縮スプラットに広く使われています。
  • Web：PlayCanvas のエンジンはスプラットをネイティブに描画でき、LOD のストリーミングにも対応しています。オープンソースのエディタ SuperSplat（リポジトリ）では、ブラウザで撮影結果を整理・編集できます。Spark（sparkjs.dev、World Labs 製）は three.js ベースのスプラットレンダラで、PLY や SPZ などを読み込めます。
  • ゲームエンジン：公式のリリースノートを見る限り、Unreal、Unity、Godot に組み込みのスプラットレンダラはありません。プラグインは多数あります。Unity には Aras Pranckevičius の UnityGaussianSplatting（MIT。作者はもう積極的には開発しないとしています）、Unreal には Luma や Volinga などのプラグイン、Godot にはコミュニティのアドオンがあります。

技術的な課題はハイブリッドレンダリング（hybrid rendering）です。スプラットはメッシュ、ライト、影、ポストプロセスと共存しなければなりません。標準的な手順は図のとおりです。まずメッシュの G バッファを描き、スプラットを投影してソートし、メッシュの深度との深度テストを行って合成します。こうすると、キャラクターが撮影した彫像の後ろを歩けます。スプラットはライティング済みで（色に撮影時の光が焼き込まれています）、正しい影も落としません。スプラットのリライティングと影は活発な研究テーマです（ニューラルレンダリング第 05 回）。

商用サービス（Meshy、Tripo、Hyper3D Rodin など）は、同様のモデルにリトポロジー、UV 展開、PBR ベイクを組み合わせて提供しています。エンジンにとって大事な問いは「メッシュを作れるか」ではなく、「そのままゲームに使えるアセットを作れるか」です。妥当な三角形数のきれいなトポロジー、重なりのない UV、ライティングを焼き込んでいない個別の PBR マップ、正しいスケールとピボット、衝突用の代理形状、LOD が必要です（リメッシュと簡略化はグラフィックス第 08 回を参照）。2026 年時点で、生成アセットは小物、プロトタイプ、背景コンテンツなら実用段階ですが、主役のアセットや変形するものにはアーティストの手直しが必要です。

マテリアル、モーション、プロシージャル生成

  • PBR テクスチャとマテリアル：拡散モデルが、テキストや写真からタイル可能なアルベド、法線、ラフネスのマップを生成します（Adobe の Substance 3D ツールには Firefly ベースのテキストからテクスチャを作る機能があります）。Hunyuan3D の Paint モデルや TRELLIS.2 は PBR マップを直接出力します。
  • モーション：MDM（Tevet et al., ICLR 2023、arXiv 2209.14916）などのテキストからモーションへの拡散モデルが骨格アニメーションを生成し、それが第 05 回のアニメーションランタイムに入ります。それ以外の部分はグラフィックス第 09 回で扱っています。
  • プロシージャル生成と LLM：LLM が幾何を直接作るのではなく、従来のプロシージャルシステム（Houdini のグラフ、Blender のスクリプト、レベルレイアウトの文法）に渡すパラメータやコードを書きます。出力は編集可能で決定的で、予算内に収まります。これがこのパターンが制作現場で好まれる理由です。

5. エンジンとエディタの中の LLM エージェント

Model Context Protocol（MCP。2024 年 11 月に Anthropic がオープンソース化、仕様）を使うと、LLM はサーバが公開するツールを呼び出せます。エディタの MCP サーバは、オブジェクトの作成、コンポーネントの編集、ゲームの実行、コンソールの読み取りといった操作を公開します。するとエージェントは、シーンを組み立て、スクリプトを書いて実行し、エラーを読んで直すことができます。公式のツールとコミュニティのプロジェクトは分けて考えましょう。

6. ニューラルゲームエンジンと対話型世界モデル

スペクトルの一番端では、エンジンが、過去のフレームとプレイヤーの行動から次のフレームを予測するネットワークに置き換わります。

\[\mathbf{o}_{t+1} \sim p_\theta\big(\mathbf{o}_{t+1} \,\big\vert\, \mathbf{o}_{t-c+1:t},\ \mathbf{a}_{t-c+1:t}\big)\]

ここで $\mathbf{o}_t$ はフレーム（通常はオートエンコーダの潜在表現）、$\mathbf{a}_t$ は行動（キー、マウス、カメラ姿勢、テキスト）、$c$ はコンテキスト長、$p_\theta$ はパラメータ $\theta$ のネットワークが表す条件付き分布で、$\sim$ はそこからのサンプリングを意味します（同じ入力でも異なる次のフレームが得られます）。多くのモデルは自己回帰型の動画拡散（autoregressive video diffusion）モデルです。拡散モデルやフローモデルが、過去の潜在表現と行動のウィンドウを条件として次の潜在フレームを生成し、リアルタイムに届くようデノイズを数ステップまで蒸留しています。生成の仕組みは世界モデル第 03 回、3D に一貫した世界の生成は世界モデル第 04 回で説明しています。ここではそれらをエンジンとして見ます。

本シリーズのエンジンと比べるとどうでしょうか。

  • 何を学ぶか：レンダリング、物理、ゲームのルール、さらには他のプレイヤーの振る舞いまで、動画と行動から暗黙的に学びます。手で指定するものは何もありません。それが魅力（動画さえあればどんな世界でも作れる）であり、問題（何も保証されない）でもあります。
  • 操作：キーとマウスは学習された行動埋め込みに対応します。新しいシステムはテキスト（「雨を降らせて」）、カメラ姿勢、空間メモリを加えています。「3 番のドアを開ける」といった API はなく、編集はプロンプトや条件付けを通すしかありません。
  • フレームレートと遅延：リアルタイムにするには、拡散モデルを数ステップに蒸留し、過去の活性をキャッシュし、しばしば専用ハードウェア（Oasis は Etched のチップ、GameNGen は TPU）を使います。1 フレームごとに大きなネットワークを評価するので、数ミリ秒で済むラスタライズと比べ、プレイヤー 1 人 1 時間あたりのエネルギーと配信コストは従来のエンジンよりはるかに高いままです。
  • 記憶と一貫性：コンテキストウィンドウが有限なので、世界はずれていきます。振り返ると部屋が変わっているかもしれません。対策は、より長いコンテキスト、姿勢付きの過去フレームを空間メモリ（spatial memory）として検索すること（RTFM、WorldPlay）、そして明示的な 3D の中間表現です（Marble はスプラットとメッシュを出力し、それを従来のエンジンが描画します）。
  • 失敗のパターン：物体の変形や消失、物理法則の破れ（めり込み、浮遊する物体）、長いロールアウトでの品質の劣化、行動の効果が遅れる・現れない、学習分布の外での劣化。

したがって 2026 年の現実的な姿は、置き換えではなく融合です。世界モデルはコンテンツ、プロトタイプ、学習環境を生成し、従来のエンジンは永続性、厳密なルール、安価なレンダリングを提供します。3D の出力（スプラット、メッシュ）が両者の橋渡しになります。

7. データ工場としてのエンジン

エンジンの最後の役割が、このシリーズと身体性 AI をつなぎます。世界モデルやロボットの方策のための学習データを生成することです（第 05 回の第 10 節）。

  • シミュレーションと合成データ：Omniverse Replicator（ドキュメント）付きの Isaac Sim、Genesis、第 05 回の GPU シミュレータは、ラベル付きのフレームやロボットの軌道を何百万も描画します。Matrix-Game 3.0 は、データエンジンの一部として Unreal Engine の描画結果で明示的に学習しています。従来のエンジンが、いまやニューラルなエンジンの学習データを作っているのです。
  • 世界基盤モデル：NVIDIA の Cosmos プラットフォーム（Agarwal et al., arXiv 2501.03575）は、フィジカル AI 向けのオープンな動画世界モデルを提供しています。Cosmos-Predict2.5 と Cosmos-Transfer2.5（arXiv 2511.00062）は未来の動画を予測し、シミュレータの描画結果（セグメンテーション、深度、エッジ）をフォトリアルな動画に変換します。これは、sim-to-real の見た目のギャップを、より良いレンダラではなく生成モデルで埋める方法です。2026 年 5 月には NVIDIA が Cosmos 3 ファミリーを公開しました（リポジトリ）。
  • 合成されたロボット経験：NVIDIA の GR00T-Dreams ブループリントは、ロボットに合わせて Cosmos モデルを追加学習し、1 枚の画像からタスクの動画を生成し、そこから行動を取り出します。Cosmos Policy（arXiv 2601.16163）は、動画世界モデルを直接ロボットの方策にファインチューニングします。

8. 未解決の問題と学習の道筋

2026 年末時点の未解決の問題です。

  1. ニューラルエンジンの制御性と永続性：厳密なゲーム状態、セーブとロード、マルチプレイの一貫性、決定的なリプレイ。いずれも第 01 回のエンジンには簡単で、世界モデルには未解決です。
  2. コスト：ラスタライズと比べたときの、ニューラルなフレームのプレイヤー 1 時間あたりのエネルギーと配信コスト。蒸留、キャッシュ、専用ハードウェア。
  3. 再構成のアーティファクト：フレーム生成のゴーストやディスオクルージョンの誤り、ニューラルマテリアルの時間的安定性、スプラットのリライティングと影。
  4. ニューラルシェーダの標準 API（SM 6.10 の LinAlg、ベンダー横断の Vulkan 拡張）と標準フォーマット（KHR_gaussian_splatting、圧縮スプラットの拡張）。
  5. 評価：見た目の品質だけでなく、世界モデルの物理的な正しさと一貫性をどう測るか（世界モデル第 05 回）。
  6. Sim-to-real：生成的な「変換」モデルがより良いレンダラに勝るのはどんなときか。物理をでっち上げないことをどう保証するか。

演習

  1. frame_model（ほかのパラメータは計算例と同じ）を使い、$t_n = 30$ ms のときに $k = 1$ で 60 fps に届く内部解像度スケールを求め、その遅延を $s = 1$、$k = 2$ の遅延と比べてください。
  2. モデルにディスプレイのリフレッシュ上限と「フレームペーシング」の規則を加えてください。生成フレームが役に立つのは $k \cdot F \le R$（$F$ は描画フレームレート、$R$ はリフレッシュレート）のときだけです。描画が 70 fps のとき、144 Hz で最良の $k$ はいくつでしょうか。
  3. 2048² で 9 チャンネルの異なるマテリアル 300 個を持つシーンのテクスチャメモリを、4 BPPC と 0.5 BPPC で計算してください。節約したメモリに追加でいくつのマテリアルが入るでしょうか。
  4. 「指定位置にプレハブを生成する」と「マテリアルのパラメータを設定する」の擬似 MCP ツールスキーマ（名前、説明、JSON パラメータ）を書いてください。LLM の呼び出しを実行する前に、エディタはどんな検証をすべきでしょうか。
  5. 表から世界モデルを 1 つ選び、永続性を試す実験を 3 つ挙げてください（たとえば、目をそらして戻す、ドアを開けて部屋を出る、出発点に戻る）。それぞれの場合に、従来のエンジンなら何が保証されるでしょうか。
ヒント
  1. 60 fps は $t_{\text{gpu}} = 1000/60 \approx 16.7$ ms に当たるので、$2 + 28 s^2 + 1 = 16.7$ を $s$ について解きます（約 $0.70$）。遅延は約 $4 + 16.7 + 8.3 = 29$ ms です。$s = 1$、$k = 2$ では $t_{\text{gpu}} = 31$ ms、描画 32 fps（表示 65 fps）、遅延は約 $4 + 31 + 31 + 7.8 \approx 74$ ms です。
  2. $k = 2$（140 fps）です。$k = 3$ ではリフレッシュレートを超え、追加のフレームは表示されません。
  3. $300 \times 2048^2 \times 9 \times 4 / 8$ バイト $\approx 5.3$ GiB に対し約 $0.66$ GiB です。節約した 4.6 GiB には、0.5 BPPC で約 2,100 個のマテリアル（1 個 2.25 MiB）が追加で入ります。
  4. プレハブが存在するか、位置がレベルの範囲内か、パラメータの型が合っているかを確認し、取り消し（Undo）の手順を必ず用意します。
  5. 物体の同一性、状態の変化、位置の永続性です。従来のエンジンはそれらをシーンとゲーム状態に明示的に保存しています。

これでグラフィックスエンジンのシリーズは終わりです。ここからは、生成の側面を学ぶなら世界モデルシリーズへ、前回の記事で扱ったエンジンの中で学習するロボットについて学ぶなら身体性 AI シリーズへ進んでください。
